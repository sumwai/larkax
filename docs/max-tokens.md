# 单次输出上限（max_tokens）

调用方在请求体里声明的 `max_tokens` 有一个**上界**：非流式请求超过它会被拒，
回 `400`。

这一条与按 Key 的额度、限流、钱包余额**互不相干**——那三条见
[limits.md](limits.md)。上界之内也不会改变任何行为：预留与结算还是按调用方
声明的那个数算。

## 为什么要有这条上界

预留（请求发出之前冻结的那笔钱）的输出侧按 `max_tokens` 算（见
`internal/billing` 的 `Reserve`），所以这个字段不是「预期产出」，而是
**这次请求最多会花掉多少钱**的依据。把它当上限而不是预期来填是常态
（不少 SDK 的默认值就很大），于是：

- 一条 `max_tokens=100000` 的请求，光预留就要按十万个输出 token 的单价冻住
  一大笔钱——余额本来够用的账户连第一条都发不出去，而它实际可能只产出几十个
  token。拒绝的理由（可用余额不足）与真实原因（预留按声明的上界冻）不是同一
  件事。
- 填到乘法放不下时，报出来的是「算不出预留上界」——把一个字段填得离谱说成了
  我们的内部故障，方向刚好指反：调用方该做的是把这个字段改小。

上界补住之后，预留按 `max_tokens` 冻结这件事本身是对的：非流式请求在响应
回来之前没有任何观测点，只能按调用方声明的上界管。

## 上界是多少

按**模型**取，从上往下第一条命中的生效：

| 顺序 | 取哪个 | 在哪儿配 | 什么时候生效 |
|---|---|---|---|
| 1 | 模型目录里登记的 `output_limit` | `larkaxctl model add` / `model update --output-limit` | 下一个请求 |
| 2 | 全局默认值（出厂 `65536`） | `larkaxctl settings set --key billing.max_output_tokens --value <token 数>` | 重启服务 |

两条要说清楚：

- **目录里那一列是逐个模型登记的**，与选路用的能力、上下文上限同一张表同一行
  （写它的命令见 [development.md](development.md) 的「配一条能接请求的链路」，
  读回来用 `larkaxctl model show --canonical <规范名>`）。目录里没登记
  （`NULL`，读出来是 `0`）的模型用全局默认值。**`0` 是「未知」，不是「零额度」**
  ——一次采集失败不该让整批模型用不了。
- **全局默认值只在启动时读一次**（settings 表里所有键都是这个口径，见
  `internal/settings`）。改完要重启服务；模型目录那一列每个请求都读，改完即
  生效。

出厂默认值取 `65536`：那是「目前已知的最大单次输出」这个量级，它是一道
**我们愿意单次承担多少**的界，不是上游的能力（上游的输出上限是上游的事）。
调小它会拒掉本来合法的长输出请求，调大它会让一次请求能冻住的余额变多。

## 超限时回什么

`400`，错误类型与「请求里缺 `max_tokens`」那一条相同（都是「这个字段不能用」，
调用方按类型分支时不必分辨两个都表示「改请求」的类型）。响应体点名字段，并
给出这次允许的上限：

```json
{"error":{"message":"max_tokens 100000 exceeds the per-request output limit 8192 for this model; lower max_tokens and retry",
          "type":"invalid_request_error","param":null,"code":null}}
```

Anthropic 那套（`/v1/messages`）的码放在 `error.type`，文案逐字相同。

三条边界：

- **恰好等于上界不算超。** 判据是「超过」，与选路那条目录判据的边界一致。
- **非正数的 `max_tokens` 仍然报「必须为正」**（同一个 `400`，文案不同）：
  那是同一个字段的另一个方向，措辞比「超过上限」准。
- **`max_tokens` 缺省仍是 `400`。** 预留要有上界才做得出来，所以这个字段没有
  默认值——也就不存在「不给它就能绕开上界」这条路。

## 判据落在哪个数上

别名（商家配置）上可以配 `max_tokens` 覆盖，覆盖会顶掉调用方给的那个数。这条
上界判的是**调用方在请求体里声明的那个数**，覆盖不参与：

- 超限时给调用方的那句话引用的是他自己写的字段与值，他改小就能成功。按覆盖
  之后的数判的话，他收到的会是一个他从没写过的数字。
- 覆盖是商家配置，配错了责任落在配置那一侧。按覆盖之后的数判的话，别名上写
  一个超过上界的数会让该别名下的**每一个**请求都收到 `400`，而调用方改请求
  一点用都没有。

代价是这个方向的：调用方在上界之内、而别名覆盖把上界抬到上界之上时，这次
请求不会被这条拒，预留仍按覆盖之后那个数冻（见 `internal/gateway` 的
`outputBound`）。那一笔多冻出来的钱是商家配置的结果，要改的是那条别名。

**流式请求不在这一条里**：流式有中途观测点，钱的处置是随流递进冻结。

## 改它的时候

| 要改什么 | 改哪 |
|---|---|
| 判据本身（比哪个数、哪些路径豁免） | `internal/gateway` 的 `checkOutputCap` 与 `outputLimit` |
| 上界从哪来、允许的范围 | `internal/assembly`（键 `billing.max_output_tokens`）与模型目录那一列 |
| 超限时给调用方的状态码与文案 | `internal/api` 的 `httpStatusOfUpstream` |
| 出厂默认值 | `internal/migrate/sql/00026_max_output_tokens.sql` |
