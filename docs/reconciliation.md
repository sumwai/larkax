# 对账

对账任务校验钱包快照与账本是否一致，并把不一致落库、告警。

```sh
go run ./cmd/larkaxctl reconcile
```

它不需要额外参数：开关与口径全部来自 `settings` 表。发现不一致时以非零退出码
收尾，方便外部调度器（cron、Kubernetes CronJob）直接判定这一轮的结果。

```sh
# 发现不一致时退出码为 1，报告已经打到 stdout
go run ./cmd/larkaxctl reconcile || echo "这一轮有需要人看的东西"
```

## 校验什么

| 快照字段 | 权威值 | 怎么算 |
|---|---|---|
| `user_wallets.balance` | `ledger_entries` | **归一到** `user:<id>` 的分录之和（`user:042` 那种写法也算这个用户的） |
| `user_wallets.frozen` | `billing_requests` | `status='pending'` 的行的 `reserved_amount` 之和 |

`frozen` 的权威值不在账本上，因为冻结与释放都不写分录——它们没有发生任何资金
流动，只是把冻住的钱放开。写一条零金额分录留痕会让「有分录就说明发生过资金流动」
这个判据失效，而对账要靠它。

除这两项外还报两类结构性问题：

- **缺钱包行**：有分录或有预留，却没有 `user_wallets` 行。对账不新建钱包行——
  新建需要知道用户是否存在、默认用哪种资产，那不该由对账来猜。
- **畸形科目**：`ledger_entries.account` 里以 `user` 开头但不合规范写法的行。
  规范写法只有一种——`user:<正整数>`，十进制、无前导零、无正号，与
  `ledger.ParseAccount` 放行的是同一套。这一类里还要分两种，处置完全不同：

  - **读得出用户 id 的**（`user:042`、`user:+42`）：那笔钱**是**算进那个用户钱包的。
    写路径把后缀读成整数，对账的汇总按同一口径归位，所以余额比对不会因此报错。
    报出来是要订正写法，不是钱不见了。

    有一个方向要注意：如果这样一条分录**当初没被算进钱包**（只可能来自绕过
    `internal/ledger/store` 的写入），余额比对就会发现快照比账本少，默认口径
    `resync_snapshot` 于是把余额**调高到账本值**。这与本文档开头那条缺陷方向
    相反，但同样是把钱改了——它是「能归位的一律归位」的必然结果：既然按口径
    这笔钱属于这个用户，快照就该包含它。
  - **读不出的**（`user :42`、`user:abc`、`user:0`、位数超限）：那笔钱既不属于任何
    用户的钱包，也没有别的地方会看见。`user:0` 属于这一类：0 号用户不存在
    （用户 id 从 1 起），那个后缀读得成整数，但钱没有落在任何钱包上。

## 不一致意味着什么

**它是异常信号，不是一种正常状态。** 它说明有代码路径绕过了
`internal/ledger/store`——直接改了钱包行，或者直接写了分录——或者预留算错了。

## 发现之后怎么办

默认**只报告不修正**。修正是 `reconcile.auto_repair` 打开之后才有的行为，
因为自动修正会把一次偶发的 bug 变成一次静默的数据改写。

### 修正的方向

`reconcile.repair_mode` 选一个，两个取值各自自洽，区别只在「哪个值算数」：

| 取值 | 做法 | 账本 | 快照 |
|---|---|---|---|
| `resync_snapshot`（默认） | 把快照重算成账本值，**不写分录** | 不动 | 改成账本值 |
| `adjust_ledger` | 写一条调账分录把账本对齐到快照值 | 加一条分录 | 不动 |

**为什么 `resync_snapshot` 不写分录。** 账本里的分录从写下那一刻起就是权威的，
不一致意味着**快照**偏离了账本。修正快照不需要任何分录——没有资金流动，
只是重算一个派生值。

反过来说，「写一条 adjustment 分录把快照修正到账本值」这个说法本身不成立：
设账本值 L、快照值 W，写一条金额 D 的分录去修，修完账本变成 L+D，而快照要
被修正到的目标**正是**账本值——于是快照变成 L+D，两者又差 D。下一轮再发现
一次，再写一条，要么永远修不平，要么把差额算两次。

`adjust_ledger` 是另一条自洽的路：以**快照**为准，写分录把账本改到快照的值。
它的取舍是明确的——从不减少用户余额（用户的账面数字就是他看到的数字），
代价是把一笔来路不明的钱记进了账本。

两种口径都不 `UPDATE` 分录。账本只追加，这一点没有例外。

### 差额落在哪个科目

`adjust_ledger` 下，修正分录的对家由 `reconcile.difference_account` 指定，
默认是 `reconcile_difference`。

之所以不默认记进 `platform_revenue`：对账差额的**来路不明**，它可能是一处
代码绕过了 store，也可能是预留算错。记为平台收入等于让一笔没人解释过的钱
混进经营收入，而收入是要被看、被汇总、被用来定价的。

`reconcile_difference` 的余额是**待查项**：查清来路之后再写一笔人工调账把它
转进 `platform_revenue`。长期非零本身就是一条应当被看见的信号。

### 修不了的情况

报出来但不动手，`Unrepairable` 字段说明为什么：

- **账本值为负**：用户欠平台钱。夹到零等于平台悄悄认下差额，而那笔钱从此在
  任何报表上都看不见。它只能由人处置（补扣、冻结账号）。
- **缺钱包行**：见上。
- **畸形科目**：见上。读不出用户 id 的那种，修它要先判断这笔钱原本该记给谁，
  猜错等于把钱挪到别人账上；读得出用户 id 的那种只要订正写法，金额已经归到了
  那个用户名下，不涉及资金怎么处置。

## 跑多快

一轮全表扫描在大库上很贵，所以默认按增量跑：只看上次跑成之后**变动过**的行。
起点记在 `reconcile_runs.watermark`，取的是上一轮**开始**的时刻而不是结束时刻
——跑的过程中新写入的行会被下一轮再读一遍。宁可重复读（比对是幂等的），
不能漏读。

判定「变动过」看三个来源，都要：

- `user_wallets.updated_at` 变过：快照被动过。
- `ledger_entries.created_at` 变过：分录写了而快照没跟上。那种情况下钱包行
  一动不动，只看 `updated_at` 永远发现不了。
- `billing_requests.started_at` 变过（且那一行还是 `pending`）：有未结算预留、
  却既没有钱包行也没有分录的用户，前两个来源都看不见他。

第三个来源的时间列与另外两个**不同源**：`started_at` 是应用进程写进去的墙钟
（写入时显式给了值，不是数据库的 `now()`）。应用时钟比数据库慢时，刚写入的
预留可能落在起点之前，这一轮读不到，而起点只增不减——下一轮同样读不到。
它与下面那个盲区是同一类，同样由定期全量兜底。

增量有一个盲区：**两边都在上次扫描之前就已经错着**的行，它永远不看。所以
超过 `reconcile.full_scan_interval_hours`（默认 168 小时）就做一次全量，
回到「每一行至少被完整看过一次」。

## 配置项

| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `reconcile.auto_repair` | bool | `false` | 是否修正。关闭时只报告 |
| `reconcile.repair_mode` | string | `"resync_snapshot"` | 修正方向 |
| `reconcile.difference_account` | string | `"reconcile_difference"` | `adjust_ledger` 下的对家科目 |
| `reconcile.shard_size` | int | `1000` | 一批比对的钱包行数上限 |
| `reconcile.full_scan_interval_hours` | int | `168` | 两次全量之间的最长间隔，`0` 表示每次都全量 |

加配置项的步骤见 [development.md](development.md#加一个配置项)。

## 运行记录

每轮在 `reconcile_runs` 留一行：比对了多少行、发现几条不一致、修了几条、
起点在哪、结局是 `done` 还是 `failed`。**只打日志是不够的**——日志轮转之后
「账目不一致」就消失了，而它恰恰是要在几周后回答「这笔钱什么时候开始少的」
的问题。

一轮跑完——不管跑成还是失败——都会把结局写回去，**超时也一样**：结账那一步
用的是不带取消的 `context` 加一个独立短超时。`ctx` 已经不能用的那一刻，正是
这一行最该写进去的时候；跟着一个已经取消的 `ctx` 走，库里就会留一行
`status='running'`。

留一行 `running` 的害处不是「下一轮读错起点」——起点只看结局是 `done` 的那些行，
没有任何代码读 `running`——而是运行记录里堆起一串看不出结局的行，事后翻的时候
说不清哪一轮是真的没跑完。

留下 `running` 行只有两种情形：**硬崩**（进程被 kill、机器掉电），以及结账这一步
**自己**写不进去（库不可用，或它的那个短超时到了）。两种都等下一轮来清：下一轮
开始时，`started_at` 早于一小时的会被标成 `failed`。阈值取一小时是因为它必须
**长于一轮合法对账可能活着的时长**（命令行给单轮的上限是 30 分钟），否则并发的
另一轮会把一个还活着的运行标成 `failed`。两个数呈这个大小关系是有意的，不是巧合。

## 未消除的不一致

比上面那张表更重要的是 `reconcile_findings`：**尚未消除的不一致各占一行**，
直到某一轮发现它消失了才删掉。

没有它的话，一条只报告、没被修掉的不一致（默认就是不修）会在下一轮**消失**：
增量扫描只看上次起点之后变动过的行，而这条不一致自己不会再变动，于是告警响
一次就永久安静，不一致还挂在那里。那比「不告警」更糟——它看起来像已经处理过了。

有了它：

- 每一轮都会把它重新报出来，直到有人处理；
- `first_seen_at` 回答「这笔钱从什么时候开始不对的」（每轮只更新 `last_seen_at`）；
- 候选查询带上这些用户，于是增量扫描不会跳过它们。

`scope` 的形态有两类：钱包类不一致是 `user:<id>@<asset>`，畸形科目是
`account:<科目原文>`。

## 告警

不一致逐条走 `Alert` 通道，`larkaxctl reconcile` 接的是错误级别的结构化日志
（`LogAlerts`）。要换成通知或工单，实现 `store.Alert` 即可——告警落地的方式
是部署的事，`store` 只管「发现了什么」。

## 测试

对账的集成测试需要真 PostgreSQL（`LARKAX_DB_DSN`），没有时跳过。
它验证的性质只在真库上存在：行锁与加锁顺序、`UPDATE` 的影响行数、
`numeric` 的精度。

```sh
export LARKAX_DB_DSN="postgres://larkax:placeholder@127.0.0.1:5432/larkax?sslmode=disable"
go test ./internal/ledger/store/
```
