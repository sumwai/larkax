# 渠道健康与额度

选路时看两类信号：渠道最近怎么样（健康度），以及它还剩多少额度。两类都由
**调用本身**产生——每完成一次上游调用，结局就被写回数据库，下一次选路就能
看到；额度这一路还会在渠道被用到、而探测结果过期时，向所有过期渠道问一次，
是否支持查询由适配器当场答回。没有独立的采集进程，也不需要额外的定时任务：
长期没有流量的渠道就停在原处。

写入方是 `internal/channels.Recorder`：`internal/gateway` 声明 `CallRecorder`
接口，本包实现它，`internal/assembly` 把它装到 Gateway 上。写入发生在收尾
路径上，但**失败只留痕、不影响请求**：一次调用该不该成功，不取决于这次记账
写没写进去。额度实测是另一个写入方（`internal/channels.QuotaProbe`），它在
渠道被用到时异步触发，见下面的「额度」一节。

## 一次调用写三处

| 写什么 | 落在哪 | 谁读它 |
|---|---|---|
| 连续失败计数 | `channels.consecutive_failures` / `last_failure_at` | `route.DrainReason`：连续失败到阈值就暂时摘除 |
| 小时桶计数 | `channel_health_rollup.requests` / `successes` / `failures` | `route.Health.SuccessRate` |
| 小时桶的延迟、缓存与成本 | `channel_health_rollup.latency_p95_ms` / `cache_hit_tokens` / `cache_miss_tokens` / `cost` / `cost_events` | `route.Health.LatencyP95`、`route.Candidate.CacheHitRate` 与 `route.Candidate.CostPerUnit` |
| 额度自记账 | `channel_quota_state` 的余量与可信度 | `route.DrainReason`（能不能用）与 `route.scoreQuota`（怎么排） |

三处各自按主键或唯一键定位单行，没有把它们绑在一起的大事务：健康度与额度是
两个独立的信号，其中一处写不进去不该让另外两处也不写。

### 延迟、缓存与成本是**重算**出来的，不是累加的

后几列要的是分位数、比例与合计，而分位数与比例都不是可累加的量：每次调用
只有一个耗时样本，把它写进 p95 等于给一个错的数起了一个对的名字。所以样本
留在用量事件里（`usage_events.duration_ms` 是「这次调用花了多久」），写入方
每次按桶把它们重新聚一遍。桶带模型维度（`(channel_id, model, bucket)`），
一次重算同时更新两类行：

- **模型行**（`model` 是规范模型名）：成本与成本事件按模型分开，选路按当前
  要发的模型取。
- **渠道级合并行**（`model = ''`）：本渠道全模型加总。健康列（计数、延迟、
  缓存）只读这一行，所以它们的语义与加模型维度之前一字不差。

| 列 | 算式 | 口径 |
|---|---|---|
| `latency_p95_ms` | `percentile_disc(0.95) WITHIN GROUP (ORDER BY duration_ms)` | 取一个**真实观测到**的毫秒数；NULL 样本不参与 |
| `cache_hit_tokens` | `SUM(cache_read_tokens)` | 命中缓存、直接复用的输入 |
| `cache_miss_tokens` | `SUM(prompt_tokens + cache_write_tokens)` | 没被缓存服务到的输入总量 |
| `cost` | `SUM(upstream_cost)` | 这个桶里该组请求的上游成本合计；没有一条带成本的事件时是 NULL |
| `cost_events` | `COUNT(upstream_cost)` | 带成本的事件条数，单位成本的分母；空组是 0 |

缓存两列的分母口径与读侧一致：`cacheHitRate` 算的是 `hit / (hit + miss)`，
而 `usage_events.prompt_tokens` 已经是**不含缓存**的输入、`cache_write_tokens`
是这次新建的缓存条目——两者相加正好是输入总量。`cache_write` 不是「没命中」
的另一种说法，但写入的 token 同样没有被命中服务到，所以它落在 miss 一侧。

`upstream_cost` 由结算时算出：按（渠道，规范模型）从 `upstream_costs` 选一条
规则，用这次的实际用量乘出来（见 `internal/pipeline` 的 `upstreamCost`）。
它装的是**我们付给上游多少**，不是售价——售价是 `usage_events.cost`，同一模型
在各渠道上由我们的定价规则决定，拿它比较渠道是无差别项。

没有生效的成本规则时两处都是 NULL（不是 0）：读侧 `CostPerUnit` 为 nil，
成本这一维不参与加权。0 落库有两种来路：规则算出来确实是 0（上游不要钱），
以及接上写入侧之前那一列 `NOT NULL DEFAULT 0` 留下的旧桶（那些桶不会再被重算）。
读侧把 0 一律当成「没有数据」，两种都不会被当成免费。

`CostPerUnit` 的分母是 `cost_events`，不是 `requests`：分子与分母因此来自
同一批事件。失败的尝试不结算、也没有用量事件，不会再把平均数摊低。桶里只有
部分请求带成本时，`SUM` 与 `COUNT` 都只算有值的那些——覆盖面不全影响的是
分母的大小，不会让单价被摊薄。

迁移 00057 之前写下的老桶没有模型维度：它们的 `model` 是空串，落进合并行，
健康列照旧可读；按模型查成本时它们不匹配任何模型名，**读作未知**——不拿合并
值冒充某个模型的成本。

这个「未知」不会持续到某个固定时长之后：写入方重算的是**当前小时桶**，所以
一对（渠道，模型）在部署之后第一次有流量时，这一小时的模型行就由那次重算
写出来；成本规则生效时，按模型的单位成本随即有数。读侧回看的是 24 小时
窗口内的桶（见 `internal/channels` 的 `healthWindow`），那是回看窗口，不是
数据变得可用所需的时间。

在那一小时第一次有流量之前，该渠道在该模型上的成本读作「没有数据」，成本
这一维**不参与加权**——不记 0，也不拿合并行的值冒充。成本在
`route.DefaultWeights` 里权重 0.5，而模型行是按（渠道，模型）各自出现的，
所以升级后的这段窗口里，凡是还没有新流量的模型，成本这一维都退出加权，
排序会随之变化。同一段时间 `larkaxctl channel health` 的成本列仍然显示值
（它读 `model = ''` 的合并行），与选路按模型读的口径不同——这个差别是
加模型维度时引入的。

重算是幂等的：上一步成功、这一步失败时写进去的是旧值，而该桶的下一次调用会
把它们整体重算一遍，不会像累加那样永久偏离。代价是每记一次调用要扫一遍该渠道
在当前小时里的用量行（走 `usage_events_channel_idx`）。

因此**健康度要在结算之后记**：用量事件是结算事务写的，提前记的话这个桶的
分位数与成本里不含刚刚这一次请求，它要等下一次调用才被带进去——那个数总落后
一个请求，而金额上完全看不出来。

### 结局分三种，不是两种

| 结论 | 什么情况 | 对渠道的影响 |
|---|---|---|
| `success` | 上游正常返回 | 连续失败清零 |
| `failure` | 上游可重试的错误，以及 401 / 402 / 403 | 连续失败加一 |
| `unattributed` | 客户端断开；请求本身不合法（400 / 404 / 422、未知模型） | 既不加一也不清零，只计入请求数 |

`unattributed` 这一档是必须的：客户端发来一个坏请求，不该让一个健康的渠道
朝摘除走一步。客户端断开时上游已经为输入计了费，所以那一次调用的**用量照扣**
额度——只有连续失败那一列不动。

流式请求在「上游接受请求」时还不算成功：之后还可能中途断掉。所以流式路径上，
换渠道过程中失败的尝试当场记，真正被采用的那一次**读完流之后**才记，一个渠道
一次请求只记一条。

### 连续失败是一个真计数

不是从小时桶里推出来的。桶重建不出「连续」这个量：桶内只要有过一次成功，
那段连续失败的长度就落在 0 与 `failures` 之间，推出来的数与真值差多少取决于
流量。

读取侧有一条**冷却期**（15 分钟）：计数非零、但最后一次失败已经过去 15 分钟
时按 0 读。这不是宽松，是防死锁——被摘除的渠道没有流量，没有流量就没有调用，
没有调用计数就永远降不回去，那个渠道会一直摘着。冷却期一过放它进来试一次：
成了就清零，败了接着加。`last_failure_at` 为 NULL 而计数非零（只可能来自手工
写入）同样按已过期处理；按「还在冷却」处理的话，那行数据会让渠道永远不可用。

摘除阈值在 `internal/route`（`consecutiveFailureCutoff`），不在这里：写入侧
只记事实，怎么用它选路是读侧的事。

## 额度

`channel_quota_state.probe_kind` 说明这个余量是怎么来的：

| probe_kind | 含义 | 现状 |
|---|---|---|
| `api_query` | 查上游的额度接口得到的实测值 | 写入侧已就位，但**今天没有适配器能报回数值**——四个真实适配器都返回 `ErrUnsupported`，所以探测不会产出这一档。库里本来没有这一行的渠道，会由「查不到」插入一行 NULL 余量（`probe_kind` 取默认的 `self_accounting`）；人工录入过 `api_query` 行的渠道，探测只更新尝试时刻与结论，`probe_kind` 保持原值 |
| `self_accounting` | 以上一次已知余量为基准，按每次调用的用量往下扣 | 已接 |
| `error_observed` | 从上游的错误里推断（例如余额不足） | **未接** |

**未接的那一条不会自己出现。** 今天有两类写入方：探测会试着拿实测值（今天
没有适配器能报回数值，见下文），自记账在每次调用之后往下扣。自记账需要先有
基准：这一行不存在、或 `remaining_estimate` 为 NULL 时它推不出任何数，什么都
不写——写一行只有 NULL 的状态改变不了读侧（候选上的 `Quota.Remaining` 仍是
nil），只是一次没有信息量的写。

基准来自上游实测或人工录入。所以对一个**既不支持查询、也没有人工录入**的
渠道，额度这一路恒为未知，`route.scoreQuota` 对未知给中性分。这不是缺陷，
是「没有基准时不猜」的必然结果：基准一旦有了，自记账立刻开始跟着每次调用
往下走，不需要改代码。

### 探测什么时候发生

渠道被路由真正尝试之前（`route.Router.OnAttempt`），若它的
`last_probe_attempt_at` 为空、或早于 `settings` 的
`quota.probe_interval_seconds`，装配层接的写入方就异步发起一次探测。
**请求不等它**：这一次用的是已有的额度快照，结果留给下一轮请求读。本进程内
同一个渠道同时只允许一次探测（single-flight），并发命中过期渠道不会向上游
打出一串查询。

三种结果分开落库：

| 结果 | 写什么 | 余量 |
|---|---|---|
| 拿到实测值 | `probe_kind=api_query`、余量、`last_probe_at`、`last_probe_attempt_at`、适配器带回的重置时刻（`resets_at`，没带回时保留原值） | 覆盖 |
| 查不到（上游没有查询接口，`ErrUnsupported`） | `last_probe_status=unsupported` 与 `last_probe_attempt_at` | 不动 |
| 探测失败 | `last_probe_status=error` 与 `last_probe_attempt_at` | 不动（保留上一次有效值） |

`last_probe_at` **只记成功的实测**：它是 `Routable` 的判据，把「查不到」
写进去会让所有不支持查询额度的渠道被判成「观测过却没拿到数值」而排除。
「多久该再探一次」用的是另一列 `last_probe_attempt_at`，三种结果都会更新它；
`last_probe_status` 把「查不到」与「探测失败」分开——前者是常态，不告警，
后者记一条日志。`last_probe_attempt_at` 还承担余量见底之后的冷却期（见下一
节）；`last_probe_status` 不参与路由判据。

可信度按时长衰减（见 `internal/quota` 的基线），所以一个很久没校准过的基准
不会一直按满信度参与打分。合并、衰减、封底到 0 这些语义都在 `internal/quota`，
写入侧只负责读旧值、调用 `Merge` / `Project`、写回新值。

衰减的起点是「实测值开始显得陈旧」那一刻，它由**探测间隔**导出：连着三个
探测间隔都没拿到新的实测值，就认为探测本身出了问题。探测间隔取
`settings` 的 `quota.probe_interval_seconds`，在装配期读出来（见
`internal/assembly`）——所以改那个键，衰减起点跟着动。它默认 `300` 秒，取值
1–31536000，越界时服务**拒绝启动**并指出这个键。

### 余量见底的渠道怎么恢复

余量为 0（或手工写入的负数）的渠道会被 `Usable` 判成不可用，而探测是
「用到时才发生」的：被排除之后没有请求会命中它，`OnAttempt` 也就不会再触发。
上游后来恢复了额度，网关也发现不了——一条渠道会一直停着。

恢复靠一条冷却期，取 `settings` 的 `quota.exhausted_cooldown_seconds`（默认
900 秒）。读侧把 `last_probe_attempt_at` 也带进判据：即使余量为 0，距**上一次
尝试探测**已满一个冷却期时，这条渠道会回到候选集；被真正尝试到时，探测再问
一次上游。默认值取 900 秒（15 分钟），与连续失败那条冷却期是同一个数。每个
冷却期，一条见底渠道获得一次被尝试的机会；**真正恢复需要探测拿到数值**——
今天四个真实适配器都回 `ErrUnsupported`（见上面的 `probe_kind` 表），而一次
成功的调用走的是自记账，0 减去用量仍被钳成 0，不会清掉这个见底状态。

| 重探的结果 | 接下来 |
|---|---|
| 探到有额度 | 余量被覆盖，渠道恢复正常路由，不需要别的动作 |
| 仍是 0 | 这次尝试把 `last_probe_attempt_at` 推到当下，它再等一个冷却期 |
| 查不到 / 探测失败 | 同样更新 `last_probe_attempt_at`，也再等一个冷却期；余量原样保留 |

`last_probe_attempt_at` 为 NULL（从未探测过，例如自记账把余量扣到 0）时按
冷却期已过处理：不放行的话，这类渠道永远等不到第一次探测。冷却期为零或负数
时这条恢复路径是关着的，见底渠道照旧一律排除——装配层总是从 `settings` 读出
一个正值并接到路由上。

它**不是**后台轮询：放行之后仍然要有请求命中它，探测才会发生。放行也不等于
「一定被试」——它回到候选集时额度那一项是最低分，同一优先级下有别的渠道可
选时排在后面；只有它是最高优先级或唯一候选时才会立刻轮到它。

「观测过却没有数值」不在这条恢复路径里：它不是「用完了」，而是一次没有给出
数值的观测留下的状态，冷却期到了也不会让探测变得能拿到数值。

### 余量的单位

`channel_quota_state.unit` 说明 `remaining_estimate` 这个数是**什么单位**：

| 值 | 含义 |
|---|---|
| `tokens` | 按 token 计的套餐 |
| `requests` | 按次计的配额 |
| `money` | 按金额计，记账单位见 `internal/money` |

NULL 表示不知道按什么计。这个列是**比较的前提**：`route.scoreQuota` 只比较
同单位的余量，一批候选里出现两种以上已知单位时，这一项对所有候选给中性分。
不同量纲的数放进同一个 `1/(1+x)` 里没有意义——1000 个 token 与 1000 元谁更
该先用掉，取决于我们不知道的定价与消耗速度。

有一条判据与单位无关，任何情况下都照旧生效：**余量 ≤ 0 的渠道被排除**。
「没有了」不需要知道没有的是什么。余量见底之后的冷却期是这条判据唯一的
例外（见上一节）：那是「放它回来问一次」，不是「当作它还有额度」。

### 「余量未知」有两种，路由对它们的处置相反

`remaining_estimate` 允许为 NULL，而 NULL 有两种来历：

| 来历 | `quota.State.Routable` | 路由怎么处置 |
|---|---|---|
| 从来没观测过（多数订阅制上游不提供查询接口） | 真 | 照旧参与排序，额度那一项给中性分 |
| 观测过却没拿到数值（探针跑了没结果，或只从错误里看到信号） | 假 | 排除该渠道 |

两者靠 `last_probe_at` 与 `last_error_code` 区分——这两列与余量一起进
`route.Candidate.Quota`，少带一列，判据就退化成「有没有余量」，
而那是路由侧早先自己重写的那一遍。

判断只有一处实现：`internal/quota` 的 `State.Routable`、`State.Usable` 与
`State.ExhaustedRetryDue`（余量见底后的冷却期），由 `route.DrainReason` 调用。
路由不自己读余量再判一遍——同一个语义两处实现，迟早分叉，而分叉的表现是
「读侧说能用、写侧说不能用」这类查不出原因的行为。
`scoreQuota` 只管排序那一半：余量越少、越接近到期越该先用掉。

自记账只扣 `unit = tokens` 的渠道：上游给的用量本身就是 token 数，换算成按元
或按次计的量是**改错一个数**，而它看起来完全正常。这与读侧「跨单位不比」是
同一条规则的读写两面。

插件看到的候选集上也是同一条规则，落法见 [plugin-contract.md](plugin-contract.md)
的「额度余量」一节：判据与这里的打分共用一处实现。

观测进 `Merge` 之前过一遍 `quota.Validate`：余量是不是有限数、是不是负的、
观测时间有没有落在将来。校验失败就**拒绝这次写入并报错**，不静默丢弃——
观测被丢掉与观测写进去了在库上长得一样，而前者的后果是额度慢慢偏掉。

## 还没接的部分

- **从错误推断额度**（`error_observed`）：没有实现。一条 `health = 'drained'`
  的行会被读侧映射成余量 0（见 `internal/channels` 的 `quota`），所以它今天
  落在上面那条见底冷却期里——每过一个冷却期被放行一次，而不是永久排除。
  要不要把一次 402 直接写成 `drained` 仍没有答案：一次 402 也可能只是那一次
  请求的问题，这是这一档要一并设计的理由。
  **额度那一侧还有第二处同样的坑**：`Merge` 的 `KindErrorObserved` 分支在没有
  数值时会设 `LastErrorCode`，而它只在 `KindAPIQuery` 分支被清。成功的探测会
  走到后者（并清掉库里那两列），所以接上之后要有答案的是「一次 429 之后、
  下一次成功探测之前的这段时间里，渠道会不会被 `Routable` 永久排除」——今天
  这个分支还没有写入方。
- **延迟的分位数只在很小的样本上算**：`latency_p50_ms` 与 `latency_p95_ms`
  由写入方从 `usage_events` 按桶重算（见 `internal/channels` 的
  `rollupSignalsSQL`），`cache_*`、`cost` 与 `cost_events` 也是。渠道级读数
  来自 `model = ''` 的合并行（全模型样本），模型行只是同一批事件按模型再切
  一次。一个低流量渠道的一小时可能只有两三次调用，那时的 p95 是较大的那个
  观测值、p50 是排在中间的那个（样本为偶数个时取偏小的那个），都算不上统计
  意义上稳定的分位数——读它们的时候要知道这一点。

读侧把空值映射成「没有数据」（`route.Candidate` 上是一个 nil 指针），打分时
**那一维整个退出加权**，剩下的维度按各自权重归一。所以「没配成本规则」既不会
把候选打成最差，也不会稀释其余维度的差别——只是那一维不参与排序。有成本数据
的渠道则按 `route.DefaultWeights` 里那一项（成本 0.5）参与打分，不需要改读侧
或打分。

默认权重是五项——`Health 1.0` / `Quota 0.6` / `Cost 0.5` / `Latency 0.3` /
`Cache 0.2`。**健康度与额度始终参与打分，两项都比成本大**，所以只盯着那三项
去估排序会估错——它们三个的权重加起来恰好等于 1.0，看起来像一组完整的权重，
其实不是。
