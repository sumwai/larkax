# 插件契约

插件是挂到请求生命周期上的一段 JS，跑在 moejs 沙箱里。它能看到请求、候选渠道
与响应的**一部分**，而能改的比能看的更少。

**契约的权威定义是 `internal/plugin/contract.go`**：那里每个类型就是一个 hook 的
上下文或补丁，字段表即权限边界——没有出现在 Patch 里的东西插件改不了，也没有
第二处代码需要记得去过滤。这一份讲「怎么用」，以及几处光看字段名看不出来的语义。

> 现状：接进主服务的只有 `onRequest` 与 `onResponse` 两个 hook（跑在哪一步、
> 为什么是那一步，见「接线」一节）。`onRoute` / `onStream` / `onUsage` 的调用点
> 还没接——它们的契约已经定下来，但线上不会跑到。

## 五个 hook

| hook | 什么时候跑 | 返回值能做什么 |
|---|---|---|
| `onRequest` | 请求发出前 | 改请求体的白名单字段、加请求头 |
| `onRoute` | 选渠道时 | 在候选集里指定一个渠道 |
| `onStream` | 流式响应的每一块 | 丢掉或替换这一块、提前终止 |
| `onResponse` | 非流式响应拿到后 | 改正文与元数据 |
| `onUsage` | 上报用量时 | 报**数量**（token 数、次数），不能报金额 |

hook 返回 `undefined`（或什么都不返回）表示「这次不改」。

字段名要写准。**五个 hook 的返回值都是严格解析的**：出现契约之外的字段
（包括拼错的字段名）会报错，而不是被静默丢掉——静默丢掉的表现是「我改了但没
生效」，那是这类问题里最难查的一种。

报错按**插件失败**处置，与插件抛异常走同一条路：`meta` 里没声明 `blocking` 时
请求照常继续，只是这次补丁整个不生效，而失败记进这次会话的失败清单
（`Session.Failures()`）；声明了 `blocking` 时请求失败。

契约里是自由形状的那几项不受影响：`metadata` 与 `units` 的**键**由插件自己定，
严格解析管的是 `text` / `metadata`、`promptTokens` / `units` 这些名字本身。

（字段名的比较不区分大小写，`channelID` 与 `channelId` 都能解出来。那是宿主
JSON 解码器的行为，不是契约的一部分——把名字写准仍然是要做的事。）

一个请求只跑一个插件：匹配上的多个按优先级取一个，其余不参与。

插件从 `"larkax"` 这个虚拟模块导入 `definePlugin`、`log`、`calendar`、`kv`。
没有 `fetch`、没有 `fs`，也没有渠道凭证——宿主根本没把它们放进插件能碰到的地方。

## 两条方向性的规则

这两条光看字段名看不出来，而违反了都会让插件「看着生效了、其实没有」。

### `max_tokens` 只许调小

它是计费预留上界的输入：调大它，预留跟着涨，而插件上报的用量以那个预留封顶
——上界与上报值由同一方控制时，插件报多少就收多少。所以：

- 调小与持平：放行。「把输出压短」是策略插件的正当用法。
- 调大：拒绝。
- 原请求没给 `max_tokens` 而补丁给了一个：同样拒绝。上界从无到有仍然由插件
  决定，而「上界从哪来」正是这条规则要管的事。

被拒时按插件失败处置（`blocking` 未声明时请求照常继续，只是补丁整个不生效），
报错文本里带着原值与补丁值——**原请求没有给 `max_tokens` 那一档没有原值可带**，
读不出来那一档带的是读到的原始形态（例如 `string: 100`），不是「原值」。

### 上报的用量有一道上界

`completionTokens` 与 `reasoningTokens` 不得超过客户端请求里的 `max_tokens`
（**补丁之前**的那个，理由同上）。超了这次上报**整份丢掉**：按内核算出的用量
计费。丢掉的是整份而不是越界的那一项——半份上报是没法解释的状态。

这次丢掉要**能被看见**（否则它表现为「插件报了但没生效」）。出口是
`Session.Failures()`——它只读，而记录失败的那两个方法（`record` / `blocking`）
未导出，所以那两步必须放在包内（`ApplyRequest` / `ApplyResponse` 就是为此存在的），
或者在包上开一个导出的记录入口——见 `MergeUsage` 的注释。

计数为负是契约违规，在解析期就报错，报错文本点出是哪个字段、值是多少。
`0` 是合法的：上游返回了空回答，那是事实而不是缺值。

## 接线：两个挂载点跑在哪里

一次请求里的顺序（`internal/api` 的 `serveOnce` → `internal/gateway` 的 `Chat`）：

```
鉴权 → 限流 → 额度早拒绝 → 解析请求体
     → onRequest        ← 补丁就地写回统一请求
     → 组装计费请求 → 预留（冻钱）→ 选渠道 → 调上游 → 记调用结局
     → onResponse       ← 补丁就地写回响应
     → 结算（写账）→ 渲染响应 → 发给调用方
```

### `onRequest` 为什么在组装计费请求之前

补丁能改 `max_tokens`，而它是**预留上界**的输入（见「`max_tokens` 只许调小」）。
排在组装计费请求之后的话，那份计费请求里留着的仍是补丁前的值，于是
「插件把 `max_tokens` 调小」不影响预留——请求照样成功、响应照样正确、日志里
插件照样跑了，只有冻住的那笔钱是错的。所以这一条由用例钉住，而且断言的是
**金额**（插件把 `max_tokens` 从 1000 调到 10 之后，预留上界跟着降到十分之一），
不是「插件被调过」：后者测的是调用发生，不是效果。

它同时排在**预留之前**，所以阻断型插件在 `onRequest` 上失败时，钱一分没冻、
幂等记录也还没建（那条记录与预留同一个事务）——调用方直接重试是安全的。

### 幂等指纹**不含**插件补丁

指纹是 `HashRequest(protocol, upstream)`，算在插件跑之前，算的是**调用方发来的
那份请求**。补丁不进指纹，后果是双向的：

- **不进（现在的做法）**：同一个键、同一份请求体，即使插件这次给出不同的补丁
  （插件被热更新过、或它的判断依赖时间与 KV），第二次也是**重放第一次的响应**，
  不会重新执行。代价要说清楚：重放出来的那份响应，与「用今天的插件重新跑一遍」
  可能不一样。
- **进**：指纹只能在插件跑完之后才算得出来，于是「查有没有现成的记录」这一步
  必须挪到插件之后——而插件是能写 KV、能读日历的，那意味着一次本该被重放挡下的
  请求会先产生副作用。更糟的是，插件只要有一点不确定性（时间、随机、KV），
  同一个请求的两次调用就会得到两个指纹，于是**每一次重试都被当成新请求重新执行
  并重新计费**——那正是幂等键要防的事。

判据因此是：指纹回答的是「调用方发的是不是同一个请求」，而补丁是宿主与插件
对那份请求的**处理结果**。处理结果变了不该让同一个请求变成另一个请求。
这也意味着**重放的那一次不跑插件**：`resolveExisting` 命中时直接发回记录里的
响应，`serveOnce`（连同插件）一次都不进。

### 撞键重试会**再跑一次** `onRequest`，但用的是没被改过的请求

`serveIdempotent` 的循环在「键被并发请求抢走」时会重进一次 `serveOnce`，
插件于是再跑一遍。这一遍拿到的必须是**重新解析出来的一份请求**，而不是上一轮
那份已经被补丁就地改过的——变换式的补丁（「把 `max_tokens` 减 1」）在前者上是
减 1，在后者上是减 2。

那一轮没有任何副作用：预留整个回滚了、上游一次没调、幂等记录随事务一起没了。
所以「插件跑了两次」只体现在它自己的日志与 KV 上，不影响计费与响应。

### `onResponse` 的元数据不进协议层

`ResponsePatch.Metadata` 在 `channel.Response` 上**没有对应字段，也不该有**：
那个类型是协议转换与渲染的输入，往里加一个插件专用的 map 会让它跟着响应一路
走到调用方，而契约里它只是插件留给自己的一段附注。所以它的落点是**宿主的日志与
快照**，由调用方决定（今天接上的是日志那一半，带 `plugin` 与 `request_id` 两个
字段；快照那一半还没接）。它也**不会**出现在发给调用方的响应体里。

正文（`text`）不同：它是给调用方看的，所以就地替换进响应。插件给的是一整段
拼接后的文本，写回来时也是整段替换——原有的文本块合成一个，位置取第一块文本的
位置，非文本块（`tool_use` 等）原样留在原位；一个文本块都没有时追加一块。
`usage` 与 `finishReason` 不在这份补丁里，插件碰不到。

### 流式请求永远拿不到 `onResponse`

流式响应是边生成边发的，没有「整份响应」这个时刻——网关那条路上
`Result.Response` 恒为 `nil`，`onResponse` 也就没有可交付的对象。所以流式请求
只跑 `onRequest`（那一步在流式与非流式之前，两条路都经过它）。给流式用的挂载点
是 `onStream`（逐块决定），它还没接。

这也是网关的 `ChatStream` **没有** hooks 参数的原因：先占一个收下不用的参数，
会让「流式也有插件钩子」看起来已经成立。

### 非阻断的失败只有日志一个出口

非阻断的失败不改变请求的结果，所以它**只能靠日志被看见**：一个每次都超时但
「不影响请求」的插件，从响应上完全看不出来。入口在请求结束时把
`Session.Failures()` 逐条记成告警（带 `plugin` / `hook` / `request_id`）；
插件加的请求头被拒时另有一条，因为那种错法的表现是「上游不支持这个头」。

阻断型的失败另有出口（请求以错误结束），但一起记在日志里——它同样是这次请求
的现场。

## 插件长什么样

```js
import { definePlugin, log } from "larkax";

export const meta = {
  key: "acme-vision",
  name: "视觉模型选路",
  apiVersion: 1,
  models: ["acme/vision"],   // 空表示所有模型
  capabilities: ["log"],     // 申请的能力，只能是宿主开放范围的子集
};

export default definePlugin({
  onRoute(ctx) {
    log("info", "候选", { n: ctx.candidates.length });
    // 不决策：交给内核按健康度与优先级排序
    return undefined;
  },
});
```

## `onRoute` 的候选集

`ctx.candidates` 是这次请求可以走的渠道，每个候选的字段：

| 字段 | 含义 |
|---|---|
| `channelId` | 渠道 ID。决策里的 `channelId` **必须在候选集之内** |
| `ownerUserId` | 渠道归属的用户 |
| `weight` / `priority` | 商家配的权重与优先级 |
| `health` | 四档：`healthy` / `degraded` / `drained` / `unknown` |
| `remainingEstimate` | 剩余额度，**只在本次候选集内可比时才给**，见下一节 |
| `confidence` | 上面那个数的可信度，`0..1`；它与 `remainingEstimate` 同生共死 |
| `upstreamCostHint` | 最近观察到的单位成本；缺省表示未知 |
| `resetsAt` | 额度重置时间，RFC3339；缺省表示没有 |

候选里**没有** `base_url`，也没有凭证：`base_url` 足以让插件推断出上游是谁。

`health` 是已经判过的结论而不是原始计数。`unknown` 表示「没有样本」，
与 `healthy` 不是一回事——按后者处理会把一个从没跑过的渠道排到最前面。

## 额度余量：什么时候是 null

`remainingEstimate` 是 `null` 的两种情况：

1. **这个渠道查不到额度。** 它与「额度为零」不同，后者给的是 `0`。
2. **候选集里出现了两种以上额度单位。** 单位可以是按 token 计、按次计、按金额计
   （见 [channel-health.md](channel-health.md) 的「单位」一节）。按 token 计的套餐
   与按元计的账户之间，「还剩 100」谁更该先用掉取决于我们不知道的定价与消耗速度，
   比出来的次序完全由单位决定。此时**所有**候选一律为 `null`，包括单位相同的
   那几个：只给一部分会让「有的有数、有的没数」看起来像那几家查额度失败了。

字段的含义因此是**「本次候选集内，这个数可以与其他候选的 `remainingEstimate`
直接比较」**，而不只是「还剩多少」。

判断「可不可比」是**集合级**的，构造候选集的一方已经做完了（判据与内核打分
共用一处实现，见 `route.MixedQuotaUnits`）。插件不需要自己判断，只需要在
`null` 时把它当作「这里没有可用的信息」。

### 正例

```js
import { definePlugin } from "larkax";

export default definePlugin({
  onRoute(ctx) {
    // null = 「没有可用的信息」。先挑出有数的那些，一个都没有就不决策。
    const 可比的 = ctx.candidates.filter((c) => c.remainingEstimate !== null);
    if (可比的.length === 0) {
      return undefined; // 交给内核排序
    }
    const 选 = 可比的.reduce((a, b) =>
      b.remainingEstimate < a.remainingEstimate ? b : a);
    return { channelId: 选.channelId, reason: "剩余额度最少" };
  },
});
```

### 反例

```js
// 不要这样写：跨候选直接比
export default definePlugin({
  onRoute(ctx) {
    const 排好的 = [...ctx.candidates].sort(
      (a, b) => b.remainingEstimate - a.remainingEstimate);
    return { channelId: 排好的[0].channelId, reason: "剩余最多" };
  },
});
```

**它不会报错，只会静默地给出一个没有依据的决策。** 两种情况：

- 单位混合时全是 `null`，`b - a` 恒为 `0`，排序一动不动——插件却照样返回一个
  `reason`，报告一件它没有做过的事。
- 部分候选查不到额度时是 `null`，而 JS 里 `null` 参与算术会变成 `0`：那些渠道
  被当成「余量为零」，排到最前或最后，取决于相减的方向。

## 限额与宿主能力的失败

插件跑在限额之内：一次 hook 调用与**请求期的顶层求值**共用同一个上限
（默认 5 秒，见 `internal/plugin/sandbox` 的 `DefaultLimits`）。超了就失败，
插件拿不到结果。

宿主能力失败时，插件 `catch` 到的 `e.message` 是「**分类码: 固定文案**」，
例如 `unavailable: 读取插件 KV 失败`、`host_timeout: 宿主能力超时`。
**原文不会跨过来**——它可能带连接串、驱动细节或上游地址，只进宿主日志。
所以按码分支，不要按文案分支：

| 码 | 含义 |
|---|---|
| `bad_argument` | 你给的参数不合法 |
| `unavailable` | 宿主依赖不可用（存储、日历数据源等） |
| `host_timeout` | 这次调用的预算已经用尽 |
| `canceled` | 请求已经结束 |
| `misconfigured` | 集成方把能力表配错了（某个成员不是函数） |
| `capability_failed` | 宿主没给这个错误分类（默认拒绝），原文只在宿主日志里 |

`bad_argument` 与 `misconfigured` 的文案里会带上出问题的参数名或能力名，
那是插件本来就拿得到的东西；其余文案是固定的，别依赖它的措辞。

### 顶层代码

模块顶层会被求值**两次**，两次都是插件代码，两次都在限额之内：

1. **编译期**（上传/注册时）：读出 `meta` 与这个插件导出了哪几个 hook。
   这一次**没有注入任何宿主能力**，顶层调 `log(...)` 只会拿到
   `宿主能力未注入：这个插件运行在没有宿主能力的环境里`。
2. **请求期**（每次请求建 runtime 时）：这一次**能力已经注入**，所以顶层
   **可以**调宿主能力——它受的是限额的约束，不是「拿不到能力」。

顶层只该声明常量。一个死循环、一次慢的宿主调用，或者几十兆的分配，会让
**整个请求没有插件**（顶层跑不完就没有 runtime），而不是「这个 hook 失败」；
重活放进 hook 里。

## 怎么改

- **加字段就是扩大插件的可见范围**，要当成一次契约变更来做，而不是顺手加一个。
  上下文类型是独立的快照类型而不是内核类型的别名，正是为了让这件事必须显式发生。
- **补丁类型的字段表就是权限边界**。往 Patch 里加字段前先问：这个改动会不会改价、
  改身份、改「这次回答是否完整」的判定？会的话它不该出现在这里。
- 契约版本在 `meta.apiVersion`。改动语义（而不只是加字段）时它要跟着动。
- **接一个新 hook 的调用点时，先定它的位置，再用一个断言效果的用例把位置钉住。**
  断言「插件被调过」是不够的：调用发生了、而补丁落在了错误的一步上，从响应上
  完全看不出来（`onRequest` 与预留的关系就是这样一条）。判据是「改一处位置，
  用例会红」——见 `internal/api/plugin_test.go` 与 `internal/gateway/hooks_test.go`。
