# 分时计价的日历数据

分时计价要回答两个问题：**某一天是不是工作日**，以及**某个时刻算不算高峰**。
前者不能靠星期推——调休把周末挪成了上班日，法定节假日又落在周一到周五。
所以它需要一份外部数据，落在两张表里：

| 表 | 存什么 |
|---|---|
| `calendar_days` | 某地区某一天：是否放假、是不是调休补班日、节假日名称 |
| `calendar_years` | 某地区某一年的同步状态：已同步 / 公告未发布 / 双源不一致 / 同步失败 |

```sh
go run ./cmd/larkaxctl price calendar import <文件>
```

**数据从哪来不在本命令的范围内。** 它只负责「读文件 → 写库」，文件由公开的
节假日数据源转换而来，或者由运维手工维护。仓库里不带任何真实数据集。

服务启动时把这两张表接到计价环境上（`internal/assembly`），规则里的
`isWorkday()`、`isHoliday()` 查的就是它。接线本身**不读数据、也不做校验**：
库里是空的照常启动，见下文「没有数据的那一年会怎样」。

## 峰谷那一半：规则里写得出，插件里还写不出

上面那句「某个时刻算不算高峰」今天有两条路，一条通、一条不通。

**规则里通。** 高峰时段由规则自己声明，写成 `isPeak("08:00-22:00")`——与
`hour(tz)` 的时区同一类：峰谷是定价口径，不由地区推断，同一地区的两个渠道
可以有各自的峰谷。窗口串与地区、时刻一起交给 `internal/calendar/peak.go` 的
`PeakAt` 判定（经 `internal/billing/calendaradapter`）。多段用逗号分开，段内
允许跨零点：

```
isPeak("08:00-12:00,14:00-18:00") ? {"prompt": 2.0} : {"prompt": 1.0}
(!isWorkday() || isPeak("08:00-12:00")) ? {"prompt": 2.0} : {"prompt": 1.0}
```

第二行的写法是「休息日整天算高峰」：接口上没有那个开关，用两条判定组合出来。

窗口的**写法**在保存规则时就解析一遍，`"25:00-26:00"`、`"8:5-9:00"` 这类当场报错；
而「全天段不能与其他段并列」属于排班语义，由日历在求值时判——那时报的是
`ErrCalendarRequired`，与「这一天的日历还没有数据」同一类，处置方式也一样
（改规则，或者等数据补齐）。

**插件里不通。** 宿主日历接口里有 `Peak`，而插件 SDK 的 calendar 命名空间里
没有对应的函数可调，所以插件写不出峰谷价。要接上它得先定「插件的窗口从哪来」
——规则那一半的答案（窗口随规则走）用不到插件上，那是一条独立的决定，见
`internal/assembly` 的 `pluginPeakSchedule`。

**这件事工具不会提醒。** `PeakAt` 挂在 `*Calendar` 这个类型上，而把
`*Calendar` 接进 assembly 之后，这个类型进了可达图，`deadcode` 就把它的方法
都算成可达，于是 `peak.go` 里那几条**从不可达清单里掉了出去**。清单里没有它，
读起来像「已经在用了」——见 [LESSONS.md](../LESSONS.md) 第 22 条。

插件那一侧的提醒同样不在工具里。`pluginCalendar.Peak` 曾经挂在
`scripts/deadmethods-allowlist.txt` 上，而规则侧接上 `isPeak()` 之后，`expr` 里
出现了一个同名的 `Peak` 调用点；那道门按方法名数调用点，于是那一条被掩护掉、
当作陈旧条目删掉了（与 `catalog.Admin.Update` 同一处境）。所以「插件写不出峰谷价」
这句话今天由代码注释承担：`internal/assembly` 的 `pluginCalendar.Peak` 与
`pluginPeakSchedule`、`internal/calendar` 的包注释，以及本节。

## 文件格式

一个 JSON 对象。**只认下面这些字段，键名写错会直接报错**——JSON 解码默认
静默忽略不认识的键，而 `offDay` 被丢掉之后那一天会按工作日算，文件看上去
完全正常。

```json
{
  "region": "CN",
  "year": 2031,
  "status": "synced",
  "source": "manual",
  "source_paper_urls": ["https://example.com/notice"],
  "sources_agree": true,
  "last_error": "",
  "days": [
    {"date": "2031-01-01", "name": "元旦", "off_day": true},
    {"date": "2031-01-02", "off_day": false},
    {"date": "2031-01-04", "off_day": false, "makeup_workday": true}
  ]
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `region` | 是 | 地区代码，目前只有 `CN` |
| `year` | 是 | 这份数据所属的年份 |
| `status` | 是 | `synced` / `pending` / `conflict` / `degraded`，见下表 |
| `source` | `synced` 时必填，其余三种状态**必须不写** | 数据的出处（`holiday-cn`、`manual` 之类），落进 `calendar_days.source` |
| `days` | `synced` 时必填 | 该年每一天的判定 |
| `source_paper_urls` | 否 | 公告原文地址，落进同名列 |
| `sources_agree` | 否 | 双源交叉校验结果。不写即「只有一个源、没得比」，与「两个源对不上」是两回事 |
| `last_error` | 否 | 同步失败的原因，`degraded` 时有意义 |

`days` 里每一天：

| 字段 | 必填 | 说明 |
|---|---|---|
| `date` | 是 | `YYYY-MM-DD`。写成 `2031-1-5` 会被拒绝，不会被规范化 |
| `off_day` | 是 | 这一天是否放假。**漏写与写 `false` 在 JSON 里长得一样**，而漏写会让那一天按工作日算，所以这里要求显式写出来 |
| `name` | 否 | 节假日名称（「春节」「国庆节」），普通日子留空 |
| `makeup_workday` | 否 | 调休补班日。默认 `false`；与 `off_day: true` 同时出现会被拒绝 |

### `status` 的四个取值

| 取值 | 含义 | 带 `days` 吗 |
|---|---|---|
| `synced` | 已同步且双源一致 | **是**，且必须覆盖本年的每一天 |
| `pending` | 该年放假安排尚未公布。对未来年份这是**正常状态** | 否 |
| `conflict` | 两个数据源不一致，待人工裁决 | 否 |
| `degraded` | 安排已公布但同步失败，这才是需要告警的状态 | 否 |

后三种状态**不能带 `days`，也不能带 `source`**。原因是判定优先级：某一天只要
有数据行就以行为准，年份状态只在行缺失时才被问到。给一个还没定论的年份写进
部分数据行，等于把「这一年还没定下来」静默换成「这几天就这么算」；而 `source`
只用于数据行，那三种状态本来就不写数据行，带上它只是多一个不会被读到的值。
两条都直接拒绝，而不是默默忽略——写错的键值被忽略时，文件看上去完全正常。

`synced` 的年份必须覆盖本年的每一天：少一天的年份不能标成 synced。那一天会被
判定成未知，用到日历的计价规则会一直失败——这比标错状态更难查。

### 覆盖范围与跨年边界

`synced` 的文件要覆盖本年 365（或 366）天，**可以额外带上相邻年份的日子**：
元旦的安排可能把去年 12 月 31 日挪成休息，而那条记录出自后一年的数据集。
隔了两年以上的日期会被拒绝——那一定是笔误，而判定按行优先，它会变成一条
谁都没打算写的行。

## 落库的语义

**同一年再灌一次是覆盖，不是追加。** 导入先在一个事务里清掉这一年上一次导入
写下的行，再写新的。所以「文件少了一天」不会被留在库里继续参与判定。

**同一天以最后一次导入为准。** `calendar_days` 的主键是 `(region, day)`，
一条只能有一个来源；相邻两年的文件都提到某一天时，后导入的那份赢。

命令每次都打印一行结果，包括覆盖掉了多少行：

```
已导入 CN 2031 年：状态=synced，本年 365 天，年外 1 天，替换原有 365 行
```

非 `synced` 的状态不带数据行，输出里会另起一句说明，好让「0 天」看起来是
预期结果而不是数据被吞了。

## 没有数据的那一年会怎样

**用到日历的规则会失败，而且失败信息说明这是配置缺口。** 判定是未知时不会
回落到「按工作日算」——那会在春节期间按高峰价收费，而账单看上去完全正常。

两条边界：

- **没有规则用到日历时，日历缺数据完全无害。** 判断只在规则真的调用
  `isWorkday()`、`isHoliday()`、`isPeak()` 这些函数时才发生。
- **启动时不检查。** 缺数据不会让服务拒绝启动——日历数据是逐年补的，未来年份
  查不到是正常状态。

成因一共六个（`internal/calendar` 的 `UnknownReason`）：`year_pending`（公告未
发布）、`year_degraded`（公告已公布但同步失败）、`year_conflict`（两个数据源不
一致）、`year_unknown`（库里没有这一年的记录）、`row_missing`（年份标着已同步，
这一天却没有记录）、`row_inconsistent`（记录自相矛盾，例如既放假又标成补班日）。
**六个都会出现在调用方看到的错误信息里**，撞上一个不认识的成因码时来这里对。

分界线是「要不要有人去看一眼」：`year_pending` 是**正常状态**，调用方按保守策略
继续即可；其余五个都要人去查同步任务与公告的状态，其中 `row_missing` 与
`row_inconsistent` 是数据本身不完整或矛盾——猜任何一边都可能让一整天的价格算错，
所以判成未知而不是按工作日放行。

## 怎么查现在有什么

数据落在 `calendar_days` / `calendar_years` 两张表里，直接查库即可：

```sql
SELECT year, status, day_count, synced_at FROM calendar_years ORDER BY year;

SELECT day, holiday_name, is_off_day, is_makeup_workday
  FROM calendar_days
 WHERE region = 'CN' AND day BETWEEN '2031-01-01' AND '2031-01-31'
 ORDER BY day;
```

`calendar_years.day_count` 是文件里**落在本年之内**的天数。它与 365（或 366）
相等即表示这一年是完整的。
