# larkaxctl 命令参考

`larkaxctl` 是 larkax 的运维命令行。根帮助页（`larkaxctl --help`）只列一级命令与当下
要用的那几行；本文件写全局约定、退出码边界与各命令的完整说明。

每条命令有两版帮助：`larkaxctl <命令> --help`（也认 `-h`）给一屏摘要，
`larkaxctl help <命令>` 与 `larkaxctl <命令> help` 给展开的那一份。

这份参考同时有 man 版：首页列出各命令页，各命令页指回首页，而命令页之间不互相引用。
它们由命令注册表与本文件生成（见 [development.md](development.md) 的「每道门在挡什么」），
不手工改。发布的 tar.gz 里带着这几页（见 [versioning.md](versioning.md)）：解开那个包，
把 `MANPATH` 指到解出来那个目录下的 `man/`，命令与下面这条同形。源码树里是这样翻的
（`man` 只认 `MANPATH` 下的 `man1/` 这类子目录，所以指到 `man/` 那一层）：

- `MANPATH="$PWD/man" man larkaxctl-channel`

## 全局约定

这几条对所有命令生效，写在子命令的前面或后面都认。

### 环境变量

运维命令只读下面这几个环境变量：

| 环境变量 | 用途 |
|---|---|
| `LARKAX_DB_DSN` | 数据库连接串 |
| `LARKAX_ENV` | 环境名 |
| `LARKAX_LOG_LEVEL` | 日志级别 |
| `LARKAX_MASTER_KEYS` | 主密钥。只有这几组命令读它：`channel create` / `update`（写凭证）、`secret rotate`、`plugin delete` / `kv set` / `kv delete`（删插件、或动它的私有存储） |

`LARKAX_ROLE` 与运维命令无关。命令行自身的配置加载见 `internal/config` 的 `LoadOps`。

### `.env` 与 `--env-file`

`.env` 文件的取值规则：

- 不给 `--env-file` 时，从当前目录往上找，**不越过 git 仓库根**，用最近的那一份。
- `--env-file <路径>` 指定另一份文件。
- 两种来源都**只填补尚未设置的环境变量**：已经在环境里导出的变量优先，`.env`
  补不上它。所以一份注入的生产环境不会被误带的开发 `.env` 覆盖。

只用 `.env`、不在环境里导出任何变量也可以。

### 退出码

| 码 | 含义 |
|---|---|
| `0` | 成功 |
| `1` | 其他失败 |
| `2` | 命令行参数错（缺字段、取值解析不了、取值的形状不合要求、标志组合不对、读过那一行才知道不对的组合） |
| `3` | 连不上数据库 |
| `4` | 约束冲突（唯一键、外键、要改或要查的那一行不存在；同一幂等键已经对应另一笔入账） |

**`1` 与 `2` 的分界不在「谁校验出来的」。** 两档里都有由包判出来的错，也都有由
命令行自己判出来的错；一个错落哪一档，由**命令自己**定——它在报出去之前把这个错算进
「参数错」的归 `2`（代码里就是包一层 `usageErr`），没算进去的落回 `1`。所以下面这几条
是**按命令列出来的清单，不要拿其中一条去推另一条**；要确认某条命令的某一档，看它
实际给哪个码。

- **`user` 的 `--name` 与 `--email` 形状不合法给 `2`**：前者是整串为一个十进制整数
  （只在 `create` 上），后者是写不成一个邮箱地址（`create` 与 `update` 都有，见下面
  「user」一节）。这类错在**命令本身**——换一个值重发就能过，与库里有什么无关。
- **`settings set` 的键名或取值不认识给 `1`，不是 `2`**。它和上一条是同一个形状
  （都由包在连库之前判出来，也都不依赖库里有什么），差别只在命令把它算进了哪一档。
  对照 `wallet --amount`、`apikey --quota` 这类把取值直接写在数值标志上的命令：
  解析不了给 `2`。
- **写在已软删的渠道上给 `1`，不是 `4`**。`channel update` / `channel enable` /
  `channel disable` 打到一个软删的 id 上，报的是「这条渠道已删」，归写入路径那一档；
  同一个 id 根本没建过才是「要改的那一行不存在」，给 `4`。软删的渠道列不进 `channel list`、
  也改不动，这两处有意分成两档。
- **写入路径上由包判出来的参数问题给 `1`**：作用域与归属的组合、表达式编译不过、
  渠道类型不认识。这三处由各包在写的那一刻判，报错原样上来，没有标成参数错那一档。

`2` 里还有一类：**命令行要读过库里的那一行才判得出**的参数组合，今天只有一处
（`user update --no-merchant` 打在 `admin` 上，见下面「user」一节）。它与上面那几条的
分别在于错在**命令本身**而不是数据里：改一下命令重发就能过，与解析阶段那几类是同一个
补救动作；而写入路径那一类错在数据，改命令没用，得先去看库里现在是什么。

上面这几个数是命令行的对外契约。按**触发条件**分的完整一张表（多出「体检结论」
那一档 D，它不打第二行、退出码照旧非零）见 [cli-output.md](cli-output.md) 的
「退出码」一节。

### 短选项

短选项固定为下面六个，其余选项一律写全名：

| 简写 | 全名 |
|---|---|
| `-u` | `--user` |
| `-m` | `--model` |
| `-o` | `--format` |
| `-v` | `--verbose` |
| `-q` | `--quiet` |
| `-V` | `--version` |

**`-V` 打版本号，`-v` 是详细模式。** 另外两条成对出现的约定：`-o` 与 `--format`
一样，写在子命令前后都认；`--verbose` 与 `--quiet` 不能同时给，两个一起给是参数错。

安全、财务与边界类的选项**不开短选项**，必须写全名：上游渠道、凭证来源、外部单据号、
速率上限、生效截止这几类。它们写短了容易看错也容易按错。

### 机器可读输出

`--format json` 把 stdout 收成一份 JSON，提示与警告走 stderr，给管道下游的 `jq`
与探针用。取值不合法时报参数错，不静默回落成表格。完整契约——状态符、上色条件、
表格对齐、时刻与时区——见 [cli-output.md](cli-output.md)。

## 按命令

每条一级命令的二级动作与参数在它自己的帮助里。帮助分两版：

- `larkaxctl <命令> --help`（也认 `-h`）打**短版**：有哪些动作、参数怎么给，
  外加一两条最关键的边界，一屏之内。
- `larkaxctl help <命令>` 与 `larkaxctl <命令> help` 打**长版**：短版之外再把
  其余边界说完。

**设计说明不在这两版里**，它在下面各节：某个字段为什么必填、这一步为什么
不可逆、别家工具怎么做，这些对跑命令的人当下没用，而写在帮助里的话每次敲错
参数都要被念一遍。

下面按根帮助页的分组逐条列出。

### 核心与诊断 (Core & Diagnostics)

#### `doctor`

系统健康与链路连通性体检。默认只读检查六项、不碰网络，`--verbose` 时每项多打
一段检查范围与完整原文，`--format json` 打一份完整的机器可读报告（它的细节本来
就在里面，所以不走 `-v`，问题清单也不截断）。

第 3、4、5 项回答的是同一个字符串在两个数组里对不上的问题：渠道的 `--models`
与目录里的规范名差一个字符，或者模型建了却没加进任何渠道的白名单——那时调用
回 503「no available upstream for the requested model」，而那句话不会说是哪
一个名字不对。第 3 项还多判一层：名字在目录里、但它声明的端点与这条渠道打的
那条对不上（目录里可以声明一个模型只在某几条端点上被服务，而渠道的 `type` 决定
它打哪条）——那时请求会打到一条服务不了的端点上，上游回 400
`unsupported_model`，从我们这边看与「模型不存在」无从分辨。第 6 项把「用户没有
钱包行」这类缺口在第一次调用之前指出来，而不是让人从 500 往回推。

「没跑成」与「通过」是两件事：没有可检查的对象时那一项报「没跑成」而不是
「通过」，退出码也非 0。两者在安静的终端里长得一样，是这个项目反复踩的坑
（见 [LESSONS.md](../LESSONS.md) 第 16 条）。

`--live` 要花钱、要凭证，默认不跑。**凭证不能写在命令行参数里**：参数会出现在
`ps` 的输出与 shell 历史里，凭证到了那里就等于交给了同机的其他进程和任何一个
能翻历史的人。所以只能从标准输入或环境变量读，与 `channel create` 同一个做法。
这里读的是打网关用的 **API Key**（`apikey create` 发的那把），不是渠道凭证。

`--endpoint` 选打哪个入口：`chat` 是 `POST /v1/chat/completions`
（`Authorization: Bearer`），`messages` 是 `POST /v1/messages`（`x-api-key`），
`responses` 是 `POST /v1/responses`（`Authorization: Bearer`）。`--base-url`
不给时按本次配置里的 `LARKAX_HTTP_ADDR`（含 `.env` 里的那一份）拼出网关地址，
与主服务听在哪儿是同一个来源：那个变量写着 `127.0.0.1:8081` 就打成
`http://127.0.0.1:8081`；写成 `:8080` 这类不写主机的「所有网卡」时按
`127.0.0.1` 打。网关不在本机、或者要打的是另一台，就显式给。

#### `settings`

运行期动态配置项管理（`settings` 表）。配置项存在库里而不是环境变量里，是为了
与数据同生共死：备份恢复、换机器时它跟着数据一起走，不会像环境变量那样漏掉一个
就整体不可用。

键与类型定义在 `internal/settings` 的 `Registry` 里，每个键的说明存在库中
`settings.description` 那一列（由迁移写入，`list` 打的就是它）。**未声明的键写不
进去**——库里出现一个代码不认识的键，表现是配置被静默忽略，而写它的人当场看不到
任何反馈。

`--by` 必填。`settings.updated_by` 记的是谁改的配置，而一条不记名的写入等于没有
审计——允许留空的话，最省事的用法就是永远不填。

有些键不接受这条路径的修改（`settings.editable` 为 false）：它们改错会造成严重
后果，只允许由迁移写入。命令会报错并指出是哪一个。另有一些键**写得进去、但改了
不会有任何效果**：代码里还没有读它们的路径（`Registry` 里标了 `Unwired` 的那
几个）。命令照常写入，并在输出里指出这一点——不指出来的话，它与一个真的生效的键
在这条命令的输出上完全一样。

密钥类配置不放这里（明文落盘并进备份），它们走 `channels` 表的信封加密。这条由
上面的白名单保证：写入只认 `Registry` 里声明过的键。

`get` 看一个配置项：值打的是 `settings.value` 的 jsonb 原文（字符串带引号，布尔
与整数不带），类型与「接没接线」取自 `Registry`。库里没有这一行时按「要查的那一行
不存在」返回 4，并区分两种缺法：`Registry` 里声明过却缺了行，多半是写它的迁移
没跑到；`Registry` 里也没有，多半是键名写错。
`-o json` 下 `setting` 条目与 `list` 里那一条逐字段相同。

#### `version`

打印版本号与编译元数据。版本号在构建时注入（见 `Makefile`），从源码直接编译出来
的是 `dev`。

### 路由与模型配置 (Routing & Models)

#### `channel`

上游渠道管理（网关、凭证、关联模型）。**碰凭证的那些写入**（`create` / `update`）
需要主密钥：凭证明文要信封加密，密钥材料只在写入侧用得上。`enable` / `disable` /
`delete` / `restore` 与读侧的 `list` / `get` / `health` 都不要主密钥——它们一处都
不读凭证密文。

**明文凭证只能从标准输入或环境变量读，不能写在命令行参数里。**命令行参数会出现
在 `ps` 的输出与 shell 历史里，凭证到了那里就等于交给了同机的其他进程和任何一个
能翻历史的人。

`create` 的 stdout 只有新渠道的 ID，其余信息走 stderr。`list` **不打印凭证密
文**，只打印它挂在哪些主密钥下（那不需要任何密钥材料）；默认不列已删的渠道，
`--all` 才列，并在「已删」那一栏标出删除时刻。

`get --id` 读一条渠道的明细：状态、关联模型、凭证挂在哪些主密钥下。
与 `list` 不同，**它读得到已删的渠道**——`list` 挑的是「现在能用哪些」，
按 ID 问一条记录时答「没有这一条」，会把「已经删了」与「ID 写错了」
混成同一句。

`health` 汇总每条渠道窗口内的调用读数与当前健康结论。汇总表给出状态、
最近一次探测时刻、请求数、失败数、失败率、缓存命中与未命中（以 token 计）、
延迟分位（p50 / p95）与成本；**成功数只在 `--id` 的详情里打**，汇总表没有
这一栏。窗口默认最近 24 小时，`--since` 收一个时长（`6h`、`90m`），或者
一个 RFC3339 时刻（`2026-10-18T00:00:00Z`）。未来时刻会被拒。默认不列
已删的渠道，`--all` 才列。

窗口只用来筛数据，不是每一项都按它算：请求数、缓存 token 与成本是窗口内
各小时的**和**（未命中算的是 prompt 加缓存写入），延迟分位每一列各取
**自己**最近一个有值的小时（p50 与 p95 因此可能来自不同的小时）——
分位数不能相加。缓存 token 那一档与选路读的是同两列，0 表示窗口内没有
样本。窗口内没有任何读数时，这几个数是 0 或 `-`，而健康结论仍然是库里
那一格。

成本那一列今天还没有写入方，恒显示 `-`；它说的是「没人记过账」，不是
「免费」。

渠道健康表（`channel_quota_state`）里没有这一条记录时，`health` 打 `unknown`：
「还没探测过」与「探过、是好的」不是同一件事。

`health --id` 额外列出窗口内逐小时的明细（请求数、成功数、失败数、
缓存 token、分位与成本）。这条渠道在窗口内一次都没被调用过时，逐小时那
一段说的是「窗口内没有逐小时的数据」，与清单为空时的「暂无渠道」不是
一句话。

`delete` 是**软删**：置 `deleted_at` 并把状态改成 `disabled`，行与它的凭证密文都
留在库里。历史账单（`billing_requests` / `usage_events`）仍然按 `channel_id` 引用
它，所以删除之后那些记录照样认得这条渠道。已删的渠道不能再 `update` /
`enable` / `disable`，再删一次不报错（打印「已经是删除状态」）。

`restore --id` 把软删的渠道改回可用：`deleted_at` 清空，状态回到 `enabled`。
恢复之后它的健康结论回落成 `unknown`——软删之前那一次结论说的是当时的渠道，
恢复不等于它现在就可用；要一条结论得重新探测。没有处于删除状态的渠道上敲
`restore` 不报错，只打一句「没有处于删除状态」。

渠道类型必须是已注册的适配器类型；类型写错时错误信息会列出已知的类型。
`--models` 至少要有一个：读取路径把 `models` 当白名单用，空数组的渠道永远选不
中。每个模型还要能被这条渠道服务——两者对不上时 `create` / `update` 会被拒绝，
并说出「模型在目录里声明的端点」与「这条渠道打的端点」各是什么：配错时现场是
上游回 400，而那句话看不出是我们这边配的。目录里没有这个模型、或者那一项没配过
时不拦：目录是人工维护、会过时的一份声明，按「不支持」处理会让新接的上游一条
渠道都建不出来。

`--base-url` 只写到路径为止：带 query（`?`）或 fragment（`#`）的地址会被拒，
错误里点出是哪一段不合法。端点是拿地址与端点路径**拼**出来的，`?` 与 `#` 在拼接
处没有判据——`https://api.example.com/v1?tenant=abc` 会拼成
`https://api.example.com/v1?tenant=abc/v1/chat/completions`，路径落到了 query
后面，而拼接本身不报错。所以挡在写入侧。

`--setting` 是渠道私有配置（自由形态的 JSON 对象），键由该渠道 `type` 指向的
适配器解释，选路层不认，管理面也不校验键名。**当前没有任何适配器读它**，所以给了
`--setting` 时命令会把这一点说出来。

`--channel` 不存在、`--type` / `--base-url` / `--model` 也都不开简写：这条命令上
挑错的是「凭证写给哪条渠道」，而 `-c` 这类单字母在别的命令行里既可能是 `channel`
也可能是 `config`。

#### `model`

规范模型目录（catalog 基础定义）。

**规范名是选路与计费共用的键**：请求里的模型名按它匹配，别名与计价规则也挂在它
上面。所以它不能带空白字符，也不能改——要换名字就建新名、把别名与规则挪过去、
再删旧名。`update` 与 `delete` 都按 `--model` 定位，它本身不可改。

**六个能力标志各有三态**：不给 = 未知（库里是 `NULL`）、给 = 支持、
`--tools=false` = 明确声明不支持。三者在选路时处置不同：未知与支持放行，不支持
会让用到那一项的请求选不到这个模型。所以 `create` 时没给的开关落库是 `NULL` 而不
是 `false`——那是「还没配过」，不是「配了说不支持」。

判断一条记录配没配过，看 `list` / `get` 的那一栏：没配过的项在 `list` 里不列
（六项都没配过时打 `-`），`get` 里逐项打出「未知 / 支持 / 不支持」。

六个能力标志**成组**写入（写入路径对那六列是一次全量覆盖），所以给了其中任何
一个，命令会先读出当前那一行，再把这次给出的盖上去：只给 `--tools` 不会把另外
五个能力抹掉。

`delete` 只在**无人引用**时允许：还有别名或计价规则挂着这个规范名时它会被拒，
并报出各有多少条。别名要先删（渠道的 `models` 白名单里还留着这个名字，删别名不
等于删那条配置），计价规则要先改掉 `model_patterns`——直接删规则不会报错，只会让
请求落到别的规则上。那条错误原样打出来，不要绕过它去库里删。

`reasoning_options` 与 `raw` 是采集来的原始元信息，命令行不写它们，也不在 `get`
里打。

#### `alias`

模型别名映射（上游模型名 ↔ 规范名）。不带 `--channel` 的别名是**平台级**，对所有
渠道生效；带 `--channel` 的是渠道级，只对那个渠道生效，并盖过同一条平台级别名。
同一个规范名在每个范围里最多只能有一个上游名——两个上游名指向同一个规范名时，
选路无从取舍。

`--overrides` 是一组**上游请求参数**的覆盖，只允许三个键：`temperature`、
`top_p`、`max_tokens`。别的键在写入时就被拒绝——它们要么改的是请求的形状
（`model`、`messages`、`tools`、`stream`），要么根本不是这个请求的参数。与调用方
冲突时的口径：调用方**给了**的采样参数以调用方为准，没给的取覆盖值；`max_tokens`
反过来，一律以覆盖值为准。

`update` 按 `--id` 定位，**渠道范围与规范名都不可改**：改渠道范围是换了一条别名，
改规范名等于把这条别名改挂到另一个计费键上，而那样同一次请求的选路与计费会指向
两个不同的模型。要改就删掉重建，两次改动各自看得见。

`resolve` 走的是请求热路径上同一条查询，所以「渠道级别名盖过平台级那条」这件事在
这里看得见（`list` 只是把两种范围各列一遍，不回答谁赢）。

#### `price`

模型计价规则与日历管理。规则的作用域决定哪两栏 id 有效：`platform` 两栏都留空；
`merchant` 必须给 `--user`；`channel` 必须给 `--channel`。写了读取路径不看的那一
栏会被拒绝，因为那是一条「配了却不生效」的规则。

表达式在写入前会编译一次，编译不过的命令直接失败：一条编译不过的规则进了库，表现
是每个用到它的请求都失败，而失败点在请求路径上。

计价项一共五个：`prompt`、`completion`、`cache_read`、`cache_write`、
`reasoning`。上游报了哪一项，规则里就必须有哪一项的单价——少一项不是少收，是这次
请求整个失败（结算报「用量里有规则未定价的计量项」）。会报缓存的上游很常见，所以
新规则把这五项都写上、用不到的填 0，比漏掉再被拦住省事。

`list` 按**裁决次序**排列：适用于某次请求的第一条就是会被选中的那条。裁决次序是
作用域（`channel` > `merchant` > `platform`）→ `priority` 大的优先 → 模型名单非空
的优先于兜底 → id 大的优先。所以同作用域同优先级下，后加一条兜底不会盖掉已有的
模型专属价；要让兜底赢，把它的 `--priority` 调高。

`update` 校验的对象是**改完之后的那一行**，所以换作用域时要把该清的那一栏一起清
掉：改成 `platform` 用 `--user 0` 与 `--channel 0`，改成 `merchant` 要给
`--user`，改成 `channel` 要给 `--channel`。给空串的 `--user` 会被拒——那多半是一
个没展开的变量，而它读起来像「不挂商家」。

`create` 与 `update` 的 `--by` 必填，两栏记的不是同一件事：`pricing_rules.created_by`
是这条价是谁**定**的（只有 `create` 写它），`pricing_rule_versions.changed_by` 是
这一版是谁**改**的（只有 `update` 写它，而且只在表达式真的变了、留了一版时才有这一
行）。`update` 不动 `created_by`——定这条价的人在改价里可能根本没参与，把这个人当成
改动人写下来，审计会读到一个没做过这件事的人。`--by` 收 `users.id` 或用户名，落库记
的是那个 ID。它**不算**一次修改：`price update` 只给 `--by` 而没有别的字段时会报
「至少要改一项」。

**启停是独立的二级动词**（`price enable` / `price disable`），改属性的命令不带状态
开关：「顺便改个状态」与「启用这条规则」是两种意图，混在一个命令里时，那条
`update` 的最后一行日志说不清是哪一种。

`explain` 把**全部适用**的规则按裁决次序列出来，第一条就是会被选中的那条，排在它
后面的每一条都在说明「为什么不是它」。`--at` 用来问过去某一刻（对账时问「这一笔
当时按哪条算的」）。一条适用的都没有时非零退出，与请求路径上的处置一致（那是拒绝
服务，不是「按 0 元计」）。

日历数据文件的格式与约束见 `larkaxctl price calendar --help`。`--channel` 与
`--effective-to` 不开简写：`-c` 在别的命令行里既可能是 `channel` 也可能是
`config`、`count`，挑错作用域会把一条规则挂到另一个渠道上；`--effective-to` 是边界
参数，写短了容易看错。

#### `price calendar`

维护分时计价用的日历数据。这一组的数据是分时计价规则的输入，离开计价规则没有别的
用处。文件格式的完整说明在 `larkaxctl price calendar --help`（写在那里而不是只写在
这里：跑 `import` 时手边应当就能查到它）。

`pending`（公告尚未发布）、`conflict`、`degraded` 三种状态只记年份状态，不带
`days` 也不带 `source`——那一年还没有定论，写进去的数据行会被当成确定的判定使用。

`list` 列出导入过的年份：地区、年份、状态、天数、双源校验结果与写下的时刻，同地区
内按年份从新到旧。**没有导入过的年份不会出现**——它没有写 `calendar_years`，也就
没有「未导入」这一行可列；判定时这样的年份按未知处理。`status` 打的是库里那一列的
原文，同步失败的原因单独排在表后一行一条，公告原文地址只在 `-v` 下打。
`-o json` 下清单在 `calendars` 里，键名用库里的列名。
`sources_agree` 为 `null` 表示那一年没有第二个源可比。

旧路径 `larkaxctl calendar import <文件>` 仍然可用。`list` 只挂在 `price` 下面，
旧路径没有这一条。

### 权限与财务 (Access & Ledger)

#### `user`

系统用户管理（创建、查询与修改）。`create` 只把新用户的 ID 打到 stdout。

角色取 `user`、`merchant`、`admin` 之一，默认 `user`。三者都是用户，
`merchant` 与 `admin` 只是 `users` 表上的标记（`admin` 同时也是 `merchant`）。
**角色今天只是记下来，不改任何一处行为**：读那两个标记的只有展示与筛选
（`list` 的角色栏与 `--role`），没有任何鉴权判断读它们，所以
`--role merchant` 不会让这个用户多出什么权限，`--role admin` 也不代表他能进管理
接口（管理面还没做）。它们留给管理面的鉴权用，接上之前别把它当成一条访问控制。

**不做幂等**：用户名已被占用时直接报错，不会改到已有的那个用户。

用户名的形状也有限制：**整串是一个十进制整数的名字建不出来**（`--name 123`、
`--name 007` 都是，带一个正负号的 `+7` 也算；`1a`、`a1`、`1.0`、`1e3` 不是），
`create` 当场报参数错并退出 2。`--user` 把这样一个名字按 ID 解释（见下面 `get` 的
标识规则），于是它建出来之后按名字读不回来——`user get` 与 `user update` 都够不着
它，只能改库。名字里带一个非数字字符就能避开。

邮箱的写法也判，收的是**地址本身**那一种，五条：`@` 恰好一个、两边都不为空；
本地部分只由字母、数字与一组常见符号组成（`+`、`_`、`-`、`'`、`!` 这些，完整的
那一组写在报错里），域名只由字母、数字、连字符与点组成；域名里有一个点；两半都
不以点开头或结尾，也不出现连着两个点；域名里用点分开的每一段，都不以连字符开头
或结尾。

`user+tag@example.com`、`first.last@example.com`、`a@b.example.com` 都收；
`not-an-email`、`first@second@example.com`、`a b@example.com`、`a@example.com.`、
`a@example`（域名没有点）、`a@-b.example.com` 都报参数错并退出 2。
带显示名、注释或引号的写法（`Bob <bob@example.com>`、`bob@example.com (comment)`）
也报错——这一列存的是地址本身，不是一个信封上的收件人栏，而同一个人的另一种写法
存进去会被当成第二个邮箱（这一列上有唯一约束）。

**非 ASCII 的字母与数字也收**（全角的 `Ａ`、西里尔文的同形字这些都算），而这一列
的大小写不敏感只覆盖 ASCII：`Ａ` 与 `A`、西里尔 `а` 与拉丁 `a` 是**两个不同的
值**，唯一约束分得开，会并存成两条。长度不设上限（标准里本地部分到 64、整串到
254）：300 字的本地部分照收，这是这一版有意留的边界。

**空邮箱不是格式错**：`create` 的 `--email` 给空串是不填这一列（库里是 `NULL`），
`update` 的 `--email` 给空串是把它清回 `NULL`（见下面 `update`）。

`list` 按 id 从小到大列出用户，一栏一个字段：ID、用户名、状态、角色、邮箱。
`--status` 取 `active`、`suspended`、`banned` 之一，`--role` 取三个角色之一，
两个都可以给、也都可以不给（不给就是列全部）。`--role` 按**称呼**逐字匹配，
与 `create` 写进去的那一个对应：`--role merchant` 列出的是称呼为 `merchant`
的用户，`--role admin` 列的是 `admin`。取值不认识时报参数错并退出 2，不回落成
「不筛」。

**状态只有 `update` 能改**：`suspended` 与 `banned` 都会让他手里的 key 全部失效
（见 `internal/auth` 的鉴权判据），把它写回去走 `user update --status`——在库里
直接改也一样生效，但那样既没有取值校验也没有回显，事后说不清是谁改的。

`get` 按 ID 或用户名读一个用户的全部字段：除清单那五栏，还有展示名、创建时间与
更新时间。标识怎么解释与别的命令一致：纯数字按 ID，否则按用户名。找不到时退出 4。
所以纯数字的用户名按名字读不出来，`create` 不让这样的名字进库（见上面），而库里
已经有的那些不动。

`update` 只改**显式给出**的字段，一个都没给就报参数错并退出 2（不做静默空操作）。
每一条旗标说的都是它自己那一列变成什么：`--status` 取三个状态之一；`--email` 与
`--display-name` 给空串表示把这一列清回 `NULL`（不是写成一个空串，`--email` 的新值
还要过上面那条格式校验）；`--merchant`
与 `--no-merchant` 把 `is_merchant` 置真 / 置假（`--no-merchant` 不能单独打在
`admin` 上，见下）；`--admin` 把 `is_admin` 置真**并且**把 `is_merchant` 一起置真
（`admin` 天然也是 `merchant`，与 `create --role admin` 落的是同一种数据），
`--no-admin` 只把 `is_admin` 置假、`merchant` 不动。
两个文本列的取值两头空白会被去掉（`create` 的 `--email` 同一口径），去掉之后是空串
就清回 `NULL`；`--status` 也是先去两头空白再比对，但空串仍然不认。

所以下面三组是互相打架的输入，**当场报参数错、不挑一个落库**：`--merchant` 与
`--no-merchant`、`--admin` 与 `--no-admin`、`--admin` 与 `--no-merchant`。

还有一条挡的是改完**那一行**而不是输入本身：`--no-merchant` 打在 `admin` 上同样
当场报参数错。它只把 `is_merchant` 置假，留下的那一行**读出来仍然是 `admin`**
（这一档按 `is_admin` 读，见上），于是回显里角色那一栏没变、屏幕上只剩首行，看起来
像什么都没做。出路有两条，一条命令都不必分两次发：先 `--no-admin`（`is_admin` 置假、
`merchant` 不动），或者 `--no-admin --no-merchant` 一起给，一步落到普通用户。

改完把**真的变了**的字段按「旧值 → 新值」逐行打到 stdout，首行是「已改用户
<用户名>」。两栏都是库里的值：旧值取自改之前读的那一行，新值取自那条 `UPDATE`
的 `RETURNING`。给出的旗标没带来变化时（例如对本来就是 `merchant` 的用户再
`--merchant`）那一行不出现，所以打出来的行与这次的改动是同一件事。用户不存在时
退出 4；邮箱撞上别的用户时报「邮箱已被占用」并带上那个值，也退出 4。

四条命令都不需要 `LARKAX_MASTER_KEYS`（它们不碰渠道凭证）；`list` 与 `get` 不改
任何一行。

#### `apikey`

API Key 访问密钥、状态与额度管理。这四个子命令都不需要 `LARKAX_MASTER_KEYS`：它们不碰
渠道凭证，也就不碰信封加密（主密钥是 `secret rotate`、`channel` 的写入与 `plugin` 的
`delete` / `kv set` / `kv delete` 那三条的事）。

**明文只打印这一次**：库里存的是 SHA-256 哈希，它不可逆，丢了没有任何办法取回，
只能重建一把。所以明文单独打到 stdout，其余信息打到 stderr——`larkaxctl apikey
create --user alice > key.txt` 保存下来的文件里只有明文，不会混进前缀、id 与提示语。

`get --id <ID>` 打一把 key 的现状：状态、备注、两列额度，以及创建、过期、最近使用三个
时刻。它读的是 `list` 那一行的同一份数据，只是收成一把，所以 `list` 里打成「继承」
「不过期」「从未」的那四处（每分钟与额度都是「继承」）在这里是同样的四个词。

两列额度都按**明文**给，不填表示 `NULL`：`--rpm` 是每分钟请求额度，**0 不是
「不限」，是「一个都不放行」**；`--quota` 是这把 key 累计可花费的金额上限，单位是
该用户钱包的资产品种（见 `user_wallets.asset`）。不填（或 `update` 时给
`--clear-rpm` / `--clear-quota`）写回 `NULL`，即「继承用户默认」——`users` 表上目前
没有这样一个默认值，所以它等价于不限。

负数一律拒绝：限流那一侧把负数也当成「一个都不放行」，而写下 `-60` 的人几乎总是
想写 `60`。让他当场改掉，比让它变成一个静默的封禁好。

`update` 一次可以改多项，只改命令行上**真的给出**的那几项，一项都没给时报参数错（一条
什么都没改的命令与一条改成功的命令在屏幕上一模一样）。改完把改了哪几项、各从什么变成
什么打到 stderr。

`--status` 取 `active`、`disabled`、`revoked` 之一。`disabled` 与 `revoked` 在鉴权那
一侧都会被拒，区别只记在**拒绝的原因**上（观测里分别计数），所以选哪一个取决于你想在
那份计数里看到什么。一把停用的 key 可以用 `--status active` 恢复。

`--expires-at` 给一个 RFC3339 时刻，到点之后这把 key 自动不可用；`--clear-expires-at`
写回「不过期」。已经过去的时刻会被拒绝：要立刻停掉一把 key 就改 `--status`，那样鉴权
记下的原因是「被停用」，而设一个已经过去的过期时刻记下的是「已过期」——两种情形要分的
是下一步该找谁。`--name` 给空串表示「没有备注」，与 `create` 不给 `--name` 是同一个
意思（列是 `NOT NULL`，空串就是它的「没有」）。

两个额度**不开简写**：它们是限额，写短了容易看错也容易按错。`apikey` 下唯一的简写
是 `-u`（`--user` 的别名，`create` 与 `list` 认它）。

旧名 `--rate-limit-rpm` 等同于 `--rpm`，`--clear-rate-limit-rpm` 等同于 `--clear-rpm`；
`--quota-limit` 等同于 `--quota`，`--clear-quota-limit` 等同于 `--clear-quota`。

#### `wallet`

用户钱包账户与入账管理。`create` 与 `credit` 都只写 `user_wallets` 与
`ledger_entries`，不碰 `users`，也不需要 `LARKAX_MASTER_KEYS`。

`create` 给一个已存在的用户开通钱包，余额为 0。它不写任何分录：新开的户在账本上
没有分录，这个用户在 `user` 科目上的分录之和为 0，与快照里的 0 自洽。带初始金额
意味着这次开户同时是一次充值，而那属于充值入口——用 `credit`。**幂等**：钱包已经
存在时什么都不做、照样退出 0，两种结果都只能靠输出的那一行分辨（逐字是「已为用户
… 开通 … 钱包，余额 0。」与「用户 … 已有 … 钱包，未改动。」），脚本匹配「开通」与
「未改动」这两个词。

`credit` 是运营手工入账：走账本写一组 `topup` 分录（借 `user:<ID>`、贷
`payment_gateway:<来源>`），并在同一个事务里更新 `user_wallets.balance`。它不绕过
账本直接改余额——那样会让钱包快照与分录对不上，下一轮对账会报。

`--ref` 是这笔入账对应的**外部单据号**（银行流水号、支付通道的单号），它同时是幂等
键，**必填且没有默认值**：它被确定性地映射成这次交易的 `txn_id`，于是同一条命令重
跑两次只会入账一次。同一个 `--ref` 配不同的金额、用户或通道不是重放，而是冲突：
数据库里那笔交易与这次要写的不是同一批分录，命令退出 4，一笔都不写。键里不能有控制
字符（换行、制表符等）——它既算交易号又进备注，而备注会把控制字符换成空格。

`--gateway` 是这笔钱从哪个外部来源进来（记进 `payment_gateway:<来源>` 科目），默认
`manual`，表示线下到账。来源名归一成小写。当前不接支付通道的回调，所以来源是操作者
说的，不是系统验证过的。钱包必须已经存在：先 `create`，再 `credit`。

资产默认取 `settings` 的 `billing.default_asset`（迁移里的默认值是 CNY）；
`--asset` 可以显式指定，但当前只有 CNY 一种受支持的资产。资产品种是钱包主键的一
部分：同一个用户可以同时有 CNY 与其他资产的钱包。用户用 `--user` 指定，纯数字按
ID 解析，否则按用户名解析。

`list` 是只读的那一条（也不需要 `LARKAX_MASTER_KEYS`），列出用户 ID、用户名、
资产、余额与冻结额。不带 `--user` 时列出全部钱包，带的时候只列那一个用户。
用户不存在时报「找不到用户」并退出 4；用户存在但还没有钱包行时，输出的是一句
明确的空清单提示而不是空表头。筛用户时 `-u` 与 `--user` 等价。

那一行的余额取自 `user_wallets.balance`，是**快照值**；从分录现算的权威值由
`ledger balance --account user:<ID>` 给，两者是否一致由 `reconcile` 比对。
冻结额是为在飞的请求预扣住的那部分，它**不包含**在余额里。机器可读那一档
（`--format json`）把两个金额打成定点小数字符串，用户 ID 打成数字。

旧名 `wallet open` 等同于 `wallet create`，
`--idempotency-key` 与 `--order` 都等同于 `--ref`。

#### `usage`

用量与计费的只读清单。两条子命令各读一张表，回答的问题不同：`events` 读
`usage_events`，那是**计量**的底稿（每次请求用了多少 token、金额按哪条口径算出来的、
收了多少钱；`billing_path` 为 `measured` 的才是一次实测，`estimated` 是按估算给的、
`fallback` 是算不出来时按退路给的）；`requests` 读 `billing_requests`，那是**每次
请求**的预留与结算（`pending` / `settled` / `released` / `failed` / `refunded`，
以及预留额与结算额）。

两条都按 `--user`（用户 ID 或用户名，两种写法都认）与时间窗筛，时刻用 RFC3339 或
只写日期（按 UTC 零点算），区间左闭右开。两个时间参数都不给就是不限时间，那时每个
月份的分区都会被扫到。时间窗按哪一列圈定，两条不一样：`events` 按**落库时刻**，
而那一列正是这张表的分区键（`usage_events` 按月分区，见 `partition` 一节），所以给了
窗口时范围之外的那些月份不会被扫到；`requests` 按请求的**受理时刻**，一次迟到的结算
不会让它从发生的那个窗口里消失。

两张表的代价不一样。`usage_events` 那边，给了窗口就能按分区裁掉范围之外的月份；
`billing_requests` 上只有 `(user_id, started_at)` 一条索引，**只给时间窗、不给
`--user`** 时，按 `started_at` 筛用不上它（索引的第一列是 `user_id`），要全表扫一遍
再排序——窗口开得越宽越慢。

两条都是**管理员动作**：跑得起 `larkaxctl` 的人本来就能连上这个库，所以这里不额外
要求别的授权，也不带角色参数。

`--limit` 是一次最多打几行，默认 50，0 表示不限。清单新的在前；被截住时末行会说明
只打了多少条，机器可读输出里对应 `summary.truncated`。

#### `ledger`

财务账本管理：读余额、校验分录，跑一轮对账，以及看对账的历史。`balance`、
`verify` 与 `runs` **只读**：不改任何一行、不写任何快照，任何写入都走各自的写入路径，
这里不提供。`reconcile` 不是只读的：它往 `reconcile_runs` 记一行，并在 `settings` 的
`reconcile.auto_repair` 为真时按口径修差额——要不要动手由那个开关决定，命令行上不
带参数，于是「线上跑的是哪一套口径」只有一个答案（库里的值）。

`runs` 读的就是 `reconcile` 写下的那张表，所以两件事对得上：清单里最新那一行就是上
一轮。每一行给出开始时刻、状态（`running` / `done` / `failed`）、范围（全量还是增
量）、起点（下一轮增量从这里开始）、比对过的钱包行数、四类差额（余额、冻结、畸形科
目、陈旧预留）与修复条数。**范围**那一栏最要紧：增量只看上次起点之后变动过的行，
一份全是增量的清单说明「两边都早就错着」的那种不一致还从来没被看过一眼。`--limit`
默认 20，0 表示不限。读它同样是管理员动作，理由与 `usage` 那两条相同。

`balance` 打出来的余额是从分录**现算**的权威值，不是 `user_wallets` 里那个快照。
两者是否一致由 `reconcile` 比对，它还会把差额归集到 `reconcile_difference`；
`balance` 只回答「账本上是多少」。

科目按账本的写法给，例如 `user:42`、`merchant_payable:7`、`payout:3`、
`payment_gateway:<通道名>`、`platform_revenue`、`upstream_cost`、
`reconcile_difference`。时刻用 RFC3339 或只写日期（按 UTC 零点算），区间左闭右开。

`verify` 的范围按「在这个区间里出现过的交易」圈定，而每一笔交易都会**整笔**读回来
校验：只按行过滤会把横跨区间边界的交易切两半，而半笔可能看起来是平的。
`verify` 发现不合法、或区间里一条分录都没有时退出 1；`reconcile` 发现不一致时也是
1。旧路径 `larkaxctl reconcile` 仍然可用。

### 系统与数据维护 (Maintenance & Data)

#### `migrate`

数据库版本迁移。`create` 只写文件、不碰数据库，其余各条都要连库。

`up-to` / `down-to` 是一步一步走到目标版本的，不调用 `goose` 自带的同名命令：实测
它们会停在目标版本的相邻位置（从 v2 执行 `down-to 0` 只退到 v1），差一位的表现比
不支持更危险。

#### `partition`

数据库月度分区维护。`usage_events` 按 `created_at` 按月分区，分区不会自己长出来：
没有预建时，过了迁移里种子覆盖的月份之后，每一行用量事件都落进兜底分区
`usage_events_default`——不报错、查询照常返回正确的行，只是这张表退化成「所有数据
堆在一个分区里」。而兜底分区里的行会挡着那个月的分区建不出来，要人工先把行搬走。

`ensure` 与 `check` 是给外部调度器用的：命令的退出码就是告警信号。`--months` 是
「从当月起算几个月」，默认 3（含当月），它决定的是提前量：给 1 只保证当月，预建任务
停摆超过一个月，下一个月的分区就不存在了；给 3 留出两个月的缓冲，代价只是多几张
空表。

`check` 只读，它不建任何东西。写入路径自己会保证当月分区存在，所以 `check` 报出
「缺月分区」说明预建任务漏跑了，而不是写入路径坏了——这两件事的处置不同，所以
`check` 不去替 `ensure` 把分区补上。

#### `secret`

安全凭证与主密钥维护，密钥轮换（`rotate`）需要主密钥。密钥本身从环境变量
（`LARKAX_MASTER_KEYS`）来，这里没有「设置密钥」这个动作：写进命令行或库里的密钥
会跟着 shell 历史与备份一起流传出去。这一组做的是**换**密钥——把已有的凭证重新包
一份新的，全程不需要明文凭证。

它挂在 `secret` 而不是 `channel` 下面：轮换读写的确实是 `channels` 那一列，但它管
的是密钥本身的生命周期，与渠道怎么配是两件事。这与 `LARKAX_ROLE` 无关：运维命令不
属于任何角色，主密钥直接从这个变量读。

#### `secret rotate`

轮换渠道凭证的主密钥。它补的是「当前主密钥的一份数据密钥副本」，**不解密凭证正
文**：每个信封本来就被旧主密钥包着，本命令给它再包一份新的。

顺序（重要）：本命令只保证新主密钥的副本存在，**不退役旧主密钥**。

1. 把新主密钥放进 `LARKAX_MASTER_KEYS` 的**首位**，旧密钥留在后面，重启服务；
2. `larkaxctl secret rotate` 看清有多少行要改；
3. `larkaxctl secret rotate --apply` 轮换（可中断、可重跑，重跑是幂等的）；
4. `larkaxctl secret rotate --verify` 退出码为 0 才说明全库每一行都含新主密钥；
5. 到这一步才能把旧主密钥从 `LARKAX_MASTER_KEYS` 里去掉。

第 4 步之前去掉旧主密钥，那些还没轮换到的行就再也解不开了。跑 `--apply` 之前先备份
`channels` 表（至少备份 `credential_enc` 这一列）：轮换改的就是这一列。中断不会让
数据不可用——每一行要么是旧的（仍被旧主密钥包着），要么是新的（新旧都能开），不存
在解不开的中间态；没跑完的部分 `--verify` 看得见。

`--apply` 会取一把 PostgreSQL 会话级互斥锁，同一时刻只允许一处轮换，已有轮换在跑时
直接失败而不排队。干跑与验证是只读的、不取锁，但会在锁被占用时提示「读到的可能不是
终态」。

退出码：`--verify` 的退出码回答「有没有漏网的行」，有就是非零；`--apply` 的退出码只
回答「这一轮跑完了没有」——轮换不了的行会被逐行打出来，但那一行坏掉不该让整次轮换
报失败（它再跑一次也还是坏的，由 `--verify` 与人工处置）。

旧路径 `larkaxctl rotate` 仍然可用。

#### `maintenance`

数据留存与过期清理。这一组的共同点是「按留存承诺删掉过期的行」：留存期到了就删，与
业务上发生了什么无关，所以它既不挂账本域也不挂某个业务对象。第三方数据（例如请求
快照）的留存各有自己的分区维护命令，见 `larkaxctl partition` 与
`larkaxctl snapshot`。

#### `maintenance idempotency`

按留存期清理请求级幂等记录。留存期取自 `settings` 表的
`idempotency.retention_hours`，不在命令行上另设参数：同一件事有两个来源时，命令行的
那个会悄悄赢，而「留存期到底是几小时」会变成一件要看是谁执行的才知道的事。

输出的是**删了多少条**而不是一句「完成」：一条都没到期时，命令的输出必须与「根本
没跑成」区分得开。旧路径 `larkaxctl idempotency cleanup` 仍然可用。

#### `snapshot`

请求结构快照管理。`cleanup` 负责把到期的删掉；`redact` 走脱敏的**输入**，`get`
读脱敏的**产出**，而 `access-log` 把 `get` 写下的访问记录读回来。

留存期取自 `settings` 表的 `request_snapshot.retention_days`，不在命令行上另设参数
（同 `maintenance idempotency`）。

`allowlist` 不需要连库。它只读 `internal/snapshot` 里那张允许表，那是纯代码里的
数据。所以它能在没有数据库、没有配置的机器上跑——而「我们到底存了什么」这个问题，
恰恰经常是在一个连不上生产库的地方被问出来的。

`get` 的 `--actor` 与 `--reason` 都是必填。读一条别人的请求结构是读敏感数据的动
作，所以每一次读都要留痕：`snapshot_access_log` 里会写下一行，记着谁、什么时候、以
什么理由看了哪一条。表里 `reason` 允许为空，那是给系统自己写的行留的余地；人手读一
次，理由必须留下。写日志与读快照在同一个事务里：一个「读了但没记」的成功返回看起来
完全正常，而它意味着这张表存在的理由落空了。同一个 `request_id` 可能有多行（请求与
响应各一行，重试也可能各一行），`get` 全部按 `created_at` 升序打出来；一条都没读到
的时候非零退出，并且不写访问日志——没读到东西不算一次访问。

`redact` 看到的结果不是库里那条快照。它把一段报文交给脱敏器，回答的是「这段报文会
长成什么样」；库里那条骨架来自**解析之后**的请求 / 响应，字段集合与这里不完全一样
——不转发的字段不会进库，而解析会补上它自己带的几个。内容层面的结论一致：允许表之
外的一律变成占位。骨架打到标准输出（可以直接接给 `jq`），方向、骨架版本、字节上限、
被替换的路径与那句提醒打到标准错误。报文从标准输入读，上限 64 MiB——这条命令是拿
一段**单次请求**的报文来试，不是拿整份日志。

`access-log` 按 `--request-id`、读取者（`--user`，用户 ID 或用户名）与时间窗筛，三者
可以一起给，也可以一个都不给（那就是最近的那些）。**`--user` 筛的是读快照的那个人**，
不是快照属于谁：这张表记的是读取动作，快照属于谁是快照那一侧的事。理由那一栏是 `get`
的 `--reason` 原文，系统自己写的行没有理由。它同样是管理员动作：跑得起 `larkaxctl` 的
人本来就能连上这个库，所以这条命令不额外要求别的授权——与 `get` 把读取者记成 `admin`
是同一条口径。窗口左闭右开，`--limit` 默认 50、0 表示不限。表上只有
`(request_id, accessed_at)` 一条索引：不按 `--request-id` 筛时，只给时间窗或只给
读取者，都要全表扫一遍再排序（同 `usage requests`）。

`request` 与 `response` 各有一张允许表，所以 `redact` 必须指明方向；`allowlist` 与
`get` 不填时两个方向都处理。旧名 `snapshot show` 等同于 `snapshot get`。

#### `consent`

原样采集请求正文的授权。`grant` 开一条授权，`list` 看现有的，`revoke` 撤销。

两个范围二选一，字段不能混着给：`single_request` 只对 `--request-id` 那一次请求生效，
到 `--expires-at` 为止；`time_window` 对 `--from` 到 `--to` 之间的全部请求生效。时间窗
那一档的到期时间就是 `--to`，不另设参数——同一件事有两个来源时，命令行那个会悄悄赢。

`grant` 必须带 `--agree`。不带时它只把同意文案打出来、什么都不写：`capture_consents`
的 `consent_text` 与 `consent_version` 两列是拿来做合规举证的，落库之前操作者得先看见
自己同意的是什么。文案是 `internal/snapshotwire` 里的常量，改文案就要把版本号加一；
旧记录里留着的仍是当时那一份。

申请时长有上限：`settings` 的 `capture.consent_max_window_hours`。`single_request` 比的是
从此刻到 `--expires-at`，`time_window` 比的是两端的长度。超过上限**报错拒绝**，不夹到
上限——夹一下会让申请的那段时长看起来生效了，而实际生效的更短，等它到期时人已经不在
看着它了。错误里同时给出上限与申请值。

`list` 不带 `--user` 时列出全部用户的授权，含已经撤销与过期的那些：这一栏回答的是
「谁开过、开的是什么范围」，而不是「此刻哪几条还有效」。状态那一栏是显示口径，由撤销、
到期与时间窗三件事算出来。`-u` 是 `grant` 与 `list` 上 `--user` 的简写（见上面的
「短选项」）；`revoke` 的位置参数是授权 ID，它没有简写。

撤销、到期、时间窗没开始或已经过去，这四种情况在**读取的那一刻**重新校验：判定发生在
脱敏那一刻（`internal/gateway` 通过 `snapshotwire` 的 `ConsentSource` 问一次），每次都查
一次库，没有缓存。撤销要立刻生效，靠的就是这一点——缓存期内撤销过的授权仍在放行原文，
而那个窗口有多长取决于缓存，不取决于撤销这个动作。查库失败时按「没有授权」处理，落下来
的是骨架。

没有有效授权时采集侧落下来的就是脱敏骨架（`capture_mode = skeleton`），有授权的那一段
是原文（`full_consented`）。读原文那条路是 `snapshot get`，它自己写访问日志。按 API key
授权这一档不做：采集那一刻拿不到 key id，`capture_consents.api_key_id` 这一列留空。

#### `plugin`

动态插件系统管理。插件的 key 与版本写在源码里（`export const meta`），所以
`publish` 默认不要求 `--key`；只有想让注册名与源码里声明的不一致时才需要它——那种
情况下两条路会对不上，命令会拒绝。

`publish` **先在沙箱里编译一遍再落库**：一个编译不过的插件不许进库，否则加载器每次
启动都要处理它。同一个 `(key, version)` 重复发布是**覆盖**：源码、元数据、名称换
新，代次（`generation`）取这个 key 当前最大的代次加一，启用状态保持原值——改一个
笔误不该让已启用的插件下线。覆盖会让这一版排到最前：它本来是 `active` 的话，下次
启动加载的就是它。换版本请改源码里的 `meta.version`，那会插入一行新代次（同样取
最大值加一），状态是 `pending`，要 `enable` 才生效。

`publish` 的 `--by` 必填。`plugins.created_by` 记的是谁写下的这一行，而一条不记名
的写入等于没有审计——允许留空的话，最省事的用法就是永远不填。它收 `users.id` 或用户
名，落库记的是那个 ID，`list` 与 `get` 的 `-o json` 里 `created_by` 那一栏就是它
（不为 `null` 表示记下来了）。**覆盖时这一栏跟着换成这一次的操作人**：那一行的
`source` / `meta` 已经被这次发布换掉了，而 `get` 里那一栏问的是写下现在这份内容的
人。同一行的 `created_at` 不跟着换——它记的是这一行什么时候出现的。

**本版没有热更新**：`publish` / `enable` / `disable` 都只改库，跑着的进程要重启才会
重新加载。key 在库里没有对应行时按「约束冲突」返回 4。

`get` 看一个插件：打的是**最新发布的那一代**（代次最高的那一行），并说出这个 key
下还有几个更老的版本——不说的话，「只有一个版本」与「有好几个、你看到的是最上面
那个」在这份输出上一样。

`list` 与 `get` 都回答**三件事**：取中的是哪一代，最新一次尝试是哪一代，那一次加载
装上了没有。取中的是加载器会装上的那一代（同一个 key 里状态为 `active` 且代次最高的
那一行），最新一次尝试是代次最高的那一行，两者不一定是同一行：发布了新版本还没
`enable` 时取中的仍是上一代。

**加载期**的结果是第三件事：加载器每启动一次都重新读一遍参与注册的行，把结果写回库
里（`last_load_result` / `last_load_error` / `last_load_at` 三列）——装上了写 `ok`、
被跳过时写 `failed` 连同当时的错误原文与时刻。它与发布期无关：`publish` 根本不收编译
不过的插件，所以「发布了却没上线」只有这三列说得出来。

`status` 那一栏读不出「取中的是哪一代」：`enable` 新版本时旧的那一行不会被按下去，
于是一个 key 下可能有好几代都写着 `active`。`list` 与 `get` 里那两栏按加载器的口径
算出来（库里没有这两列），它们是同一个答案的两半：

| 这一行 | 「在跑」 | 「上次加载」 |
|---|---|---|
| 取中的那一代，上一次加载装上了 | `是` | `装上了`（那次加载的时刻） |
| 取中的那一代，上一次加载跳过了它 | `否` | `没装成`（时刻），原文在表后 |
| 取中的那一代，还没有加载记录 | `还没试` | `-` |
| 不是取中的那一代 | `否` | `-` |

同一个 key 里至多一行是取中的那一代，所以「是」至多一行。「**取中的那一代被跳过
时，这个 key 什么都不在跑**」——加载器在一个 key 里只取一代，跳过它不会退回更老的
那一代，那一刻哪一行都不是「是」。`get` 有同样的两栏，失败时也在表后打一句原文。

「还没试」与「否」是两回事：那三列由加载器写下来，它还没写过。来路有两条，下一步
不一样——`plugin.enabled` 关着时加载器整条链路不装配、根本不读表，重启多少次都不会
有记录，要先把这个设置打开（见 [settings.md](settings.md)）；开着时才是「发布或启用
之后还没重启过」，重启一次就有了。写回没落地时（连不上库、写超时）留下的也是旧的
那一份记录，所以「上次加载」的时刻还要读：它说的是**最近一次写成功**的尝试。

**跳过不改任何状态**：那一代的 `status` 仍是 `active`，启用记录也不动，所以下次启动
照样会再试一次——插件没装成时，先把源码或这次的装配调好再重启，不必重新发布。

`-o json` 下 `plugin` 条目在 `list` 的字段之外多三栏：`versions`、`created_at`、
`created_by`。两个命令的条目都带另外四栏：`latest`（这一条是不是最新一次尝试，
也就是代次最高的那一行——覆盖取的是最大代次加一，所以它就是最后发布的那一次；
早先写下的行里两行可能同代次，那时不止一条为真——那种并列就是当时覆盖发布把代次
原地加一留下的）、`running_generation`（这个 key 取中的那一代，
形如 `{"version": …, "generation": …}`，没有时是 `null`）、
`running_load`（那一次加载的结果 `{result, error, at}`，`error` 装上了是 `null`，
`at` 在那一行没有记下时刻时是 `null`——手工改库的行可以只填结果那一列，见迁移 00034；
还没有加载记录时整个是 `null`）、`compile_error`（发布期编译不过的原文，
没有时是 `null`；只有手工改库的行会有值）。

取中不等于在跑，而 `running_generation` 与 `running_load` 是**按 key 给**的：
同一个 key 的每一条带着同一份，脚本要判的是**这一条自己**是不是取中的那一条——
`version` 与 `generation` 都与 `running_generation` 相等（代次会撞车：
早先写下的行里两行可能同代次，那时只比代次就会在同一个 key 里撞出两行来——
那种并列是当时覆盖发布把代次原地加一留下的）。是取中的那一条时，
`running_load` 为 `null` 是 `还没试`、
`result` 是 `ok` 是 `是`、是 `failed` 是 `否`（原文在 `error`）；
不是取中的那一条时是 `否`，与它自己那份 `running_load` 无关。

`delete` 是硬删除：插件行、它的启用记录与 `plugin_kv` 里属于它的键一起删掉，不可
逆，也没有导出。`plugin_kv` 没有指向 `plugins` 的外键，不在这里一起清的话，那些行
会永远留在库里而没有任何命令看得见它们。回显在 stderr 上，三样数量各报一次。

`plugin kv` 是插件私有键值存储（`plugin_kv` 表）的三个动词：`get` / `set` /
`delete`。一个键的身份是三段——插件、用户、键，三条命令都要给全 `--plugin` 与
`--user`。**过期的键按不存在处置**：`get` 与 `delete` 都说没有这个键（退出码 4），
而过期的行仍留在表里，由下一次 `set` 顺手清掉。`set` 的 `--ttl` 只认 Go 的时长
写法（`1h30m`、`45s`），不给或给 0 表示不过期，负数被拒。写入不对值做任何解析：
它是插件的私有数据。

**只读的那几条不要主密钥**（`list` / `get` / `kv get`）；`delete` 与 `kv set` /
`kv delete` 要求 `LARKAX_MASTER_KEYS` 在场，`publish` 不在内——它不 seal 任何
东西。命令本身不做解密，这一条要的是「这台机器带着运维凭证」。
