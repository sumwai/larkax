# larkaxctl 命令参考

`larkaxctl` 是 larkax 的运维命令行。根帮助页（`larkaxctl --help`）只列一级命令与当下
要用的那几行；本文件写全局约定、退出码边界与各命令的完整说明。

每条命令有两版帮助：`larkaxctl <命令> --help`（也认 `-h`）给一屏摘要，
`larkaxctl help <命令>` 与 `larkaxctl <命令> help` 给展开的那一份。

这份参考同时有 man 版：首页列出各命令页，各命令页指回首页，而命令页之间不互相引用。
它们由命令注册表与本文件生成（见 [development.md](development.md) 的「每道门在挡什么」），
不手工改。发布的 tar.gz 里带着这几页（见 [versioning.md](versioning.md)）：解开那个包，
把 `MANPATH` 指到解出来那个目录下的 `man/`，命令与下面这条同形。源码树里是这样翻的
（`man` 只认 `MANPATH` 下的 `man1/` 这类子目录，所以指到 `man/` 那一层）：

- `MANPATH="$PWD/man" man larkaxctl-channel`

## 全局约定

这几条对所有命令生效，写在子命令的前面或后面都认。

### 环境变量

运维命令只读下面这几个环境变量：

| 环境变量 | 用途 |
|---|---|
| `LARKAX_DB_DSN` | 数据库连接串 |
| `LARKAX_ENV` | 环境名 |
| `LARKAX_LOG_LEVEL` | 日志级别 |
| `LARKAX_MASTER_KEYS` | 主密钥。只有这几组命令读它：`channel create` / `update`（写凭证）、`channel sync-models`（解出凭证去拉上游模型清单）、`secret rotate`、`plugin delete` / `kv set` / `kv delete`（删插件、或动它的私有存储） |

`LARKAX_ROLE` 与运维命令无关。命令行自身的配置加载见 `internal/config` 的 `LoadOps`。

### 展示文本里的控制字符

写进库、随后会原样打进终端表格或单条回显的自由文本字段（展示名、备注、渠道名、
模型名与别名、计价规则名、读取理由、插件元数据与键等）**拒绝控制字符**（C0 与
DEL，换行、制表符、ESC 都在其中）：换行会把一栏折成两行，ESC 这类转义序列还会被
终端当成指令执行。命令当场报参数错并退出 2，报错点名是哪一个字符；空格、标点、
中文都照收。`plugin kv set --value` 不在其列：那一栏按设计原样输出。

### `.env` 与 `--env-file`

`.env` 文件的取值规则：

- 不给 `--env-file` 时，从当前目录往上找，**不越过 git 仓库根**，用最近的那一份。
- `--env-file <路径>` 指定另一份文件。
- 两种来源都**只填补尚未设置的环境变量**：已经在环境里导出的变量优先，`.env`
  补不上它。所以一份注入的生产环境不会被误带的开发 `.env` 覆盖。

只用 `.env`、不在环境里导出任何变量也可以。

### 退出码

| 码 | 含义 |
|---|---|
| `0` | 成功 |
| `1` | 其他失败 |
| `2` | 命令行参数错（缺字段、取值解析不了、取值的形状不合要求、标志组合不对、读过那一行才知道不对的组合） |
| `3` | 连不上数据库 |
| `4` | 约束冲突（唯一键、外键、要改或要查的那一行不存在；同一幂等键已经对应另一笔入账） |

**`1` 与 `2` 的分界不在「谁校验出来的」。** 两档里都有由包判出来的错，也都有由
命令行自己判出来的错；一个错落哪一档，由**命令自己**定——它在报出去之前把这个错算进
「参数错」的归 `2`（代码里就是包一层 `usageErr`），没算进去的落回 `1`。所以下面这几条
是**按命令列出来的清单，不要拿其中一条去推另一条**；要确认某条命令的某一档，看它
实际给哪个码。

- **`user` 的 `--name` 与 `--email` 形状不合法给 `2`**：前者是整串为一个十进制整数
  或者含控制字符（都只在 `create` 上），后者是写不成一个邮箱地址（`create` 与 `update` 都有，
  见下面「user」一节）。这类错在**命令本身**——换一个值重发就能过，与库里有什么无关。
- **`user delete` 的状态前提与余额前提给 `4`**：没打标就 `purge` 或 `revert`、
  重复打标、重复匿名化、余额或冻结额不是 0，都是「库里那一行现在不是那个状态」，
  下一步是先把数据挪到能执行的位置。`--confirm` 与当前用户名对不上给 `2`：它错在
  命令里的那个值，把名字写对就能过（虽然要读过那一行才判得出）。
- **`settings set` 的键名或取值不认识给 `1`，不是 `2`**。它和上一条是同一个形状
  （都由包在连库之前判出来，也都不依赖库里有什么），差别只在命令把它算进了哪一档。
  对照 `wallet --amount`、`apikey --quota` 这类把取值直接写在数值标志上的命令：
  解析不了给 `2`。
- **写在已软删的渠道上给 `1`，不是 `4`**。`channel update` / `channel enable` /
  `channel disable` / `channel sync-models` 打到一个软删的 id 上，报的是「这条渠道
  已删」，归写入路径那一档；同一个 id 根本没建过才是「要改的那一行不存在」，给 `4`。
  软删的渠道列不进 `channel list`、也改不动，这两处有意分成两档。
- **写入路径上由包判出来的参数问题给 `1`**：作用域与归属的组合、表达式编译不过、
  渠道类型不认识。这三处由各包在写的那一刻判，报错原样上来，没有标成参数错那一档。
- **`wallet list` 有一格金额读不出来时给 `1`，而 stdout 上仍是一整张清单**：那一格打
  「不可读（超出可表示范围）」，其余行照打，stderr 上补一行说清是哪一行哪一格、库里的
  原文是什么（见下面「wallet」一节）。带上 `--user` 时反过来，是整条失败、stdout 空：
  窄查询问的就是那一格的值。

`2` 里还有一类：**命令行要读过库里的那一行才判得出**的参数组合，今天只有一处
（`user update --no-merchant` 打在 `admin` 上，见下面「user」一节）。它与上面那几条的
分别在于错在**命令本身**而不是数据里：改一下命令重发就能过，与解析阶段那几类是同一个
补救动作；而写入路径那一类错在数据，改命令没用，得先去看库里现在是什么。

上面这几个数是命令行的对外契约。按**触发条件**分的完整一张表（多出「体检结论」
那一档 D，它不打第二行、退出码照旧非零）见 [cli-output.md](cli-output.md) 的
「退出码」一节。

### 短选项

短选项固定为下面六个，其余选项一律写全名：

| 简写 | 全名 |
|---|---|
| `-u` | `--user` |
| `-m` | `--model` |
| `-o` | `--format` |
| `-v` | `--verbose` |
| `-q` | `--quiet` |
| `-V` | `--version` |

**`-V` 打版本号，`-v` 是详细模式。** 另外两条成对出现的约定：`-o` 与 `--format`
一样，写在子命令前后都认；`--verbose` 与 `--quiet` 不能同时给，两个一起给是参数错。

安全、财务与边界类的选项**不开短选项**，必须写全名：上游渠道、凭证来源、外部单据号、
速率上限、生效截止这几类。它们写短了容易看错也容易按错。

### 机器可读输出

`--format json` 把 stdout 收成一份 JSON，提示与警告走 stderr，给管道下游的 `jq`
与探针用。取值不合法时报参数错，不静默回落成表格。完整契约——状态符、上色条件、
表格对齐、时刻与时区——见 [cli-output.md](cli-output.md)。

## 按命令

每条一级命令的二级动作与参数在它自己的帮助里。帮助分两版：

- `larkaxctl <命令> --help`（也认 `-h`）打**短版**：有哪些动作、参数怎么给，
  外加一两条最关键的边界，一屏之内。
- `larkaxctl help <命令>` 与 `larkaxctl <命令> help` 打**长版**：短版之外再把
  其余边界说完。

**设计说明不在这两版里**，它在下面各节：某个字段为什么必填、这一步为什么
不可逆、别家工具怎么做，这些对跑命令的人当下没用，而写在帮助里的话每次敲错
参数都要被念一遍。

下面按根帮助页的分组逐条列出。

### 核心与诊断 (Core & Diagnostics)

#### `doctor`

系统健康与链路连通性体检。默认只读检查七项、不碰网络，`--verbose` 时每项多打
一段检查范围与完整原文，`--format json` 打一份完整的机器可读报告（它的细节本来
就在里面，所以不走 `-v`，问题清单也不截断）。

第 3、4、5 项回答的是同一个字符串在两个数组里对不上的问题：渠道的 `--models`
与目录里的规范名差一个字符，或者模型建了却没加进任何渠道的白名单——那时调用
回 503「no available upstream for the requested model」，而那句话不会说是哪
一个名字不对。第 3 项还多判一层：名字在目录里、但它声明的端点与这条渠道打的
那条对不上（目录里可以声明一个模型只在某几条端点上被服务，而渠道的 `type` 决定
它打哪条）——那时请求会打到一条服务不了的端点上，上游回 400
`unsupported_model`，从我们这边看与「模型不存在」无从分辨。

第 6 项问的是同一个问题的另一半，对象换成了规则：计价规则与成本规则的
`model_patterns` 里写到的名字都在目录里吗。写错时那条规则永远命中不了，而它在
任何清单里都看起来是配好的；空名单表示「适用于全部模型」，不报。第 7 项把
「用户没有钱包行」这类缺口在第一次调用之前指出来，而不是让人从 500 往回推。

「没跑成」与「通过」是两件事：没有可检查的对象时那一项报「没跑成」而不是
「通过」，退出码也非 0。两者在安静的终端里长得一样，是这个项目反复踩的坑
（见 [LESSONS.md](../LESSONS.md) 第 16 条）。

`--live` 要花钱、要凭证，默认不跑。**凭证不能写在命令行参数里**：参数会出现在
`ps` 的输出与 shell 历史里，凭证到了那里就等于交给了同机的其他进程和任何一个
能翻历史的人。所以只能从标准输入或环境变量读，与 `channel create` 同一个做法。
这里读的是打网关用的 **API Key**（`apikey create` 发的那把），不是渠道凭证。

`--endpoint` 选打哪个入口：`chat` 是 `POST /v1/chat/completions`
（`Authorization: Bearer`），`messages` 是 `POST /v1/messages`（`x-api-key`），
`responses` 是 `POST /v1/responses`（`Authorization: Bearer`）。`--base-url`
不给时按本次配置里的 `LARKAX_HTTP_ADDR`（含 `.env` 里的那一份）拼出网关地址，
与主服务听在哪儿是同一个来源：那个变量写着 `127.0.0.1:8081` 就打成
`http://127.0.0.1:8081`；写成 `:8080` 这类不写主机的「所有网卡」时按
`127.0.0.1` 打。网关不在本机、或者要打的是另一台，就显式给。

#### `settings`

运行期动态配置项管理（`settings` 表）。配置项存在库里而不是环境变量里，是为了
与数据同生共死：备份恢复、换机器时它跟着数据一起走，不会像环境变量那样漏掉一个
就整体不可用。

键与类型定义在 `internal/settings` 的 `Registry` 里，每个键的说明存在库中
`settings.description` 那一列（由迁移写入，`list` 打的就是它）。**未声明的键写不
进去**——库里出现一个代码不认识的键，表现是配置被静默忽略，而写它的人当场看不到
任何反馈。

`--by` 必填。`settings.updated_by` 记的是谁改的配置，而一条不记名的写入等于没有
审计——允许留空的话，最省事的用法就是永远不填。

有些键不接受这条路径的修改（`settings.editable` 为 false）：它们改错会造成严重
后果，只允许由迁移写入。命令会报错并指出是哪一个。另有一些键**写得进去、但改了
不会有任何效果**：代码里还没有读它们的路径（`Registry` 里标了 `Unwired` 的那
几个）。命令照常写入，并在输出里指出这一点——不指出来的话，它与一个真的生效的键
在这条命令的输出上完全一样。

密钥类配置不放这里（明文落盘并进备份），它们走 `channels` 表的信封加密。这条由
上面的白名单保证：写入只认 `Registry` 里声明过的键。

`get` 看一个配置项：值打的是 `settings.value` 的 jsonb 原文（字符串带引号，布尔
与整数不带），类型与「接没接线」取自 `Registry`。库里没有这一行时按「要查的那一行
不存在」返回 4，并区分两种缺法：`Registry` 里声明过却缺了行，多半是写它的迁移
没跑到；`Registry` 里也没有，多半是键名写错。
`-o json` 下 `setting` 条目与 `list` 里那一条逐字段相同。

#### `admin`

管理内部监听上 admin API 的令牌。那一块接口面见 [admin-api.md](admin-api.md)。

`create` 生成 32 字节随机令牌（base64url），stdout 只有令牌那一行，说明走 stderr。
明文只出现这一次：库里只存它的 SHA-256，丢了只能重新生成。新令牌是**替换**而不是
追加，旧令牌立刻失效。`revoke` 之后任何令牌都匹配不上（请求得到 401）；它与
「从没配置过」不同——后者回 503，提示先 create，那时 `revoke` 不改库、直接报错
让你先创建一枚。

两条命令都不接受位置参数，也不支持 `--format json`：它们的输出是给人接走的一行值，
不是一份报告。

#### `version`

打印版本号与编译元数据。版本号在构建时注入（见 `Makefile`），从源码直接编译出来
的是 `dev`。

### 路由与模型配置 (Routing & Models)

#### `channel`

上游渠道管理（网关、凭证、关联模型）。**碰凭证的那些命令**（`create` / `update`
写凭证，`sync-models` 解出凭证去调用上游）需要主密钥：前者要信封加密，后者要解开
才能发请求。`enable` / `disable` / `delete` / `restore` 与读侧的 `list` / `get` /
`health` / `upstream-models` 都不要主密钥——它们一处都不读凭证密文。

**明文凭证只能从标准输入或环境变量读，不能写在命令行参数里。**命令行参数会出现
在 `ps` 的输出与 shell 历史里，凭证到了那里就等于交给了同机的其他进程和任何一个
能翻历史的人。

`create` 的 stdout 只有新渠道的 ID，其余信息走 stderr。`list` **不打印凭证密
文**，只打印它挂在哪些主密钥下（那不需要任何密钥材料）；默认不列已删的渠道，
`--all` 才列，并在「已删」那一栏标出删除时刻。

`get --id` 读一条渠道的明细：状态、关联模型、凭证挂在哪些主密钥下。
与 `list` 不同，**它读得到已删的渠道**——`list` 挑的是「现在能用哪些」，
按 ID 问一条记录时答「没有这一条」，会把「已经删了」与「ID 写错了」
混成同一句。

`health` 汇总每条渠道窗口内的调用读数与当前健康结论。汇总表给出状态、
最近一次探测时刻、请求数、失败数、失败率、缓存命中与未命中（以 token 计）、
延迟分位（p50 / p95）与成本；**成功数只在 `--id` 的详情里打**，汇总表没有
这一栏。窗口默认最近 24 小时，`--since` 收一个时长（`6h`、`90m`），或者
一个 RFC3339 时刻（`2026-10-18T00:00:00Z`）。未来时刻会被拒。默认不列
已删的渠道，`--all` 才列。

窗口只用来筛数据，不是每一项都按它算：请求数、缓存 token 与成本是窗口内
各小时的**和**（未命中算的是 prompt 加缓存写入），延迟分位每一列各取
**自己**最近一个有值的小时（p50 与 p95 因此可能来自不同的小时）——
分位数不能相加。缓存 token 那一档与选路读的是同两列，0 表示窗口内没有
样本。窗口内没有任何读数时，这几个数是 0 或 `-`，而健康结论仍然是库里
那一格。

成本那一列是窗口内各小时桶的上游成本合计（口径见
[channel-health.md](channel-health.md) 的「延迟、缓存与成本是重算出来的」
一节）：`-` 表示这一列没有可用的数——窗口里没有一条带成本的事件，或者合计
恰好为 0。别把它读成「免费」；没有配成本规则的渠道就是这一档。

渠道健康表（`channel_quota_state`）里没有这一条记录时，`health` 打 `unknown`：
「还没探测过」与「探过、是好的」不是同一件事。

`health --id` 额外列出窗口内逐小时的明细（请求数、成功数、失败数、
缓存 token、分位与成本）。这条渠道在窗口内一次都没被调用过时，逐小时那
一段说的是「窗口内没有逐小时的数据」，与清单为空时的「暂无渠道」不是
一句话。

`delete` 是**软删**：置 `deleted_at` 并把状态改成 `disabled`，行与它的凭证密文都
留在库里。历史账单（`billing_requests` / `usage_events`）仍然按 `channel_id` 引用
它，所以删除之后那些记录照样认得这条渠道。已删的渠道不能再 `update` /
`enable` / `disable`，再删一次不报错（打印「已经是删除状态」）。

`restore --id` 把软删的渠道改回可用：`deleted_at` 清空，状态回到 `enabled`。
恢复之后它的健康结论回落成 `unknown`——软删之前那一次结论说的是当时的渠道，
恢复不等于它现在就可用；要一条结论得重新探测。没有处于删除状态的渠道上敲
`restore` 不报错，只打一句「没有处于删除状态」。

`sync-models --id` 从上游拉一次这条渠道的模型清单并落库，需要主密钥。落库的是
**上游自己的模型名**，与 `channels.models` 那一栏不是同一份东西：后者是选路用的
规范名，两者之间隔着别名映射。这份清单不参与选路，只是给人看的事实。它是一次
显式同步——启动时不拉、请求路径上不调用、也没有后台轮询，所以记下的是**上次
同步那一刻**的上游清单，会过时。

上游不提供模型列表接口是常态：适配器回「不支持」时 `sync-models` 照样成功返回
（退出码 0），状态记成 `unsupported`，**已有清单一行不动**——「没有这个接口」
不构成「清单是空的」的证据。上游不可达或返回错误时命令失败，库里什么都不改。

`upstream-models --id` 读库里那一份清单与同步状态，不碰网络、不要主密钥。它给出
最近一次尝试与最近一次成功各自的时刻：这两个可以指向不同的时间（同步成功过，
后来上游改成不支持了）。清单的三栏是模型名、首次见到、最近见到；同一个名字连续
同步两次只会刷新「最近见到」，不会多出一行。同步状态有三档：已同步（`synced`）、
上游不支持（`unsupported`）、未同步（`never`，这一档只出现在读侧，库里没有对应的行）。

`channel get` 里那一栏 `models` 是选路白名单（规范名），`upstream-models` 打的是
上游模型名。两份都在屏幕上时别混着读。

渠道类型必须是已注册的适配器类型；类型写错时错误信息会列出已知的类型。
`--models` 至少要有一个：读取路径把 `models` 当白名单用，空数组的渠道永远选不
中。每个模型还要能被这条渠道服务——两者对不上时 `create` / `update` 会被拒绝，
并说出「模型在目录里声明的端点」与「这条渠道打的端点」各是什么：配错时现场是
上游回 400，而那句话看不出是我们这边配的。目录里没有这个模型、或者那一项没配过
时不拦：目录是人工维护、会过时的一份声明，按「不支持」处理会让新接的上游一条
渠道都建不出来。

`--base-url` 只写到路径为止：带 query（`?`）或 fragment（`#`）的地址会被拒，
错误里点出是哪一段不合法。端点是拿地址与端点路径**拼**出来的，`?` 与 `#` 在拼接
处没有判据——`https://api.example.com/v1?tenant=abc` 会拼成
`https://api.example.com/v1?tenant=abc/v1/chat/completions`，路径落到了 query
后面，而拼接本身不报错。所以挡在写入侧。

`--setting` 是渠道私有配置（自由形态的 JSON 对象），键由该渠道 `type` 指向的
适配器解释，选路层不认，管理面也不校验键名。**今天有两个键有读者。**

`reasoning_effort_map` 由 `openai` 与 `openai-responses` 两个适配器读：
它把 `reasoning_effort` 的取值翻成该渠道认的写法（映射到空字符串表示把
这个字段从出站报文里去掉，表里没有的取值照原样发）。例如只认 `off` 的上游，
写成 `{"reasoning_effort_map":{"none":"off"}}`；要剔掉这个字段时，
写成 `{"reasoning_effort_map":{"none":""}}` 这一串。

`usage` 由 `openai`、`anthropic` 与 `openai-responses` 三个适配器读。
它的 `completion_includes_reasoning` 这一位决定上游报的输出 token 里含不含
推理：不写时按「含」算——OpenAI 的 `completion_tokens` 与 Anthropic 的 `output_tokens` 都这样；
只有把可见输出与推理分列报出的上游要显式写成 `{"usage":{"completion_includes_reasoning":false}}` 这一串。
不写的话，计费前减掉推理会让输出那一侧少收；推理比可见输出多时，整段输出
都收不到钱。两种口径靠数字分不出来，所以按渠道声明。

三个适配器都读它，但只有把推理分列报出的上游需要配：`anthropic` 渠道上
这一位没有数值效果——Claude 的用量不单列推理，`ReasoningTokens` 恒为 0，
两种取值算出的金额相同。

内层键名没有点名机制：`usage` 这一层拼错会被提示；内层那个键少一个 s 就等于没写，
它会静默按「含推理」处理，而这一位在钱路上。反过来，在本来就含推理的口径上
写 false，同一批推理会被收两次：输出整段按输出价算一次，推理那一项再加一次。

写进去的键这条渠道的 `type` 不认时（拼错的、别的 `type` 的），照样不报错、
不挡写入，但 `create`，以及给了 `--setting` 或 `--type` 的 `update`，成功之后
会逐个点名打到 stderr 上，`channel list` 也把这样的渠道点出来。

`--channel` 不存在、`--type` / `--base-url` / `--model` 也都不开简写：这条命令上
挑错的是「凭证写给哪条渠道」，而 `-c` 这类单字母在别的命令行里既可能是 `channel`
也可能是 `config`。

#### `model`

规范模型目录（catalog 基础定义）。

**规范名是选路与计费共用的键**：请求里的模型名按它匹配，别名与计价规则也挂在它
上面。所以它不能带空白字符，也不能改——要换名字就建新名、把别名与规则挪过去、
再删旧名。`update` 与 `delete` 都按 `--model` 定位，它本身不可改。

**六个能力标志各有三态**：不给 = 未知（库里是 `NULL`）、给 = 支持、
`--tools=false` = 明确声明不支持。三者在选路时处置不同：未知与支持放行，不支持
会让用到那一项的请求选不到这个模型。所以 `create` 时没给的开关落库是 `NULL` 而不
是 `false`——那是「还没配过」，不是「配了说不支持」。

判断一条记录配没配过，看 `list` / `get` 的那一栏：没配过的项在 `list` 里不列
（六项都没配过时打 `-`），`get` 里逐项打出「未知 / 支持 / 不支持」。

六个能力标志**成组**写入（写入路径对那六列是一次全量覆盖），所以给了其中任何
一个，命令会先读出当前那一行，再把这次给出的盖上去：只给 `--tools` 不会把另外
五个能力抹掉。

`delete` 只在**无人引用**时允许：还有别名或计价规则挂着这个规范名时它会被拒，
并报出各有多少条。别名要先删（渠道的 `models` 白名单里还留着这个名字，删别名不
等于删那条配置），计价规则要先改掉 `model_patterns`——直接删规则不会报错，只会让
请求落到别的规则上。那条错误原样打出来，不要绕过它去库里删。

`reasoning_options` 与 `raw` 是采集来的原始元信息，命令行不写它们，也不在 `get`
里打。

#### `alias`

模型别名映射（上游模型名 ↔ 规范名）。不带 `--channel` 的别名是**平台级**，对所有
渠道生效；带 `--channel` 的是渠道级，只对那个渠道生效，并盖过同一条平台级别名。
同一个规范名在每个范围里最多只能有一个上游名——两个上游名指向同一个规范名时，
选路无从取舍。

`--overrides` 是一组**上游请求参数**的覆盖，只允许三个键：`temperature`、
`top_p`、`max_tokens`。别的键在写入时就被拒绝——它们要么改的是请求的形状
（`model`、`messages`、`tools`、`stream`），要么根本不是这个请求的参数。与调用方
冲突时的口径：调用方**给了**的采样参数以调用方为准，没给的取覆盖值；`max_tokens`
反过来，一律以覆盖值为准。

`update` 按 `--id` 定位，**渠道范围与规范名都不可改**：改渠道范围是换了一条别名，
改规范名等于把这条别名改挂到另一个计费键上，而那样同一次请求的选路与计费会指向
两个不同的模型。要改就删掉重建，两次改动各自看得见。

`resolve` 走的是请求热路径上同一条查询，所以「渠道级别名盖过平台级那条」这件事在
这里看得见（`list` 只是把两种范围各列一遍，不回答谁赢）。

#### `price`

模型计价规则与日历管理。规则的作用域决定哪两栏 id 有效：`platform` 两栏都留空；
`merchant` 必须给 `--user`；`channel` 必须给 `--channel`。写了读取路径不看的那一
栏会被拒绝，因为那是一条「配了却不生效」的规则。

表达式在写入前会编译一次，编译不过的命令直接失败：一条编译不过的规则进了库，表现
是每个用到它的请求都失败，而失败点在请求路径上。

结构化定价表用 `--schedule-file` 给一份 JSON，与其他旗标一样在连库之前读完并校验。
`--expr` 与它**二选一**：写入时表会编译成表达式存进同一栏，`price list` 与求值用
的都是编译结果。

- `tz`：判定用的 IANA 时区名，必填。
- `base`：兜底单价。键与表达式相同（`prompt`、`completion`、`cache_read`、
  `cache_write`、`reasoning`、`fixed`、`minimum`），不能为空。
- `overrides`：覆盖项，每项是「条件 + 单价」。条件从这几个维度里选，一项里写多个
  维度表示「且」：`weekdays`（`mon` … `sun`，可写多个）、`window`
  （`HH:MM-HH:MM`，整点边界，可跨零点）、`day_kind`（`work` / `rest`）、
  `holidays`（节假日名，与 `holidayName()` 的返回值逐字比较，且不是补班日）、
  `min_context_tokens`（输入上下文 token 门槛，含缓存读写）。单价只写要改的
  键，没写的键沿用 `base`。

**同一维度上两条覆盖重叠会被拒**（门槛之间例外：门槛高的自动先命中，
不必给 `position`）。不同维度同时成立时用 `position` 裁决，大的优先；跨维度的
覆盖必须显式给 `position`。

`day_kind` 与 `holidays` 读日历数据：那一年没有导入、或当天查不到记录时求值失败，
不会退回某一档价（见 [calendar-data.md](calendar-data.md)）。

`price show <规则 ID>` 打一条规则的定价依据：带表的规则打那张表，手写规则的打表达
式。`-o json` 下两栏都给（`schedule` 与 `expr`），脚本可以核对两者一致。

带表的规则要改成手写表达式，必须同时给 `--clear-schedule`：库里存的是表编译出的那
条表达式，直接改它会让表与计价两份说法分家。`--clear-schedule` 只清表，表达式留在
原处；与 `--expr` 一起给就是换成一条手写规则，与 `--schedule-file` 互斥。

计价项一共五个：`prompt`、`completion`、`cache_read`、`cache_write`、
`reasoning`。上游报了哪一项，规则里就必须有哪一项的单价——少一项不是少收，是这次
请求整个失败（结算报「用量里有规则未定价的计量项」）。会报缓存的上游很常见，所以
新规则把这五项都写上、用不到的填 0，比漏掉再被拦住省事。

`list` 按**裁决次序**排列：适用于某次请求的第一条就是会被选中的那条。裁决次序是
作用域（`channel` > `merchant` > `platform`）→ `priority` 大的优先 → 模型名单非空
的优先于兜底 → id 大的优先。所以同作用域同优先级下，后加一条兜底不会盖掉已有的
模型专属价；要让兜底赢，把它的 `--priority` 调高。

`update` 校验的对象是**改完之后的那一行**，所以换作用域时要把该清的那一栏一起清
掉：改成 `platform` 用 `--user 0` 与 `--channel 0`，改成 `merchant` 要给
`--user`，改成 `channel` 要给 `--channel`。给空串的 `--user` 会被拒——那多半是一
个没展开的变量，而它读起来像「不挂商家」。

`create` 与 `update` 的 `--by` 必填，两栏记的不是同一件事：`pricing_rules.created_by`
是这条价是谁**定**的（只有 `create` 写它），`pricing_rule_versions.changed_by` 是
这一版是谁**改**的（只有 `update` 写它，而且只在表达式真的变了、留了一版时才有这一
行）。`update` 不动 `created_by`——定这条价的人在改价里可能根本没参与，把这个人当成
改动人写下来，审计会读到一个没做过这件事的人。`--by` 收 `users.id` 或用户名，落库记
的是那个 ID。它**不算**一次修改：`price update` 只给 `--by` 而没有别的字段时会报
「至少要改一项」。

**启停是独立的二级动词**（`price enable` / `price disable`），改属性的命令不带状态
开关：「顺便改个状态」与「启用这条规则」是两种意图，混在一个命令里时，那条
`update` 的最后一行日志说不清是哪一种。

`explain` 把**全部适用**的规则按裁决次序列出来，第一条就是会被选中的那条，排在它
后面的每一条都在说明「为什么不是它」。`--at` 用来问过去某一刻（对账时问「这一笔
当时按哪条算的」）。一条适用的都没有时非零退出，与请求路径上的处置一致（那是拒绝
服务，不是「按 0 元计」）。

日历数据文件的格式与约束见 `larkaxctl price calendar --help`。`--channel` 与
`--effective-to` 不开简写：`-c` 在别的命令行里既可能是 `channel` 也可能是
`config`、`count`，挑错作用域会把一条规则挂到另一个渠道上；`--effective-to` 是边界
参数，写短了容易看错。

#### `price calendar`

维护分时计价用的日历数据。这一组的数据是分时计价规则的输入，离开计价规则没有别的
用处。文件格式的完整说明在 `larkaxctl price calendar --help`（写在那里而不是只写在
这里：跑 `import` 时手边应当就能查到它）。

`pending`（公告尚未发布）、`conflict`、`degraded` 三种状态只记年份状态，不带
`days` 也不带 `source`——那一年还没有定论，写进去的数据行会被当成确定的判定使用。

`list` 列出导入过的年份：地区、年份、状态、天数、双源校验结果与写下的时刻，同地区
内按年份从新到旧。**没有导入过的年份不会出现**——它没有写 `calendar_years`，也就
没有「未导入」这一行可列；判定时这样的年份按未知处理。`status` 打的是库里那一列的
原文，同步失败的原因单独排在表后一行一条，公告原文地址只在 `-v` 下打。
`-o json` 下清单在 `calendars` 里，键名用库里的列名。
`sources_agree` 为 `null` 表示那一年没有第二个源可比。

旧路径 `larkaxctl calendar import <文件>` 仍然可用。`list` 只挂在 `price` 下面，
旧路径没有这一条。

#### `upstream-cost`

上游成本规则：一次调用**我们付给上游**多少钱。它与 `price` 是两条线——那边记的是
向用户收多少，这边记的是自己花多少。两条线各有一张规则表，谁也不会盖住谁：同一笔
请求既能匹配到一条售价规则、也能匹配到一条成本规则，两边各挑各的。

这张表在结算时被读取：每完成一次调用，结算按（渠道，规范模型）挑一条成本规则，
用这次的实际用量算出 `usage_events.upstream_cost`，渠道健康度的成本那一列再从
那里按小时桶汇总。所以停用或修改一条规则，从下一次结算起就会改变成本那一列的
算术结果；它不影响售价（那是 `price` 那一侧的事），也不拒绝请求——没有生效的
规则时这一列留 NULL，选路里成本这一维不参与打分。

一条规则绑在**一条渠道**上，可以再收窄到几个模型。参数与列的对应：

- `--channel` → `channel_id`：必填，外键到 `channels.id`。
- `--models` → `model_patterns`：规范模型名，逗号分隔。留空表示适用于全部模型，
  这样的规则是这条渠道上的兜底规则。
- `--expr` → `expr`：表达式，与 `price` 同一套语法，写入前编译一次。
- `--priority` → `priority`：默认 0。
- `--effective-from` → `effective_from`：默认「此刻」。
- `--effective-to` → `effective_to`：不给表示不过期。

模型名按**元素逐字匹配**，不支持通配符（写 `*` 会被拒）。表达式的计价项与 `price`
是同一批（`prompt`、`completion`、`cache_read`、`cache_write`、`reasoning`）。一项
单价都不写的表达式**会被接受**（`list` 在那一栏打「（一项都没有）」），但结算时它
覆盖不了这次用量的计价项，`billing.ValidateCharges` 会拒，那一笔成本留 NULL 并记
一条告警——不会算成 0。

**挑哪条规则**：在适用于这条渠道这个模型这一刻的规则里按裁决次序取第一条——
`priority` 大的优先 → 模型名单非空的优先于兜底 → id 大的优先。这里没有 `price` 的
作用域那一层：成本规则只有渠道这一维，所以同一条渠道内部比。时间窗口与模型名单两条
判据与售价那一侧共用同一段：`effective_from <= 此刻 < effective_to`（左闭右开，
开始时点那一瞬间算，结束时点那一瞬间不算），`model_patterns` 为空即适用于全部模型。

`list` 有三档：不带筛选时列全库的规则，`--channel` 列这条渠道的全部规则（含已经过期
与还没生效的），再带 `--model` 时**只列适用的规则**，并多一栏「裁决」——标出这一刻
选中的是哪条、其余每条为什么不是它（不适用的那些根本不出现在这张表里）。`--at` 把
「这一刻」换成指定的时刻，用来回答「当时按哪条算的」；不给 `--model` 而给 `--at`
会被拒，`--model` 也要配 `--channel` 一起给。

一条都不适用时打「没有适用的成本规则。」并**正常退出**，这与 `price explain` 不同：
那一边没有可用规则是拒绝服务，这一边的结论只是「这条渠道这个模型没有成本规则」。
`-o json` 下清单在 `costs` 里，另有 `query`（这一次问的是哪条渠道哪个模型哪一刻）与
`summary.total`；每行的 `verdict` 是 `selected` / `shadowed`，没给 `--model` 时是
`null`。

`update` 只改给出的那几项，校验的是**改完之后的那一行**，所以窗口要缩、要挪都写得
出来。`--clear-effective-to` 把上界清回「不过期」（它与 `--effective-to` 互斥）；
`--channel` 既不能清空也不能给一个不存在的渠道。

`disable` 把上界收到此刻：`upstream_costs` 上没有单独的启停列，一条规则「从现在起
不再适用」就是它的窗口到此为止。两种形状会被拒——还没生效的（把上界收到此刻会把生效
区间收成空）与已经失效的（那等于让它从此刻起重新生效，与停用正好相反）。要看一条规则
现在是什么样，用 `upstream-cost list`。

`upstream_costs` 上没有记「谁建的、谁改的」那几列，所以这条命令没有 `--by`。

### 权限与财务 (Access & Ledger)

#### `user`

系统用户管理（创建、查询、修改与销户）。`create` 只把新用户的 ID 打到 stdout。

角色取 `user`、`merchant`、`admin` 之一，默认 `user`。三者都是用户，
`merchant` 与 `admin` 只是 `users` 表上的标记（`admin` 同时也是 `merchant`）。
**角色今天只是记下来，不改任何一处行为**：读那两个标记的只有展示与筛选
（`list` 的角色栏与 `--role`），没有任何鉴权判断读它们，所以
`--role merchant` 不会让这个用户多出什么权限，`--role admin` 也不代表他能进管理
接口（管理面还没做）。它们留给管理面的鉴权用，接上之前别把它当成一条访问控制。

**不做幂等**：用户名已被占用时直接报错，不会改到已有的那个用户。

用户名的形状有两条限制，都在 `create` 上当场判、报参数错并退出 2。

**一、整串是一个十进制整数的名字建不出来**（`--name 123`、`--name 007` 都是，
带一个正负号的 `+7` 也算；`1a`、`a1`、`1.0`、`1e3` 不是）。`--user` 把这样一个
名字按 ID 解释（见下面 `get` 的标识规则），于是它建出来之后按名字读不回来——
`user get` 与 `user update` 都够不着它，只能改库。名字里带一个非数字字符就能避开。

**二、名字里不能有控制字符**（C0 与 DEL，换行、制表符、ESC 都在其中）。
这一类名字进了库之后，凡是要打它的地方都会破：清单与写命令的回显按
「一条记录一行、一个字段一栏」排版，换行折出一条没有栏名的续行，
ESC 序列则原样进执行者的终端。它进账本分录的备注时还会被清洗一次，
不过清洗只认 `\r`、`\n`、`\t`（换成空格），ESC 这类原样留在备注里——
于是带这三个字符的名字，回显里写的与库里记的不是同一个串。报错点名是哪一个字符。
**这一条不是字符白名单**：点、连字符、空格、中文都照收。两头的空白先去掉再判，
与落库的值一致——`--name $'\ta\t'` 存进去的是 `a`。

邮箱的写法也判，收的是**地址本身**那一种，五条：`@` 恰好一个、两边都不为空；
本地部分只由字母、数字与一组常见符号组成（`+`、`_`、`-`、`'`、`!` 这些，完整的
那一组写在报错里），域名只由字母、数字、连字符与点组成；域名里有一个点；两半都
不以点开头或结尾，也不出现连着两个点；域名里用点分开的每一段，都不以连字符开头
或结尾。

`user+tag@example.com`、`first.last@example.com`、`a@b.example.com` 都收；
`not-an-email`、`first@second@example.com`、`a b@example.com`、`a@example.com.`、
`a@example`（域名没有点）、`a@-b.example.com` 都报参数错并退出 2。
带显示名、注释或引号的写法（`Bob <bob@example.com>`、`bob@example.com (comment)`）
也报错——这一列存的是地址本身，不是一个信封上的收件人栏，而同一个人的另一种写法
存进去会被当成第二个邮箱（这一列上有唯一约束）。

**非 ASCII 的字母与数字也收**（全角的 `Ａ`、西里尔文的同形字这些都算），而这一列
的大小写不敏感只覆盖 ASCII：`Ａ` 与 `A`、西里尔 `а` 与拉丁 `a` 是**两个不同的
值**，唯一约束分得开，会并存成两条。长度不设上限（标准里本地部分到 64、整串到
254）：300 字的本地部分照收，这是这一版有意留的边界。

**空邮箱不是格式错**：`create` 的 `--email` 给空串是不填这一列（库里是 `NULL`），
`update` 的 `--email` 给空串是把它清回 `NULL`（见下面 `update`）。

`list` 按 id 从小到大列出用户，一栏一个字段：ID、用户名、状态、角色、邮箱。
`--status` 取 `active`、`suspended`、`banned` 之一，`--role` 取三个角色之一，
两个都可以给、也都可以不给（不给就是列全部）。`--role` 按**称呼**逐字匹配，
与 `create` 写进去的那一个对应：`--role merchant` 列出的是称呼为 `merchant`
的用户，`--role admin` 列的是 `admin`。取值不认识时报参数错并退出 2，不回落成
「不筛」。

**状态有三档经 `update` 改**：`suspended` 与 `banned` 都会让他手里的 key 全部失效
（见 `internal/auth` 的鉴权判据），把它写回去走 `user update --status`——在库里
直接改也一样生效，但那样既没有取值校验也没有回显，事后说不清是谁改的。
另外两档（`deletion_requested` 与 `deleted`）只能经下面 `delete` 那一族进入与
离开，`update --status` 不收它们：`deleted` 是匿名化之后的终态，从 `update`
直接写进去会跳过清身份与作废 key 的步骤。

反过来，这两档也不收 `update` 的**状态**改动：已经 `deleted` 的账号不收任何
`update`（改邮箱、展示名会被拒并退出 4），否则占位身份就有一条命令能写回真
身份；停在 `deletion_requested` 的账号不能用 `--status` 改走，报错指向
`delete revert`——那条路会一起清掉 `deletion_prior_status`，从 `update` 直接写
`active` 则会把旧值留在那一列上。

`get` 按 ID 或用户名读一个用户的全部字段：除清单那五栏，还有展示名、删除时间、
创建时间与更新时间。标识怎么解释与别的命令一致：纯数字按 ID，否则按用户名。
找不到时退出 4。
所以纯数字的用户名按名字读不出来，`create` 不让这样的名字进库（见上面），而库里
已经有的那些不动。

`update` 只改**显式给出**的字段，一个都没给就报参数错并退出 2（不做静默空操作）。
每一条旗标说的都是它自己那一列变成什么：`--status` 取三个状态之一；`--email` 与
`--display-name` 给空串表示把这一列清回 `NULL`（不是写成一个空串，`--email` 的新值
还要过上面那条格式校验）；`--merchant`
与 `--no-merchant` 把 `is_merchant` 置真 / 置假（`--no-merchant` 不能单独打在
`admin` 上，见下）；`--admin` 把 `is_admin` 置真**并且**把 `is_merchant` 一起置真
（`admin` 天然也是 `merchant`，与 `create --role admin` 落的是同一种数据），
`--no-admin` 只把 `is_admin` 置假、`merchant` 不动。
两个文本列的取值两头空白会被去掉（`create` 的 `--email` 同一口径），去掉之后是空串
就清回 `NULL`；`--status` 也是先去两头空白再比对，但空串仍然不认。

`--display-name` 与用户名同一条控制字符判据：换行、制表符、ESC 这些会让
「一条记录一行、一个字段一栏」的排版破掉，当场报参数错并退出 2，报错点名是哪一个
字符。去掉两头空白之后仍是空串的照收——那是「清掉这一列」。

所以下面三组是互相打架的输入，**当场报参数错、不挑一个落库**：`--merchant` 与
`--no-merchant`、`--admin` 与 `--no-admin`、`--admin` 与 `--no-merchant`。

还有一条挡的是改完**那一行**而不是输入本身：`--no-merchant` 打在 `admin` 上同样
当场报参数错。它只把 `is_merchant` 置假，留下的那一行**读出来仍然是 `admin`**
（这一档按 `is_admin` 读，见上），于是回显里角色那一栏没变、屏幕上只剩首行，看起来
像什么都没做。出路有两条，一条命令都不必分两次发：先 `--no-admin`（`is_admin` 置假、
`merchant` 不动），或者 `--no-admin --no-merchant` 一起给，一步落到普通用户。

改完把**真的变了**的字段按「旧值 → 新值」逐行打到 stdout，首行是「已改用户
<用户名>」。两栏都是库里的值：旧值取自改之前读的那一行，新值取自那条 `UPDATE`
的 `RETURNING`。给出的旗标没带来变化时（例如对本来就是 `merchant` 的用户再
`--merchant`）那一行不出现，所以打出来的行与这次的改动是同一件事。用户不存在时
退出 4；邮箱撞上别的用户时报「邮箱已被占用」并带上那个值，也退出 4。

`password` 设或重置控制台口令。用户标识既可以用 `--user`，也可以直接写成一个
位置参数；两种混用当场报参数错并退出 2。

口令只有两条来路，必须给且只给一个：`--generate` 由本命令生成一个随机口令，
长度 24 个 base64url 字符；`--stdin` 从标准输入读。**不接受把口令写成命令行
参数**：参数会进 shell 历史，而同一个进程的参数在 `/proc` 里对同机的其他用户
可读。`--stdin` 会去掉行尾的换行（`\n` 与 CRLF 都去），口令开头与中间的空白
原样保留；标准输入是空的、或超过 4096 字节时报参数错并退出 2。

stdout 恰好一行，就是新口令，只显示这一次；其余说明走 stderr。口令策略与登录
侧同一份判据：12–128 个字符、不能等于用户名、不能有控制字符。设置成功后这个
用户的**全部**控制台会话立即吊销——运维重置的场景是「不知道谁还开着控制台」，
留下任何一个旧会话都让这次重置只对下一次登录生效，所以没有「保留当前会话」
这一档。

`unlock` 清掉一个账号的失败计数与锁定（连续失败 5 次后开始锁定，按失败次数
指数增长，上限 15 分钟）。它只把「现在能不能试」恢复成默认，不动口令、不动
会话：解锁不会让一个已经失效的会话重新可用，也不会改掉任何人的凭证。

`create --generate-password` 在建号的同时设一个随机初始口令：stdout 那一行
因此是**口令**而不是用户 ID，ID 与用户名走 stderr。要接走 ID 的脚本不要带
这个旗标。

`delete` 这一族把账号从「要求删除」走到终态，分两步，中间可以撤回。想点出
谁被删过时看 `status` 与 `deleted_at`：行基本不删，唯一的例外是用户态插件 KV
（`plugin_kv` 里属于这个用户的行随匿名化删掉）。

`delete request` 打标（可撤）：把账号置为 `deletion_requested`，并记下它原来的
状态。从这个时刻起，用户手里的 API Key 全部失效——鉴权只认 `status = active`，
打标之后这些 key 在任何一条路上都过不去。key 一行都不改，所以 `delete revert` 之后
原本有效的 key 恢复有效（此前停用的仍然是停用）。

打标之前先看钱包：**余额与冻结额都必须是 0**。不是 0 时报「可用余额必须为 0」
并给出当前的两个数，退出 4。冻结额也在判据里，因为它是还没结算的请求预扣住的那部分，匿名化之后
它们仍会结算。下一步是先用 `wallet adjust` 调账，或等退款与还没结算完的请求
处理完。

打标与匿名化还各有一道判据：**不能因此让平台失去最后一个能进管理组的账号**。
`delete request` 打在仍为 `active` 的管理员上、`delete purge` 打在
打标之前是 `active`、且此刻仍挂着管理员的行上时，都会在同一个事务里数一遍
撤掉这一行之后还剩不剩 `active` 管理员，一个不剩就拒绝，退出 4。错误文案会
点出是哪个账号，动作指引是「先给另一个账号 admin 角色再销户」。
`delete revert` 不判：唯一管理员要能把自己从待删除拉回来。

`delete revert` 撤掉打标：状态回到 request 之前的那一个——原来 `active` 就回
`active`，原来 `suspended` 就回 `suspended`，不会被顺手放回 `active`。key 仍然
一行都不动。

`delete purge` 匿名化（不可逆）：只接已经处于 `deletion_requested` 的账号，并且
要 `--confirm` 逐字写出当前用户名。没有 `--confirm`、写错、或者账号还没打标时
什么都不写。它在**一个事务里**做这几件事：

- `api_keys` 里状态还是 `active` 的全部置为 `revoked`，行保留；此前已经
  `disabled` 的保留原来的状态（「之前停用过」也是一条要留下的记录）。
- `plugin_kv` 里属于这个用户的键全部删除（按插件与用户隔离的那一份）。
- `capture_consents` 里还没撤销的授权全部撤销（写 `revoked_at`），行保留；到期
  仍按各自的 `expires_at`，早已撤销的那一条不会被改写时刻。
- `users` 行置为 `deleted`、写下 `deleted_at`，并把用户名、邮箱、展示名换成
  不可逆的占位：`deleted-user-<ID>`、`deleted-user-<ID>@example.com`、
  `已注销用户 #<ID>`。占位用户名已被别人占用时按 `-2`、`-3` 往后找。
- 钱包行与账本分录**不动**：财务记录不随账号删除清除（见
  [request-retention.md](request-retention.md)）。
- 请求快照**不动**：它们按各自的留存期由 `snapshot cleanup` 删除。

匿名化之后原来的用户名就查不到了（那一行已经换成占位值），要再看它得用
`user get --user <ID>`，或者按占位用户名 `deleted-user-<ID>` 找。

余额与冻结额在 `purge` 时再判一次：打标之后仍可能有退款或调账进来，而匿名化
之后就没有账号去收这笔钱了。

**哪些一致性在库层、哪些只在应用层。** 库上有两条 CHECK 钉住状态与列的配套：
`status = deleted` 必有 `deleted_at`，`status = deletion_requested` 必有
`deletion_prior_status`。剩下的几件——终态账号的 API Key 已作废、插件 KV 已清、
采集授权已撤销——**没有触发器**，只由 `purge` 的同一个事务保证；绕过 `purge`
直接 `UPDATE users` 不会连带动那几张表。

`create` / `list` / `get` / `update` 只碰 `users` 表（不碰渠道凭证）；`delete`
那一族会写到 `api_keys`、`plugin_kv` 与 `capture_consents`，钱包只读加锁。
除了 `plugin_kv` 里属于这个用户的行，别的行都不删。它们都不需要
`LARKAX_MASTER_KEYS`。

**用户级履约操作也挂在 `user` 下**：`user plan`、`user wallet`、`user key`、
`user usage`。核心宾语——哪个用户、哪个套餐——写成**位置参数**，修饰项（`--ref`、
`--expires-at`、`--amount`）仍然是旗标。

- `user plan`：`grant` / `list` / `void` / `order`——该用户持有的订阅与扣费顺序。
- `user wallet`：`show` / `credit` / `adjust` / `refund`——该用户的钱包。
- `user key`：`list` / `create` / `plans`——该用户的 API Key，以及一把 Key 能用哪些订阅。
- `user usage`：`events` / `requests`——该用户的用量与计费。

四条子组的语义与各自的旗标跟对应的顶层命令**逐字相同**，区别只在宾语的位置：

| 新路径 | 旧写法（仍可用） |
|---|---|
| `user plan grant <用户> <套餐> --ref … --expires-at …` | `plan grant --user <用户> --plan <套餐> …` |
| `user plan list <用户>` | `plan subscriptions --user <用户>` |
| `user plan void <订阅 ID> --ref …` | `plan void --id <订阅 ID> …` |
| `user plan order show <用户>` / `user plan order set <用户> …` | `plan order show --user <用户>` / `plan order set --user <用户> …` |
| `user key plans show <API Key ID>` / `user key plans set <API Key ID> …` | `plan key show --id <API Key ID>` / `plan key set --id <API Key ID> …` |
| `user wallet show <用户>` | `wallet list --user <用户>` |
| `user wallet credit <用户> …` / `adjust` / `refund` | `wallet credit --user <用户> …` / `adjust` / `refund` |
| `user key create <用户> …` / `user key list <用户>` | `apikey create --user <用户> …`、`apikey list --user <用户>` |
| `user usage events <用户> …` / `requests` | `usage events --user <用户> …` / `requests` |

旧写法**至少保留一个发布周期**，命中时在 stderr 打一行指向新路径（`提示：…`，
`-q` 之下跟着压掉，`--format json` 的 stdout 不受影响）。这行提示与这一次跑成
没跑成无关：参数写得出来就提示——**失败时更要说**，「Key 不存在」只说明数据不在，
而人手上那条命令可能早该换了。唯一的例外是参数错（退出码 2）：那时 stderr 上已经
是一屏用法，再补一句搬家提示只会把「先把参数写对」挤到后面。不带 `--user` 的
`wallet list` / `apikey list` / `usage events|requests` 回答的是全量，没有对应的
新路径，因此不提示。

新路径**不新增业务能力**：`user plan grant` 与 `plan grant` 走的是同一段代码，
幂等键、退出码与两种输出契约都一样。`plan` 剩下的只有商品定义（`create` /
`list` / `get` / `enable` / `disable`）；开通钱包（`wallet create`）、商户提现
（`wallet payout`）与支付通道（`wallet payment`）不在这一组里，仍在 `wallet` 下。

#### `apikey`

API Key 访问密钥、状态与额度管理。这四个子命令都不需要 `LARKAX_MASTER_KEYS`：它们不碰
渠道凭证，也就不碰信封加密（主密钥是 `secret rotate`、`channel` 的写入与 `plugin` 的
`delete` / `kv set` / `kv delete` 那三条的事）。

**明文只打印这一次**：库里存的是 SHA-256 哈希，它不可逆，丢了没有任何办法取回，
只能重建一把。所以明文单独打到 stdout，其余信息打到 stderr——`larkaxctl apikey
create --user alice > key.txt` 保存下来的文件里只有明文，不会混进前缀、id 与提示语。

`get --id <ID>` 打一把 key 的现状：状态、备注、两列额度，以及创建、过期、最近使用三个
时刻。它读的是 `list` 那一行的同一份数据，只是收成一把，所以 `list` 里打成「继承」
「不过期」「从未」的那四处（每分钟与额度都是「继承」）在这里是同样的四个词。

两列额度都按**明文**给，不填表示 `NULL`：`--rpm` 是每分钟请求额度，**0 不是
「不限」，是「一个都不放行」**；`--quota` 是这把 key 累计可花费的金额上限，单位是
该用户钱包的资产品种（见 `user_wallets.asset`）。不填（或 `update` 时给
`--clear-rpm` / `--clear-quota`）写回 `NULL`，即「继承用户默认」——`users` 表上目前
没有这样一个默认值，所以它等价于不限。

负数一律拒绝：限流那一侧把负数也当成「一个都不放行」，而写下 `-60` 的人几乎总是
想写 `60`。让他当场改掉，比让它变成一个静默的封禁好。

`update` 一次可以改多项，只改命令行上**真的给出**的那几项，一项都没给时报参数错（一条
什么都没改的命令与一条改成功的命令在屏幕上一模一样）。改完把改了哪几项、各从什么变成
什么打到 stderr。

`--status` 取 `active`、`disabled`、`revoked` 之一。`disabled` 与 `revoked` 在鉴权那
一侧都会被拒，区别只记在**拒绝的原因**上（观测里分别计数），所以选哪一个取决于你想在
那份计数里看到什么。一把停用的 key 可以用 `--status active` 恢复。

`--expires-at` 给一个 RFC3339 时刻，到点之后这把 key 自动不可用；`--clear-expires-at`
写回「不过期」。已经过去的时刻会被拒绝：要立刻停掉一把 key 就改 `--status`，那样鉴权
记下的原因是「被停用」，而设一个已经过去的过期时刻记下的是「已过期」——两种情形要分的
是下一步该找谁。`--name` 给空串表示「没有备注」，与 `create` 不给 `--name` 是同一个
意思（列是 `NOT NULL`，空串就是它的「没有」）。备注会进 `list` / `get` 的「备注」那
一栏，所以换行、制表符、ESC 这些控制字符当场报参数错并退出 2，报错点名是哪一个字符。

两个额度**不开简写**：它们是限额，写短了容易看错也容易按错。`apikey` 下唯一的简写
是 `-u`（`--user` 的别名，`create` 与 `list` 认它）。

旧名 `--rate-limit-rpm` 等同于 `--rpm`，`--clear-rate-limit-rpm` 等同于 `--clear-rpm`；
`--quota-limit` 等同于 `--quota`，`--clear-quota-limit` 等同于 `--clear-quota`。

#### `wallet`

用户钱包账户与入账管理。`create`、`credit`、`adjust` 与 `refund` 都只写
`user_wallets` 与 `ledger_entries`，不碰 `users`，也不需要 `LARKAX_MASTER_KEYS`；
`payout` 那一族写 `payout_requests` 与 `ledger_entries`，`payment` 那一族写
`payment_orders` 与 `ledger_entries`（各自见它那一节）。

`create` 给一个已存在的用户开通钱包，余额为 0。它不写任何分录：新开的户在账本上
没有分录，这个用户在 `user` 科目上的分录之和为 0，与快照里的 0 自洽。带初始金额
意味着这次开户同时是一次充值，而那属于充值入口——用 `credit`。**幂等**：钱包已经
存在时什么都不做、照样退出 0，两种结果都只能靠输出的那一行分辨（逐字是「已为用户
… 开通 … 钱包，余额 0。」与「用户 … 已有 … 钱包，未改动。」），脚本匹配「开通」与
「未改动」这两个词。

`credit` 是运营手工入账：走账本写一组 `topup` 分录（借 `user:<ID>`、贷
`payment_gateway:<来源>`），并在同一个事务里更新 `user_wallets.balance`。它不绕过
账本直接改余额——那样会让钱包快照与分录对不上，下一轮对账会报。

`--ref` 是这笔入账对应的**外部单据号**（银行流水号、支付通道的单号），它同时是幂等
键，**必填且没有默认值**：它被确定性地映射成这次交易的 `txn_id`，于是同一条命令重
跑两次只会入账一次。同一个 `--ref` 配不同的金额、用户或通道不是重放，而是冲突：
数据库里那笔交易与这次要写的不是同一批分录，命令退出 4，一笔都不写。键里不能有控制
字符（换行、制表符等）——它既算交易号又进备注，而备注会把控制字符换成空格。

`--gateway` 是这笔钱从哪个外部来源进来（记进 `payment_gateway:<来源>` 科目），默认
`manual`，表示线下到账。来源名归一成小写。`credit` 的来源是操作者说的，不是系统
验证过的；通道通知那条路走 `wallet payment`，金额以通道发回来的为准。钱包必须已经
存在：先 `create`，再 `credit`。

`adjust` 是运营手工调账：走账本写一组 `adjustment` 分录，被调科目是 `user:<ID>`、
对家是 `platform_revenue`，并在同一个事务里更新 `user_wallets.balance`。修出来的
是一笔**有科目、有原因、有单据号的账本分录**，而不是直接改快照——直接改快照不产生
分录，账本与快照从此对不上，下一轮对账会报差额，报了也查不出出处。

`--amount` **带符号**：负数是「把记多的钱扣回来」，不是写错了。被调的科目与对家都
不由旗标指定：前者固定是 `user:<ID>`，后者固定是 `platform_revenue`（调账的实质
是平台认下这笔差额）。它只调余额，不碰冻结额：冻结额不在账本里，调它产生不了
分录；也不接 `--asset`，品种随 `billing.default_asset` 走。

`--memo` 与 `--by` 都必填。`--memo` 里不能有控制字符（换行、制表符之类就算）：回显
打的是原样的原因，而库里那一份会把它们换成空格，两边因此不是同一个串。`--by` 收
用户 ID 或用户名，先解析成一个真实存在的用户，再把用户名与单据号跟在原因后面写进
分录的备注，逐字是「<原因>（操作人 <用户名>，单据 <ref>）」——账本里没有记操作人的
列，谁调的只能落在这里。它只是记名：这条命令与
`credit` 是同一条面，没有额外的角色校验。单据号进备注有它自己的理由：交易号是它的
哈希，从单据号算得到交易号，反过来算不回来。操作人与单据号那一段是**固定后缀、锚在
串尾**：原因里可以出现同样形状的括号，按这个格式反解单号时要从末尾往前认这一段。

`--ref` 与 `credit` 的那一个同义（外部单据号 + 幂等键），但**两条命令的键互不相认**：
同一个单据号在调账与入账上是两笔互不相干的交易。同一个 `--ref` 配不同的金额、用户、
原因或操作人不是重放，而是冲突：命令退出 4，一笔都不写。

结果余额会变成负数时拒绝，一笔都不写：`user_wallets.balance` 上有 CHECK 约束
（`balance >= 0`），而负的用户余额说明某处少扣了钱，它应当被拦住而不是记成负数。
报告里那一对「余额 从多少 到多少」取自分录现算的**权威值**，不是 `user_wallets` 里
那个快照：它与 `ledger balance --account user:<ID>` 是同一个数，两者不一致时以账本
为准。

资产默认取 `settings` 的 `billing.default_asset`（迁移里的默认值是 CNY）。它是钱包
主键的一部分，所以同一个用户可以同时有 CNY 与其他资产的钱包；能用 `--asset` 的命令
是 `create`、`credit`、`refund`、`payout request` 与 `payment create`（`payout` 的
其余三条动的是已经建好那一条单子的品种），当前只有 CNY 一种受支持的资产。用户一律用
`--user` 指定（`create`、`credit`、`adjust`、`refund`、`payout request`、
`payment create`、`list` 认它）：纯数字按 ID 解析，否则按用户名解析。

`list` 是只读的那一条（也不需要 `LARKAX_MASTER_KEYS`），列出用户 ID、用户名、
资产、余额与冻结额。不带 `--user` 时列出全部钱包，带的时候只列那一个用户。
用户不存在时报「找不到用户」并退出 4；用户存在但还没有钱包行时，输出的是一句
明确的空清单提示而不是空表头。筛用户时 `-u` 与 `--user` 等价。

余额与冻结额那两格**可能读不出来**：库里那两列是 `numeric(20, 8)`，能装下的数比命令
能表示的范围大，所以可以存在一个这两列装得下、而命令表示不了的数。这时那一格在表格里
打「不可读（超出可表示范围）」，**其余行照打**，命令退出 1，并且在 stderr 上说清是哪一
个用户的哪一格、库里的原文是什么。不带 `--user` 的那一屏因此不会因为一行坏数据整个消失
——但它不是一次成功的调用，退出码非零。带上 `--user` 时反过来：窄查询问的就是那一格的
值，读不出来就是没答上来，一个字都不打、退出 1。

机器可读那一档里，读不出来的那一格是 `null`，而同一行还有一个 `unreadable` 写出它是哪
一栏：单看 `null` 分不出「这一栏没有值」与「值读不出来」两件事，而钱包那两栏是非空列，
把话写明之后，读的一方不必知道那条列约束才判得出。`summary` 的 `unreadable_rows` 数的
是**行**：一行两格都读不出来只算一行，所以它可能小于 `unreadable` 列出的栏数。

那一行的余额取自 `user_wallets.balance`，是**快照值**；从分录现算的权威值由
`ledger balance --account user:<ID>` 给，两者是否一致由 `reconcile` 比对。
冻结额是为在飞的请求预扣住的那部分，它**不包含**在余额里。机器可读那一档
（`--format json`）把两个金额打成定点小数字符串，用户 ID 打成数字。

旧名 `wallet open` 等同于 `wallet create`；`credit` 上 `--idempotency-key` 与
`--order` 都等同于 `--ref`（`adjust` 没有旧名）。`-u` 是 `--user` 的简写，
`create`、`credit`、`adjust`、`refund`、`list`、`payout request` 与
`payment create` 认它。

#### `wallet refund`

把用户已经付过的钱退回去。走账本写一组 `refund` 分录（借 `user:<ID>`，其余几笔是
贷方），并在同一个事务里更新 `user_wallets.balance`：快照与分录一起动，不做那种只改
快照的退款——那样账本与快照从此对不上，下一轮对账会报差额，报了也查不出出处。用户
必须已经开过户（先跑 `wallet create`）：余额要跟着动，没有那一行时命令退出 4。

对家按旗标给的那几项拆，`--amount` 先减去分成与上游成本，剩下的差额进平台收入：

| 旗标 | 贷方科目 |
|---|---|
| `--merchant <商户>` + `--merchant-share <金额>` | `merchant_payable:<商户>` |
| `--upstream-cost <金额>` | `upstream_cost` |
| 上面两项之后的差额（也可能就是全部） | `platform_revenue` |

差额为零时那一笔不写；原本没分账的消费，`--merchant` 与 `--upstream-cost` 都留空。

`--merchant` 与 `--merchant-share` **必须一起给**：只给商户是一次静默丢弃——操作者
以为冲回了那个商户的分成，而账面上一分钱都没落到他身上；只给金额则说不清记在谁
名下。两项之和超过 `--amount` 时退出 2（参数错），连库都不连。

`--amount ≤ 原始消费` 这条上界**不由命令校验**：命令看不到那次消费的金额（`--ref`
是外部单据号，不是本库里某一条计费请求的外键）。越过它的退款在账面上仍然平——它就
是一笔多退的钱——所以只能靠人拿单据核对。

`--ref` 是这笔退款对应的外部单据号，与 `credit` 的那一个同义（必填、是幂等键、键里
不能有控制字符），但**两条命令的键互不相认**：同一个单据号在退款与入账上是两笔互不
相干的交易。同一个 `--ref` 配不同的金额、用户或分账不是重放，而是冲突：命令退出 4，
一笔都不写，报错里带着这把键推出来的交易号。

它同时**进分录备注**，逐字是「退款：<原因>（单据 <ref>）」，没给 `--memo` 时是
「退款（单据 <ref>）」：交易号是单据号的哈希，从单据号算得到交易号，反过来算不回来，
不落备注就没有第二条路把这张退款单对上这笔账。

重跑同一条命令时回显逐字是「幂等键 <ref> 已经退过款，本次未改动。交易 <txn_id>。」
随后列出此前写入的分录；第一次成功时那一行是「已退款给用户 <用户名>：<金额> <资产>，
幂等键 <ref>，交易 <txn_id>。」，`--memo` 的内容另起一行打「原因：…」。

#### `wallet payout`

商户提现的动作：`request` 由商户申请并把待付冻住、`settle` 由平台主动清算（一步建单
并记账，单子直接落 `approved`）、`approve` 批准、`reject` 驳回并解除冻结、`paid` 打款。
状态怎么走：

| 现在的状态 | 动作 | 之后 |
|---|---|---|
| `pending` | `approve` | `approved` |
| `pending` | `reject` | `rejected`（同时解除冻结） |
| `approved` | `paid` | `paid` |
| `rejected` / `paid` | 别的动作 | 拒绝，退出 4 |

`settle` 不在这张表里：它不是把一条已有的单子往前推，而是建一条**直接是 `approved`**
的单子，所以之后照旧用 `paid` 收尾。

**`paid` 只放行 `approved`**：这是唯一一个把钱付出去的入口，别的路径都到不了它。给
一张 `pending` 或 `rejected` 的单子打款，命令退出 4，报错同时点出它现在是什么状态、
这一步要什么状态，并且**一笔分录都不写**。`rejected` 与 `paid` 是终态。

申请那一步就把钱冻住：贷 `merchant_payable:<商户>`、借 `payout:<单id>`，钱从「他还能
申请的分成」挪进「这条单子的待付」。`settle` 的账面形状相同，只是分录类型是 `settle`
而不是 `payout_request`，对账时「平台清算的」与「商户申请的」因此分得开。批准**不写
分录**——这一步没有钱动，落库的只有审批人与时刻。驳回写的是申请那一笔的镜像（借
`merchant_payable:<商户>`、贷 `payout:<单id>`），冻结随之解除。打款写的是出账那一组
（贷 `payout:<单id>`、借 `payment_gateway:<通道>`），钱从待付出账。

单子与它那一组分录在**同一个事务**里写：任何一步中断，留下的都是一个完整的状态——
不会出现「单子建好了、钱没冻上」或者「钱冻着、没有单子说明是谁申请的」。

各条动作的旗标：

| 动作 | 旗标 |
|---|---|
| `request` | `--user`（商户）、`--amount`、`--ref`（申请单号）、`[--asset]`、`[--destination <收款信息 JSON>]` |
| `settle` | `--user`（商户）、`--amount`、`--ref`（结算单号）、`--destination <收款信息 JSON>`、`--by`（操作人）、`[--note]` |
| `approve` / `reject` | `--id`（提现单 ID）、`--by`（操作人）、`[--note]` |
| `paid` | `--id`、`--gateway`、`[--gateway-ref]`（通道给的凭据号） |

`--destination` 是商户的收款信息，**必须是一个 JSON 对象**（形如 `{"bank":"…"}`），
落进 `destination` 那一列（jsonb）。`request` 不给就是空对象；`settle` 那一档**必填**
——平台已经决定付了，付到哪里必须当场说清。字符串、数组与 `null` 都在连库之前按参数
错拒掉（退出 2）：那一列是 jsonb，而打款通道要按字段取值，一个不是对象的 JSON 取不出
任何字段。命令不解释它的内容，要哪些字段是通道那一侧的事。

收款信息**事后不能改**：这一族没有修改命令。所以同一个单号配同一份收款信息是重放，
配了另一份不是重放而是冲突（退出 4），一笔都不写——否则重跑一条旧命令会把那张单子的
收款账号悄悄换掉。要换收款方式只能驳回后重新申请。比较按 jsonb 的等值口径，键的顺序
与空白不影响判定。

`settle` 建出来的单子没有驳回那条路，建出来就一直停在 `approved`，也没有撤销命令。
**不要再对它 `paid`**：`paid --id` 会照单上记着的收款信息付出去，而回显不打印收款
信息，命令行上分不出两张单的收款账户。

`--ref`（申请单号 / 结算单号）也会进分录备注：申请那一档写在 `payout` 那条上，
逐字是「提现申请（单据 <ref>）」；清算那一档写在 `merchant_payable` 那条上，
逐字是「平台清算（单据 <ref>）」。理由与退款那一条相同：交易号是它的哈希，不落
备注就对不回这张单。

`--by` 收用户 ID 或用户名，先解析成一个真实存在的用户
——审批与清算都是记名动作，一行查无此人的记录追不出是谁做的。`--note` 进
`review_note`，不能有控制字符：回显会原样把它打出来，而库里那一份不过清洗。

`--gateway` 必填，`credit` 上那个 `manual` 默认值在这里**不适用**：通道未知时这笔
分录对不上任何一份通道账单。`--gateway-ref` 可选，它只是分录备注里的凭据号，**不是**幂等键
（幂等键见下），它也不能有控制字符。

五个动作各有**一把独立的幂等键**，都由外部单号或单子 id 推出来，互不相认：

- `request` 按 `--ref`（申请单号）。
- `settle` 按 `--ref`（结算单号）。它与 `request` 的键用不同的域前缀，所以同一个单号
  在「商户申请」与「平台清算」上是两笔不相干的交易。
- `reject` 与 `paid` 按**提现单 id**，不是通道给的 `--gateway-ref`：一张单子只可能被
  驳回一次、只可能打款成功一次。键取凭据号的话，同一张单换一个号会被算成一笔**新**
  交易，待付科目被扣成负数——那是重复打款，而它一路都不会报错。
- `approve` 不写分录，它的幂等由状态挡着。

重跑时回显分别逐字是「申请单号 <ref> 已经建过单，本次未改动。」「结算单号 <ref> 已经
清算过，本次未改动。」「提现单 <id> 已经批准过，本次未改动。」「提现单 <id> 已经驳回
过，本次未改动。」「提现单 <id> 已经打过款，本次未改动。」，都退出 0；重跑 `approve`
与 `settle` **不覆盖**上一次记下的审批人与时刻（`settle` 的 `--by` 只在第一次落库）。
同一把键配不同的内容（换商户、换金额、换通道、换凭据号、换收款信息）不是重放，而是
冲突：退出 4。

按 `--id` 找不到那一行时是「没有这条提现单: id = <id>」，退出 4（不是 2）：命令没有
写错，是库里没有这一行，下一步先去看库里现在有什么。

这一族**不动用户余额**：一分钱都不发到 `user:` 科目上，所以商户不需要先 `create`
钱包。

申请与清算都**校验商户的分成余额**：`merchant_payable:<商户>` 上的分录之和不够这次
金额时退出 1、一笔都不写（与 `wallet adjust` 把余额调成负数同一档），报错里带
「当前能提多少、这次要提多少」。分成的写入侧是消费结算：它按
[`settings`](settings.md) 的 `billing.merchant_share_bp` 把售价的一部分记到
`merchant_payable:<渠道所属商户>` 上。这个键默认是 `0`，也就是不分账——那时分成
余额恒为 0，申请与清算都会被一律拒掉，这是刻意的，不是这些命令坏了；边界是「不能动
平台还不欠的钱」。这条校验**不要求分成科目永远非负**：退款把分成冲成负数是允许的
（平台多付给了商户、商户欠平台），退款不会因此被拒。

这一族也没有 `list`：列单子要直接查 `payout_requests`。

`-h` / `--help` 与写错参数时打的是短版（`larkaxctl wallet --help`），这一族的说明书
单独一份：`larkaxctl wallet payout help`。

#### `wallet payment`

支付通道那一侧的充值：`create` 在通道侧建单并落一行 `payment_orders`（状态
`created`），`status` 读这张单子的现状。**`create` 不入账**：钱要等通道把
「已支付」的通知发到回调入口才进来（路径、请求体与状态码见
[api.md](api.md) 的「支付回调」）。

| 子命令 | 旗标 |
|---|---|
| `create` | `--user`、`--amount`、`--ref`（商户单号）、`[--asset]`、`[--notify-url]` |
| `status` | `--order`（商户单号） |

`--ref` 必填，是商户单号，同时是幂等键：同一个单号重跑只会得到同一张单子
（回显「订单号 … 已经下过单，本次未改动。」，退出 0）；同一个单号配不同的
用户、金额或资产不是重放，而是冲突（退出 4）。它不能带控制字符，理由与
`wallet credit` 的 `--ref` 相同。

`--amount` 必填且为正；`--user` 收 ID 或用户名；`--asset` 默认取
`billing.default_asset`。`--notify-url` 原样交给通道，命令不解释它。

通知到达后，账本写一组 `topup` 分录（借 `user:<ID>`、贷
`payment_gateway:<通道>`；手续费另记借 `upstream_cost`、贷 `platform_revenue`）。
状态机只能往前走：只有 `created` 收到「已支付」才入账并转成 `paid`；
`failed` / `expired` / `refunded` 是终态，之后到「已支付」的通知被放过、账本
不动。同一份通知重发不改变分录与余额。分录、余额快照与单据状态在**同一个事务**
里写，任何一步失败都整笔回滚。

`create` 要求用户已经有该资产的钱包，缺这一行时按与 `wallet credit` 同一档拒绝
（退出 4）——回调入账时账本也要写这个用户的钱包快照，缺行会让通知处理失败。因此
**回调入账要求钱包已经存在**。

`status` 先读本地那一行，再问通道这张单子现在是什么状态。假通道没有自己的账本，
它答的就是本地那一行，所以两栏今天恒等；接上真实通道之后才可能出现差异（通知丢了
时本地还停在 `created`，而通道那边已经付过）。本地没有这张单子、或通道侧查不到时
退出 4。

**这条通道默认关闭**：`settings.payment.fake_enabled` 为 `false` 时 `create` 与
`status` 都拒绝（退出 1），回调入口也不挂（那条路径回 501）。假通道的签名密钥是
公开的占位值，只用于本地联调，见 [settings.md](settings.md) 的「支付」一节。

#### `plan`

额度包（预存的服务量）的运维入口，也就是**商品定义**：一个包长什么样、还能不能再发。

某个用户持有的订阅、他的扣费顺序与一把 API Key 能用哪些订阅，已经搬到
`user plan` 与 `user key plans` 下（见「user」一节），核心宾语写成位置参数。
旧路径 `plan grant` / `plan void` / `plan subscriptions` / `plan key` / `plan order`
仍然可用，命中时在 stderr 提示新路径。下面几节讲的语义在两条路径上相同。

**三种计量单位**：`--unit amount` 的包按标价扣，`--quota` 与 `--face-value` 是同一个数
（只填一个即可）；`token` 包按输入加输出的 token 数扣；`request` 包每次扣 1。后两种包
里 `--quota` 是可用量、`--face-value` 是这个包值多少钱，两个都要填。账本上每个包只有
一个数——面值，消费分录的形状不随单位变化。

`--models` 按规范模型名精确匹配（与计价规则的模型名同一个键），逗号分隔。**token 与次数
包必须至少给一个模型**：它们的价值与模型强相关，不限定范围就是一个可能亏本的包；金额包
可以不给，空表示不限。

`grant` 建一条订阅，并把面值记进 `prepaid:<订阅 ID>`。`--ref` 是发放单号，也是幂等键：
同一个单号重跑只会发一次，第二次打「已经发过」并退出 0。同一单号配不同的用户、包或到期
时刻是冲突（退出 4），一笔都不写。`--expires-at` 必须是晚于现在的 RFC3339 时刻。

`void` 作废一条订阅，把剩余面值转回平台收入。`--status` 默认 `canceled`（运营提前收回），
给 `expired` 表示到期作废；两种在账上是同一个事件。`--ref` 是作废单号，同样是幂等键。

`key show` / `key set` 管一把 API Key 的额度包名单，今天的正式写法是
`user key plans show|set <API Key ID>`（旧写法 `plan key show|set --id <API Key ID>`
仍可用）。**没有配过名单表示可以用这个用户名下
全部订阅**；`--all` 清空名单，回到这个状态。名单里每一条都必须是这把 key 所属用户的订阅，
否则当场报错（退出 1）、一行都不写。名单至少要有一条——`--plans` 给空串会被拒——要恢复成
「全部」用 `--all`。删掉 key 或删掉订阅之后，关联行跟着删。

`order show` / `order set` 管扣费顺序的三档，正式写法是 `user plan order show|set <用户>`
（旧写法 `plan order … --user <用户>` 仍可用）：`plan_first`（先额度包后余额，平台默认）、
`balance_first`（先余额后额度包）、`balance_only`（只走余额）。用户上的值覆盖平台默认，
`--clear` 清掉覆盖。平台默认在 `settings` 的 `plans.charge_order` 上，用
`larkaxctl settings set plans.charge_order <取值>` 改。读侧遇到认不出的取值不报错：用户
那一行认不出就回落到平台默认；平台那一行缺失、不是 JSON 或取值也认不出，才回落到兜底值
`plan_first`。两种都记一条日志。

`plan list` 列出全部额度包（含停用的）；`plan get --key <key>` 打一个包的详情。
`user plan list <用户>` 列出一个用户的全部订阅（有效的、到期的、已作废的都在），「剩余」
那一栏是 `prepaid` 科目的余额。

`enable` / `disable` 控制一个包还能不能用于**新的发放**：已经发出去的订阅不受影响，它们的
面值在发放时就定下了；要收回某一份额度用 `user plan void`。

#### `usage`

用量与计费的只读清单。两条子命令各读一张表，回答的问题不同：`events` 读
`usage_events`，那是**计量**的底稿（每次请求用了多少 token、金额按哪条口径算出来的、
收了多少钱；`billing_path` 为 `measured` 的才是一次实测，`estimated` 是按估算给的、
`fallback` 是算不出来时按退路给的）；`requests` 读 `billing_requests`，那是**每次
请求**的预留与结算（`pending` / `settled` / `released` / `failed` / `refunded`，
以及两笔预留额与结算额）。

`requests` 的预留分成并列的两栏。`钱包预留` 是钱从账户余额冻住的那部分
（`billing_requests.reserved_amount`）：额度包覆盖的请求在这一栏是 0，钱一分没冻。
`包预留` 是这笔请求占着的额度包面值（`plan_reserved_amount`）。两个数不合并——
加在一起就答不了「钱包冻了多少」这个问题。机器可读档里
对应 `reserved_amount` 与 `plan_reserved_amount`。

`requests` 的每一行还给出定这一单价的**规则 id**（机器可读档里是 `pricing_rule_id`，
表格里那一栏叫 `规则`）。规则事后可变，所以账单要能回答「当时按哪条规则算的」这个
问题；`pricing_expr_snapshot` 记的是表达式当时长什么样，答不了是哪条规则定的价。
请求没有落到任何规则上时那一栏是空的：表格打 `-`，机器可读档是 `null`，
不用 0 冒充「没有」——0 不是一个合法的规则 id。

两条都按 `--user`（用户 ID 或用户名，两种写法都认）与时间窗筛，时刻用 RFC3339 或
只写日期（按 UTC 零点算），区间左闭右开。按用户看这两张表另有正式写法
`user usage events|requests <用户>`（见「user」一节），输出与 `--user` 那一档逐字相同；
旧写法 `usage events|requests --user …` 仍可用并在 stderr 提示新路径。两个时间参数都不给
就是不限时间，那时每个
月份的分区都会被扫到。时间窗按哪一列圈定，两条不一样：`events` 按**落库时刻**，
而那一列正是这张表的分区键（`usage_events` 按月分区，见 `partition` 一节），所以给了
窗口时范围之外的那些月份不会被扫到；`requests` 按请求的**受理时刻**，一次迟到的结算
不会让它从发生的那个窗口里消失。

两张表的代价不一样。`usage_events` 那边，给了窗口就能按分区裁掉范围之外的月份；
`billing_requests` 上只有 `(user_id, started_at)` 一条索引，**只给时间窗、不给
`--user`** 时，按 `started_at` 筛用不上它（索引的第一列是 `user_id`），要全表扫一遍
再排序——窗口开得越宽越慢。

两条都是**管理员动作**：跑得起 `larkaxctl` 的人本来就能连上这个库，所以这里不额外
要求别的授权，也不带角色参数。

`--limit` 是一次最多打几行，默认 50，0 表示不限。清单新的在前；被截住时末行会说明
只打了多少条，机器可读输出里对应 `summary.truncated`。

#### `ledger`

财务账本管理：读余额、校验分录，跑一轮对账，以及看对账的历史。`balance`、
`verify` 与 `runs` **只读**：不改任何一行、不写任何快照，任何写入都走各自的写入路径，
这里不提供。`reconcile` 不是只读的：它往 `reconcile_runs` 记一行，并在 `settings` 的
`reconcile.auto_repair` 为真时按口径修差额——要不要动手由那个开关决定，命令行上不
带参数，于是「线上跑的是哪一套口径」只有一个答案（库里的值）。

`runs` 读的就是 `reconcile` 写下的那张表，所以两件事对得上：清单里最新那一行就是上
一轮。每一行给出开始时刻、状态（`running` / `done` / `failed`）、范围（全量还是增
量）、起点（下一轮增量从这里开始）、比对过的用户数、五类差额（余额、冻结、畸形科
目、陈旧预留、额度包面值）与修复条数。**范围**那一栏最要紧：增量只看上次起点之后
变动过的行，一份全是增量的清单说明「两边都早就错着」的那种不一致还从来没被看过一
眼。`--limit` 默认 20，0 表示不限。读它同样是管理员动作，理由与 `usage` 那两条相同。

`balance` 打出来的余额是从分录**现算**的权威值，不是 `user_wallets` 里那个快照。
两者是否一致由 `reconcile` 比对，它还会把差额归集到 `reconcile_difference`；
`balance` 只回答「账本上是多少」。

科目按账本的写法给，例如 `user:42`、`merchant_payable:7`、`payout:3`、
`payment_gateway:<通道名>`、`platform_revenue`、`upstream_cost`、
`reconcile_difference`。时刻用 RFC3339 或只写日期（按 UTC 零点算），区间左闭右开。

`verify` 的范围按「在这个区间里出现过的交易」圈定，而每一笔交易都会**整笔**读回来
校验：只按行过滤会把横跨区间边界的交易切两半，而半笔可能看起来是平的。
`verify` 发现不合法、或区间里一条分录都没有时退出 1；`reconcile` 发现不一致时也是
1。旧路径 `larkaxctl reconcile` 仍然可用。

### 系统与数据维护 (Maintenance & Data)

#### `migrate`

数据库版本迁移。`create` 只写文件、不碰数据库，其余各条都要连库。

`up-to` / `down-to` 是一步一步走到目标版本的，不调用 `goose` 自带的同名命令：实测
它们会停在目标版本的相邻位置（从 v2 执行 `down-to 0` 只退到 v1），差一位的表现比
不支持更危险。

`up` 默认不补应用「编号比当前版本小、却从未应用过」的迁移，遇到时列出那几条并停下。
确认要补时加 `--allow-missing`：goose 先按版本顺序补应用它们，再应用所有更大的未应用
迁移，补了哪几条打在 stderr 上。其余动作不接受这个开关。什么时候该用、不改二进制的
手工等价做法见 [development.md](development.md) 的「编号更小的迁移漏掉时」一节。

#### `partition`

数据库月度分区维护。`usage_events` 按 `created_at` 按月分区，分区不会自己长出来：
没有预建时，过了迁移里种子覆盖的月份之后，每一行用量事件都落进兜底分区
`usage_events_default`——不报错、查询照常返回正确的行，只是这张表退化成「所有数据
堆在一个分区里」。而兜底分区里的行会挡着那个月的分区建不出来，要人工先把行搬走。

`ensure` 与 `check` 是给外部调度器用的：命令的退出码就是告警信号。`--months` 是
「从当月起算几个月」，默认 3（含当月），它决定的是提前量：给 1 只保证当月，预建任务
停摆超过一个月，下一个月的分区就不存在了；给 3 留出两个月的缓冲，代价只是多几张
空表。

`check` 只读，它不建任何东西。写入路径自己会保证当月分区存在，所以 `check` 报出
「缺月分区」说明预建任务漏跑了，而不是写入路径坏了——这两件事的处置不同，所以
`check` 不去替 `ensure` 把分区补上。

#### `secret`

安全凭证与主密钥维护，密钥轮换（`rotate`）需要主密钥。密钥本身从环境变量
（`LARKAX_MASTER_KEYS`）来，这里没有「设置密钥」这个动作：写进命令行或库里的密钥
会跟着 shell 历史与备份一起流传出去。这一组做的是**换**密钥——把已有的凭证重新包
一份新的，全程不需要明文凭证。

它挂在 `secret` 而不是 `channel` 下面：轮换读写的确实是 `channels` 那一列，但它管
的是密钥本身的生命周期，与渠道怎么配是两件事。这与 `LARKAX_ROLE` 无关：运维命令不
属于任何角色，主密钥直接从这个变量读。

#### `secret rotate`

轮换渠道凭证的主密钥。它补的是「当前主密钥的一份数据密钥副本」，**不解密凭证正
文**：每个信封本来就被旧主密钥包着，本命令给它再包一份新的。

顺序（重要）：本命令只保证新主密钥的副本存在，**不退役旧主密钥**。

1. 把新主密钥放进 `LARKAX_MASTER_KEYS` 的**首位**，旧密钥留在后面，重启服务；
2. `larkaxctl secret rotate` 看清有多少行要改；
3. `larkaxctl secret rotate --apply` 轮换（可中断、可重跑，重跑是幂等的）；
4. `larkaxctl secret rotate --verify` 退出码为 0 才说明全库每一行都含新主密钥；
5. 到这一步才能把旧主密钥从 `LARKAX_MASTER_KEYS` 里去掉。

第 4 步之前去掉旧主密钥，那些还没轮换到的行就再也解不开了。跑 `--apply` 之前先备份
`channels` 表（至少备份 `credential_enc` 这一列）：轮换改的就是这一列。中断不会让
数据不可用——每一行要么是旧的（仍被旧主密钥包着），要么是新的（新旧都能开），不存
在解不开的中间态；没跑完的部分 `--verify` 看得见。

`--apply` 会取一把 PostgreSQL 会话级互斥锁，同一时刻只允许一处轮换，已有轮换在跑时
直接失败而不排队。干跑与验证是只读的、不取锁，但会在锁被占用时提示「读到的可能不是
终态」。

退出码：`--verify` 的退出码回答「有没有漏网的行」，有就是非零；`--apply` 的退出码只
回答「这一轮跑完了没有」——轮换不了的行会被逐行打出来，但那一行坏掉不该让整次轮换
报失败（它再跑一次也还是坏的，由 `--verify` 与人工处置）。

旧路径 `larkaxctl rotate` 仍然可用。

#### `maintenance`

数据留存与过期清理。这一组的共同点是「按留存承诺删掉过期的行」：留存期到了就删，与
业务上发生了什么无关，所以它既不挂账本域也不挂某个业务对象。第三方数据（例如请求
快照）的留存各有自己的分区维护命令，见 `larkaxctl partition` 与
`larkaxctl snapshot`。

#### `maintenance idempotency`

按留存期清理请求级幂等记录。留存期取自 `settings` 表的
`idempotency.retention_hours`，不在命令行上另设参数：同一件事有两个来源时，命令行的
那个会悄悄赢，而「留存期到底是几小时」会变成一件要看是谁执行的才知道的事。

输出的是**删了多少条**而不是一句「完成」：一条都没到期时，命令的输出必须与「根本
没跑成」区分得开。旧路径 `larkaxctl idempotency cleanup` 仍然可用。

#### `maintenance session`

清理控制台会话表（`user_sessions`）。登出与改口令只是给会话行盖上 `revoked_at`，
过期行也不会自己消失，所以这张表需要有人定期来删。

留存期取自 `settings` 表的 `console.session_retention_days`，不在命令行上另设参数
（同 `maintenance idempotency`）。

删两类行：

- `expires_at` 已经过去的——到点即删，**与留存窗口无关**；
- 已吊销且 `revoked_at` 早于「现在减去留存窗口」的。

窗口内被吊销、**且尚未过期**的会话留着：排查「这个会话是什么时候被踢的」要看它们。
（改口令会给所有未吊销的会话盖上 `revoked_at`，不过滤过期，所以「已吊销」不蕴含
「没过期」。）窗口按 `revoked_at` 算，不按 `expires_at`。

`--dry-run` 只数一遍，一行都不删。重复跑是安全的：第二次没有可删的行，输出
`已删除：0 条（没有到期记录）` 并退出 0。`--format json` 不支持（写类命令）。

**首轮可能超过默认超时。** 这张表在命令出现之前只增不减，第一次跑要删掉全部历史行，
而命令的超时固定为 2 分钟：删不完时命令以超时失败退出，这一条 `DELETE` 回滚、一行都
没删（语句是原子的）。重跑仍会一次删掉同样大的量，所以积压特别大时要先 `--dry-run`
估量条数，必要时按时间段手工分批删。

#### `snapshot`

请求结构快照管理。`cleanup` 负责把到期的删掉；`redact` 走脱敏的**输入**，`get`
读脱敏的**产出**，而 `access-log` 把 `get` 写下的访问记录读回来。

留存期取自 `settings` 表的 `request_snapshot.retention_days`，不在命令行上另设参数
（同 `maintenance idempotency`）。

`allowlist` 不需要连库。它只读 `internal/snapshot` 里那张允许表，那是纯代码里的
数据。所以它能在没有数据库、没有配置的机器上跑——而「我们到底存了什么」这个问题，
恰恰经常是在一个连不上生产库的地方被问出来的。

`get` 的 `--actor` 与 `--reason` 都是必填。读一条别人的请求结构是读敏感数据的动
作，所以每一次读都要留痕：`snapshot_access_log` 里会写下一行，记着谁、什么时候、以
什么理由看了哪一条。表里 `reason` 允许为空，那是给系统自己写的行留的余地；人手读一
次，理由必须留下。写日志与读快照在同一个事务里：一个「读了但没记」的成功返回看起来
完全正常，而它意味着这张表存在的理由落空了。同一个 `request_id` 可能有多行（请求与
响应各一行，重试也可能各一行），`get` 全部按 `created_at` 升序打出来；一条都没读到
的时候非零退出，并且不写访问日志——没读到东西不算一次访问。

原样采集的行（`capture_mode = full_consented`）在打正文之前会按这一行的 `user_id` 与
`request_id` 再查一次授权，没有缓存。授权到期、撤销，或者记录已经不在时，那一行照常
列出来，正文不显示：人类可读那一档在正文的位置写一句「授权已失效或无法确认，
原文不再可读」，机器可读那一档 `skeleton` 为 `null`、`raw_withheld` 为 `true`
（平时是 `false`）。查库失败时按「没有授权」处理，方向与采集侧一致；渲染这一层
分不出「确实失效」与「查不出来」，所以那句话把两种情形写在一起。

`redact` 看到的结果不是库里那条快照。它把一段报文交给脱敏器，回答的是「这段报文会
长成什么样」；库里那条骨架来自**解析之后**的请求 / 响应，字段集合与这里不完全一样
——不转发的字段不会进库，而解析会补上它自己带的几个。内容层面的结论一致：允许表之
外的一律变成占位。骨架打到标准输出（可以直接接给 `jq`），方向、骨架版本、字节上限、
被替换的路径与那句提醒打到标准错误。报文从标准输入读，上限 64 MiB——这条命令是拿
一段**单次请求**的报文来试，不是拿整份日志。

`access-log` 按 `--request-id`、读取者（`--user`，用户 ID 或用户名）与时间窗筛，三者
可以一起给，也可以一个都不给（那就是最近的那些）。**`--user` 筛的是读快照的那个人**，
不是快照属于谁：这张表记的是读取动作，快照属于谁是快照那一侧的事。理由那一栏是 `get`
的 `--reason` 原文，系统自己写的行没有理由。它同样是管理员动作：跑得起 `larkaxctl` 的
人本来就能连上这个库，所以这条命令不额外要求别的授权——与 `get` 把读取者记成 `admin`
是同一条口径。窗口左闭右开，`--limit` 默认 50、0 表示不限。表上只有
`(request_id, accessed_at)` 一条索引：不按 `--request-id` 筛时，只给时间窗或只给
读取者，都要全表扫一遍再排序（同 `usage requests`）。

`request` 与 `response` 各有一张允许表，所以 `redact` 必须指明方向；`allowlist` 与
`get` 不填时两个方向都处理。旧名 `snapshot show` 等同于 `snapshot get`。

#### `consent`

原样采集请求正文的授权。`grant` 开一条授权，`list` 看现有的，`revoke` 撤销。

两个范围二选一，字段不能混着给：`single_request` 只对 `--request-id` 那一次请求生效，
到 `--expires-at` 为止；`time_window` 对 `--from` 到 `--to` 之间的全部请求生效。时间窗
那一档的到期时间就是 `--to`，不另设参数——同一件事有两个来源时，命令行那个会悄悄赢。

`grant` 必须带 `--agree`。不带时它只把同意文案打出来、什么都不写：`capture_consents`
的 `consent_text` 与 `consent_version` 两列是拿来做合规举证的，落库之前操作者得先看见
自己同意的是什么。文案是 `internal/snapshotwire` 里的常量，改文案就要把版本号加一；
旧记录里留着的仍是当时那一份。

申请时长有上限：`settings` 的 `capture.consent_max_window_hours`。`single_request` 比的是
从此刻到 `--expires-at`，`time_window` 比的是两端的长度。超过上限**报错拒绝**，不夹到
上限——夹一下会让申请的那段时长看起来生效了，而实际生效的更短，等它到期时人已经不在
看着它了。错误里同时给出上限与申请值。

`list` 不带 `--user` 时列出全部用户的授权，含已经撤销与过期的那些：这一栏回答的是
「谁开过、开的是什么范围」，而不是「此刻哪几条还有效」。状态那一栏是显示口径，由撤销、
到期与时间窗三件事算出来。`-u` 是 `grant` 与 `list` 上 `--user` 的简写（见上面的
「短选项」）；`revoke` 的位置参数是授权 ID，它没有简写。

撤销、到期、时间窗没开始或已经过去，这四种情况在**读取的那一刻**重新校验：判定发生在
脱敏那一刻（`internal/gateway` 通过 `snapshotwire` 的 `ConsentSource` 问一次），每次都查
一次库，没有缓存。撤销要立刻生效，靠的就是这一点——缓存期内撤销过的授权仍在放行原文，
而那个窗口有多长取决于缓存，不取决于撤销这个动作。查库失败时按「没有授权」处理，落下来
的是骨架。

没有有效授权时采集侧落下来的就是脱敏骨架（`capture_mode = skeleton`），有授权的那一段
是原文（`full_consented`）。读原文那条路是 `snapshot get`，它自己写访问日志。按 API key
授权这一档不做：采集那一刻拿不到 key id，`capture_consents.api_key_id` 这一列留空。

#### `plugin`

动态插件系统管理。插件的 key 与版本写在源码里（`export const meta`），所以
`publish` 默认不要求 `--key`；只有想让注册名与源码里声明的不一致时才需要它——那种
情况下两条路会对不上，命令会拒绝。

`publish` **先在沙箱里编译一遍再落库**：一个编译不过的插件不许进库，否则加载器每次
启动都要处理它。同一个 `(key, version)` 重复发布是**覆盖**：源码、元数据、名称换
新，代次（`generation`）取这个 key 当前最大的代次加一，启用状态保持原值——改一个
笔误不该让已启用的插件下线。覆盖会让这一版排到最前：它本来是 `active` 的话，下次
加载（启动或 SIGHUP）装上的就是它。换版本请改源码里的 `meta.version`，那会插入一行
新代次（同样取最大值加一），状态是 `pending`，要 `enable` 才生效。

`publish` 的 `--by` 必填。`plugins.created_by` 记的是谁写下的这一行，而一条不记名
的写入等于没有审计——允许留空的话，最省事的用法就是永远不填。它收 `users.id` 或用户
名，落库记的是那个 ID，`list` 与 `get` 的 `-o json` 里 `created_by` 那一栏就是它
（不为 `null` 表示记下来了）。**覆盖时这一栏跟着换成这一次的操作人**：那一行的
`source` / `meta` 已经被这次发布换掉了，而 `get` 里那一栏问的是写下现在这份内容的
人。同一行的 `created_at` 不跟着换——它记的是这一行什么时候出现的。

**改完要重新加载**：`publish` / `enable` / `disable` 都只改库，跑着的进程不会自己发现。
对 larkax 进程发 `SIGHUP` 会重新读库并原子切换——在途请求继续用它开始时取到的那一份，
下一个请求走新的一份；新的一代编译不过时整批不发布，线上仍是上一份注册表。重启进程
也会重新加载。SIGHUP 是逐进程的，多实例部署时每个实例都要发。key 在库里没有对应行时
按「约束冲突」返回 4。

`get` 看一个插件：打的是**最新发布的那一代**（代次最高的那一行），并说出这个 key
下还有几个更老的版本——不说的话，「只有一个版本」与「有好几个、你看到的是最上面
那个」在这份输出上一样。

`list` 与 `get` 都回答**三件事**：取中的是哪一代，最新一次尝试是哪一代，那一次加载
装上了没有。取中的是加载器会装上的那一代（同一个 key 里状态为 `active` 且代次最高的
那一行），最新一次尝试是代次最高的那一行，两者不一定是同一行：发布了新版本还没
`enable` 时取中的仍是上一代。

**加载期**的结果是第三件事：加载器每次装载（启动、或收到 SIGHUP）都重新读一遍参与
注册的行，把结果写回库里（`last_load_result` / `last_load_error` / `last_load_at`
三列）——装上了写 `ok`，没装成时写 `failed` 连同当时的错误原文与时刻。它与发布期
无关：`publish` 根本不收编译不过的插件，所以「发布了却没上线」只有这三列说得出来。

`status` 那一栏读不出「取中的是哪一代」：`enable` 新版本时旧的那一行不会被按下去，
于是一个 key 下可能有好几代都写着 `active`。`list` 与 `get` 里那两栏按加载器的口径
算出来（库里没有这两列），它们是同一个答案的两半：

| 这一行 | 「在跑」 | 「上次加载」 |
|---|---|---|
| 取中的那一代，上一次加载装上了 | `是` | `装上了`（那次加载的时刻） |
| 取中的那一代，上一次加载跳过了它 | `否` | `没装成`（时刻），原文在表后 |
| 取中的那一代，还没有加载记录 | `还没试` | `-` |
| 不是取中的那一代 | `否` | `-` |

同一个 key 里至多一行是取中的那一代，所以「是」至多一行。「**取中的那一代被跳过
时，这个 key 什么都不在跑**」——加载器在一个 key 里只取一代，跳过它不会退回更老的
那一代，那一刻哪一行都不是「是」。`get` 有同样的两栏，失败时也在表后打一句原文。

「还没试」与「否」是两回事：那三列由加载器写下来，它还没写过。来路有两条，下一步
不一样——`plugin.enabled` 关着时加载器整条链路不装配、根本不读表，重启或发 SIGHUP
多少次都不会有记录，要先把这个设置打开（见 [settings.md](settings.md)）；开着时才是
「发布或启用之后还没重新加载过」，重启一次或发一次 SIGHUP 就有了。写回没落地时
（连不上库、写超时）留下的也是旧的那一份记录，所以「上次加载」的时刻还要读：它说的
是**最近一次写成功**的尝试。

**启动时跳过不改任何状态**：那一代的 `status` 仍是 `active`，启用记录也不动，所以下次
启动照样会再试一次——插件没装成时，先把源码或这次的装配调好再重启，不必重新发布。

**SIGHUP 与启动在「有插件编译不过」时处置不同**：启动时没有旧表可守，跳过坏插件、其余
照常上线（服务总得起来）；SIGHUP 时手上有一份正在服务的注册表，所以**整批不发布**、
旧的那一份继续服务，失败的那几行写回 `failed` 与错误原文。此时 `list` / `get` 报的是
**这一次尝试**的结果（取中的那一代写着「否 / 没装成」），而进程里仍在跑的是上一份
注册表——那通常是更老的一代。

`-o json` 下 `plugin` 条目在 `list` 的字段之外多三栏：`versions`、`created_at`、
`created_by`。两个命令的条目都带另外四栏：`latest`（这一条是不是最新一次尝试，
也就是代次最高的那一行——覆盖取的是最大代次加一，所以它就是最后发布的那一次；
早先写下的行里两行可能同代次，那时不止一条为真——那种并列就是当时覆盖发布把代次
原地加一留下的）、`running_generation`（这个 key 取中的那一代，
形如 `{"version": …, "generation": …}`，没有时是 `null`）、
`running_load`（那一次加载的结果 `{result, error, at}`，`error` 装上了是 `null`，
`at` 在那一行没有记下时刻时是 `null`——手工改库的行可以只填结果那一列，见迁移 00034；
还没有加载记录时整个是 `null`）、`compile_error`（发布期编译不过的原文，
没有时是 `null`；只有手工改库的行会有值）。

取中不等于在跑，而 `running_generation` 与 `running_load` 是**按 key 给**的：
同一个 key 的每一条带着同一份，脚本要判的是**这一条自己**是不是取中的那一条——
`version` 与 `generation` 都与 `running_generation` 相等（代次会撞车：
早先写下的行里两行可能同代次，那时只比代次就会在同一个 key 里撞出两行来——
那种并列是当时覆盖发布把代次原地加一留下的）。是取中的那一条时，
`running_load` 为 `null` 是 `还没试`、
`result` 是 `ok` 是 `是`、是 `failed` 是 `否`（原文在 `error`）；
不是取中的那一条时是 `否`，与它自己那份 `running_load` 无关。

`delete` 是硬删除：插件行、它的启用记录与 `plugin_kv` 里属于它的键一起删掉，不可
逆，也没有导出。`plugin_kv` 没有指向 `plugins` 的外键，不在这里一起清的话，那些行
会永远留在库里而没有任何命令看得见它们。回显在 stderr 上，三样数量各报一次。

`plugin kv` 是插件私有键值存储（`plugin_kv` 表）的三个动词：`get` / `set` /
`delete`。一个键的身份是三段——插件、用户、键，三条命令都要给全 `--plugin` 与
`--user`。**过期的键按不存在处置**：`get` 与 `delete` 都说没有这个键（退出码 4），
而过期的行仍留在表里，由下一次 `set` 顺手清掉。`set` 的 `--ttl` 只认 Go 的时长
写法（`1h30m`、`45s`），不给或给 0 表示不过期，负数被拒。写入不对值做任何解析：
它是插件的私有数据。

**只读的那几条不要主密钥**（`list` / `get` / `kv get`）；`delete` 与 `kv set` /
`kv delete` 要求 `LARKAX_MASTER_KEYS` 在场，`publish` 不在内——它不 seal 任何
东西。命令本身不做解密，这一条要的是「这台机器带着运维凭证」。

这张表只收一级命令的搬家。user 那一族是二级动作的搬家（plan grant 变成
