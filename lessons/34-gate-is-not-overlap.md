# 34 · 并发用例只加闸门，不保证 goroutine 真的重叠

**编号** 34 · **日期** 2026-10-17 · **摘要**：8 个 goroutine 等同一个 `close(start)` 再动手，
看着是并发；但连接是**懒建**的、空闲池默认只留 2 条，于是先拿到连接的一两个把活干完了，
其余几个还在建连接——竞态窗口一次都没撞上，而用例**十轮全绿**。

**现象**

`larkaxctl wallet open` 的幂等靠 `INSERT ... ON CONFLICT (user_id, asset) DO NOTHING`，
用例要证明「并发开户只建一行」。第一版这样写：

```go
start := make(chan struct{})
var wg sync.WaitGroup
for i := 0; i < 8; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        <-start
        _, err := store.OpenWallet(ctx, userID, asset)
        _ = err
    }()
}
close(start)
wg.Wait()
```

看着是 8 个 goroutine 一起冲。把它拿去跑**「先查再插」那版实现**——本来就该在并发下
失败的那版——**三轮全绿**。

**原因**

`database/sql` 的连接是**懒建**的，而 `MaxIdleConns` 默认只有 2。8 个 goroutine 同时
从 `<-start` 出来之后，真正能立刻发 SQL 的只有手里已经有连接的那一两个；其余几个在
**建新连接**，而那要几十毫秒。等它们连上，先头那一两个早就把行插完了，
`ON CONFLICT` 那一支根本没被两个 goroutine 同时走过。

**闸门闸住的只是「开始等」，不是「开始做」。** 中间隔着一层「拿到资源」的排队，
而排队的长度由池的配置决定。这件事是被量出来的，不是想出来的：

| 闸门 | 预热 | 跑「先查再插」那版 |
|---|---|---|
| 有 | 无 | 三轮全绿（什么都没钉住） |
| 无 | 无 | 两绿一红（靠运气） |
| 有 | 有 | 三轮全红 |
| 无 | 有 | 三轮全红 |

第一行就是那次差点被当成「用例写好了」的组合：**判据看着在、其实一个变异体都没钉住。**

**解决**

放闸之前**先把连接都建好并同时持有**：`SetMaxOpenConns(n)` + `SetMaxIdleConns(n)`，
先并发取 n 条连接、全部拿到之后再一起放回，然后放闸。这样从闸门后面出来的
goroutine **都已经握着连接**，中间那层排队没有了。

n=8 时窗口还是太窄（十轮漏一轮），改成 **16** 之后：

```
真实实现（ON CONFLICT），n=16：10 轮全绿
先查再插，n=16：40 轮里 39 轮红
```

要证明用例会红，**不必把改坏的实现写进工作树**。`go test -overlay` 能把另一份实现
喂给编译器，工作树一个字节都不动：

```sh
go test -overlay=/tmp/broken.json -run TestOpenWalletConcurrent ./internal/ledger/store/
```

**预防**

> 这条用例钉住的到底是「并发下行为正确」，还是「恰好这一轮没撞上」？

只加闸门的并发用例答不了这一句。**判据是「窗口真的被撞上」**，所以要主动把窗口做宽：
预热、加大并发数、把「拿到资源」这一步挪出临界区。

**漏掉的那一轮要认下来。** 40 轮里漏 1 轮是这类用例的固有性质——它依赖调度恰好把几个
goroutine 叠在一起，不是判据写错。但**反方向必须是确定的**：真实实现跑多少轮都绿，
所以不会误报。这一条要写进用例注释，否则下一个人会以为那个 39/40 是没修干净。

与第 16 条（「跳过」在输出里和「通过」长得一样）同族：那一条说「没跑」看起来像
「通过」，这一条说**「跑了但没撞上」看起来也像「通过」**。
