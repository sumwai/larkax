# 48 · 失败路径的用例用了「碰巧存在」的 id：整包绿、单跑红

**编号** 48 · **日期** 2026-10-23 · **摘要**：失败路径用例把「不存在的 id」写成
`--id 1`。整包跑时，同包别的用例先建出来的 Key 恰好占了 id 1，于是这条用例走的是
**成功路径**——它仍然是绿的，因为它断的是「有提示」而不是「失败」。单跑时库里没有
id 1，走失败路径，用例红。整包与单跑给出相反的结论，而输出里没有一行提示。

**现象**

```text
$ go test ./cmd/larkaxctl/ -count=1     # 整包
ok  	cmd/larkaxctl	43.084s

$ go test ./cmd/larkaxctl/ -run TestLegacyUserPathsStayAndPointToNewPath
--- FAIL: TestLegacyUserPathsStayAndPointToNewPath/plan_key_show
```

两次都「通过」或「失败」得很有道理，差别只在库里有没有那一行。

**为什么会漏**

DSN 缺席那一类至少会 `t.Skip`，`--- SKIP` 在输出里看得见，CI 另有一道门专门
确认集成用例真的跑了。**同一个包内的隐式顺序依赖没有这道门**：它不跳过、不报警，
只是把用例悄悄换到了另一条分支上。而失败路径的用例通常只断言「报错时的形状」，
走成功路径时那条断言可能同样成立（「有提示」成功失败都打），于是它绿得毫无破绽。

**判据**

失败路径的用例，id 要用**不可能存在**的值，而不是「现在不存在」的值：

```go
// 错：靠库里恰好没有 id 1
[]string{"plan", "key", "show", "--id", "1"}

// 对：与库的状态无关
[]string{"plan", "key", "show", "--id", "9223372036854775807"}
```

同类还有「上一个用例留下的钱包 / 订阅 / 用户」——凡是 `--user <固定名>` 这种写法，
都要问一句「同包别的用例会不会建出它」。

**复核时怎么用**

别人的「整包 ok」不能单独当证据：整包绿而单跑红，恰恰说明用例的前提依赖了包内顺序。
复核失败路径的用例时，要么单跑那条，要么看它用的 id 是否与库状态无关。
