# 25 · 两条分支各自的 CI 都绿，合起来不绿——而门禁抓不到

**编号** 25 · **日期** 2026-10-17 · **摘要**：两条分支改的不是同一行，git 看不到冲突，而门禁与 CI 都是单分支视角。

**现象**

一条分支给 `Charge.PricedAt` 加了**必填校验**（零值即报错），并把**自己分支上**
那 12 处测试夹具都补上了 `PricedAt`。
另一条并行分支新加了一个 `settle()` 夹具，造的 `Charge` 没有 `PricedAt`。

两条分支都基于同一个 main，**各自的树上都没有冲突**，所以：

- 各自的单元测试绿；
- 各自的门禁（含全量 `-race`）15/15 绿；
- 各自的 CI 绿。

合进 main 之后，后合的那一条挂在
`缺少受理时刻：调用方没有设置 pipeline.Charge.PricedAt`。

这与[第 11 条](11-branch-off-foreign-branch.md)（在别人的分支上开分支）不是一回事：那一条是**分支基线**错了，
这一条是**两条分支的语义**撞了，而 git 看不到——它们改的不是同一行。

**同一个形状的第二个实例**：一条分支给测试助手 `billedCharge` 加了一个 `billID` 参数，
另一条分支**新增**了一个测试文件，里面按旧签名调它。新增文件对旧签名——git 看不出冲突，
**编译器才看得出来**（`not enough arguments in call to billedCharge`）。
判据还是那一句：这条分支让哪件以前合法的事变成非法了？这里是「按旧签名调用」，
而受害者是**新增的测试文件**，也就是[第 25 条](25-each-branch-green-merge-red.md)里说的最容易漏的那一类。
两次都是门禁抓出来的，而不是人看出来的。

**预防**

- 一条分支**收紧或新增一个必填约束**时，在 PR 描述里单开一句写清楚：
  收紧了什么、影响哪些构造点。合并的人按这句去另一条在飞的分支里找一遍。
- 判据：**「这条分支让哪件以前合法的事变成非法了？」** 答得出来的话，
  拿这个答案去扫其余在飞分支**新增的测试夹具**（新增的最容易漏，
  既有的多半已经被同一条分支补过）。
- 门禁与 CI 都是**单分支**视角的，别指望它们。这类冲突只能靠合并的人主动问，
  所以它必须写进 PR 描述，而不是留在实现者的脑子里。
