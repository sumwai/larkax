# 45 · 编号有序的两条迁移被乱序合入，已升级的库再也升不上去

**编号** 45 · **日期** 2026-10-21 · **摘要**：两条分支各加一条迁移、号不撞
（`00049` 与 `00050`），但**号大的先合入并被部署**。在那之后升级过的库记下了
版本 50、没有 49，goose 从此拒绝前进——不是它坏了，是它按设计拦住了乱序。

**现象**

`larkaxctl migrate up` 直接失败，库停在上一个版本：

```
执行 up 失败: error: found 1 missing migrations before current version 50:
	version 49: 00049_prepaid_plans.sql
```

之后**所有**新迁移都进不去。症状会先出现在别处：`00051` 没应用，`settings`
缺它插入的那个键，服务启动报「settings 缺少配置项」。看起来是配置问题，
实际是迁移根本没跑到。

**原因**

迁移编号在**写文件那一刻**取「当时的 next」，而合并顺序与编号顺序无关。
两条分支同时起飞时，号小的那条被评审、被修、被推迟，号大的那条先合并、
先部署——中间那两个小时里做过的升级就都没见过 49。

goose 的判据是「存在比当前版本小的未应用迁移就拒绝前进」
（`findMissingMigrations`），这是安全默认：乱序应用可能踩到后一条迁移的假设。
所以「号不撞」并不等于「能升上去」，同第 38 条是同一家族的两面：那条讲**号会撞**，
这条讲**号对、序错**。

**解决**

1. 运行时接出逃生口：`migrate up --allow-missing`，走
   `goose.UpContext(ctx, db, ".", goose.WithAllowMissing())`，先把缺的按编号补上，
   再应用所有更新的。默认仍严格，否则乱序会变成静默的常态。
2. 不改二进制的手工等价做法：按 `-- +goose Up` 段单独补跑那条 SQL，再往
   `goose_db_version` 插一行 `(version_id, is_applied)`，然后正常 `migrate up`。
   **手工补的是缺的那条，不是最新那条**——顺序反过来会把后面的迁移建在不存在的
   表上。

**预防**

- **合并前先看 main 上的最大号**：`git ls-tree origin/main internal/migrate/sql`
  里最大的那个号，比 PR 里新增的号大，就先把 PR 的号改成下一个空号再合
  （未部署过的迁移改号是安全的；已经有人在库里应用过就别改，走第 1 条）。
  只有两条分支都带迁移时才有这一步，但**两条同时带迁移时它不许省**。
- **两条 PR 都带迁移时按号从小到大合**：先合小号，大号那条 rebase 后号自然还在后面。
- **乱序这条路径要有用例**：造一个「当前版本 N、N-1 缺失」的库，钉住两件事——
  不带开关仍然报原来的错、带开关能补应用并继续前进。只在正常库上跑 `up` 测不到它。

第 25 条（两条分支各自的 CI 都绿、合起来不绿）。
