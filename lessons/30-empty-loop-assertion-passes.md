# 30 · 遍历一堆东西的断言，东西为空时全部静默通过

**编号** 30 · **日期** 2026-10-17 · **摘要**：循环体一次都不进等于通过，所以要先断言条数、再遍历。

**现象**

一条跨协议流式用例里，「每对 `content_block_start` / `content_block_stop` 配平」
那条断言**从没响过**——把帧摊平成「块帧」时 `kind` 填的是 SSE 的事件名
（`content_block_start`），而断言里 `switch` 的 case 写的是 `start` / `delta` / `stop`。
**一条 case 都没匹配上，整个循环体一次都没进。**

它安静地通过了，输出与「块全部配平」长得一模一样。发现它的是**另一条**断言
（「收到 0 个工具块」）——如果那条不存在，这个守卫会一直空转下去。

**原因**

「遍历一堆元素、逐个断言」这个形状里，**循环体一次都不进等于通过**：
「一个元素都没有」与「每个元素都合格」在断言结果上是同一件事。
这是[第 16 条](16-silent-check-failure.md)（「没跑成」与「跑成了」同形）的数据版本——[第 16 条](16-silent-check-failure.md)说的是**工具**，
这一条说的是**被遍历的数据**。

**怎么防**

1. **先断言条数，再遍历。** 条数写死成这个场景的**确切**条数（不是 `> 0`）：
   `start 2 / delta 4 / stop 2`。取不到就当场挂，读者立刻知道该往哪看。
2. **哨兵用 `t.Errorf`，不要 `t.Fatalf`。** 第一版用的是 `Fatalf`，结果它把后面
   三条具体报错全挡掉了，只留下一句「条数不对」——读者还是不知道该看哪儿。
3. **每条断言都要有一次实测触发。** 这条用例用两次变异把三条断言各触发了一次
   （改回 #291 的修法 → 配平那条响；命中旧下标重开 → 条数与「下标只 start 一次」
   两条响）。三条里有一条从没响过，就等于它从没被证明在工作（[第 23 条](23-untested-guard.md)）。

**这是「断言必须钉在括号上」的姊妹条**（[第 23 条](23-untested-guard.md)与 #291 那一轮记的）：那一条说的是
断言要钉在**缺陷的形状**上，这一条说的是断言**至少要被执行到**。
