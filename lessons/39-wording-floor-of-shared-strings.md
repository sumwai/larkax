# 39 · 一个字符串被两个入口共用时，措辞的下限由**最窄的那个入口**决定

**编号** 39 · **日期** 2026-10-18 · **摘要**：同一句错误信息既经命令行、又经 HTTP 管理面
返回给使用者时，里面只能出现**两个入口都成立**的东西。命令名、`--参数` 写法、退出码、
文件路径这些只有命令行才有的词，会让另一个入口的读者读到一个它没有的东西。

**现象**

给渠道写入路径加一条校验（模型的目录声明与渠道的端点对不上就拒绝）时，很自然想写成：

```
larkaxctl channel create: --models 里有模型 "x" 这条渠道服务不了（渠道 type 是 openai）
```

这句话在命令行上读起来完全成立——使用者刚敲完那条命令，`--models` 与 `larkaxctl`
就在他眼前。**但同一个错误也由 HTTP 管理面返回**（命令行的 `create`/`update`
走的就是那个管理面），那边的调用方没有 `--models` 这个参数、也不认识 `larkaxctl`，
它拿到的是管理面请求体里的一个字段名。

这一处是在**设计时对照两个入口**发现的，没有落进代码；但它差一点就落了进去——
因为写这句话的时候，人正站在**最宽的那个入口**上。

**原因**

两个入口各自的词汇表不是同一个：

| 只有命令行才有的词 | 只有管理面才有的词 |
|---|---|
| 命令名（`larkaxctl channel create`） | 路由与 HTTP 方法 |
| `--` 前缀的参数写法 | 请求体里的字段名 |
| 退出码、usage 提示、`<参数>` 占位写法 | 状态码、响应头 |

而写法上的**下限由最窄的那个入口决定**：一句话要在两个入口都读得通，
就只能用两个词汇表的**交集**——数据本身的那些名字（字段名、模型名、端点、
枚举值、渠道 `type` 这类库里就有的东西）。

这与第 24 条是同一个形状的另一半：那条讲「同一件事在两处各做一次，
缺陷长在缝里」；这条讲**同一句话被两处共用**，缺陷长在措辞里，
而它不会报错——两边都能打印，只是有一边的读者读不懂。

**解决**

共用串里只写两个入口都成立的东西。具体到本仓：

- **可以写**：数据字段名（`models` 而不是 `--models`）、模型名、端点路径、
  渠道 `type` 的取值、库里的枚举值；
- **不要写**：命令名与子命令、`--` 前缀、退出码、usage/帮助文案、
  「请运行 …」「加 `-f` 重试」这类只对命令行成立的指令。

判断方法：把这句话**当成管理面响应体**读一遍。读不通就说明它写宽了。

**预防**

> 这句话还会在**哪儿**被打印出来？那些地方的读者手里有什么、没有什么？

新加一句对外的话（错误、日志里给人看的说明、警告）时问一次。
**把参数名与命令名统一起来是另一件事**（那是改所有入口的措辞），
与本条不冲突：先把共用串收进交集，再谈交集里的词要不要换。
