# 13 · 按文件类型限定检查范围，而不是继续补形态白名单

**编号** 13 · **日期** 2026-10-16 · **摘要**：假阳性集中在源码、真阳性集中在配置，按文件类型限定范围比继续补白名单更接近问题的根。

**现象**

第三次被同一类问题挡住：新写的 Anthropic 适配器里有一行

```go
PromptTokens:     inputTokens,
CompletionTokens: outputTokens,
```

赋值类模式报为「键名含 token、右侧是一长串标识符」。

**原因**

[第 12 条](12-shape-allowlist-false-positives.md)已经记过两次，结论是「逐个补前缀治标不治本」。这次验证了那个判断：
补到第三轮，白名单里已经有四条放行模式，全都只为了排除 Go 的字段访问语法。

而真正的观察是：**赋值类模式的假阳性只出现在源码文件里，真阳性只出现在
配置文件里**。两个分布几乎不重叠——凭证写在 Go 源码里的概率极低，
写在 `.env` / YAML / JSON 里的概率极高。

**解决**

不继续补形态，改成**限定生效范围**：赋值类模式只在
`.env`、`.yml`、`.json`、`.toml`、`.sh` 等配置与脚本文件上跑。
形态类（密钥前缀、私钥头、私有主机、本机路径、邮箱）不受限制——
那些在代码里出现同样意味着泄露。

顺带修掉一个一直没被发现的口子：键名与分隔符之间不允许收尾引号，
于是 `"password": "…"` 这种 JSON 写法**整条漏掉**。这个口子一直存在，
只是因为自测样本全是 `.env` 风格的无引号写法才没暴露。

自测从 38 条到 49 条，其中 11 条专门验证「同一个内容在源码里不报、
在配置里必报」。

**记录必须晚于修复**

这一轮里发生了一件顺带的事：记录[第 13 条](13-scope-by-file-type.md)的文档 PR 自己没能过红线检查。
文档里为说明问题引用了那段 Go 代码，而文档分支是从**修复之前**的 main
切出来的，所以旧规则照旧把它当凭证报。

处置是把文档分支 rebase 到修复之后的 main 上。值得记下的是顺序：
「修规则」与「记录这个规则为什么该修」是两个 PR，而后者引用的恰恰是
前者要消除的那个误报。同一件事的另一面是[第 9 条](09-fake-keys-blocked-by-push-protection.md)——那里的自测样本，
也是因为「写给工具看的东西，工具自己也会检查」而出问题。

**预防**

- 一个检查规则反复误报时，先问「它的假阳性集中在哪、真阳性集中在哪」。
  两个分布若能按某个维度干净分开，就用那个维度限定范围，
  而不是在规则内部继续加例外。
- **白名单的条数本身就是信号。** 四条放行模式全部服务于同一个目的
  （排除某种语法），说明判断维度选错了。
- 加文件类型限制的同时要检查：原本靠宽范围兜住的真阳性有没有漏。
  这次就漏了 JSON 的带引号键名，是补测试用例时发现的。

---
- **记录一个修复时，那个记录本身可能仍然被旧规则拦下。** 先合并修复，
  再让文档分支 rebase 到它上面；不要指望文档能豁免检查——
  文档里写一个真口令，形态上与配置文件里的没有区别。
