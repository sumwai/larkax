# 41 · 同名掩护可以被一次与它无关的重构拿掉

**编号** 41 · **日期** 2026-10-18 · **摘要**：`scripts/check-deadmethods.sh` 按**方法名**
数调用点，于是 `fmt.Printf(...)` 一直在掩护 `redisLogAdapter.Printf`。另一个 PR 把
`larkaxctl` 的 `fmt.Printf` 全换成 `fmt.Fprintf(humanStdout(), …)`，掩护消失，那个方法
露了出来——**在 main 上**，而不是在那个 PR 的分支上。

**现象**

PR 的 CI 全绿，合入之后 main 的同一道门红了：

```
✗ 新出现的「导出方法没有调用点」 —— 要么接线，要么加进白名单：
   internal/ratelimit/redis.go|redisLogAdapter.Printf
· 白名单里这几条已经不在扫描结果里了，可以删掉了：
   internal/money/money.go|Amount.Units
```

两条同时出现不是巧合，下面分开说。

**原因**

这道门的判据是**语法上的调用点**，而调用点名字取的是选择器的最后一段：`fmt.Printf(…)`
这一处的名字就是 `Printf`。`redisLogAdapter.Printf` 与它同名，于是算「有人调」——
脚本头注释里写着这件事，它本来就是这道门最主要的假阴性来源。

于是掩护的存活与否，取决于**全仓有没有任何一个 `Printf` 调用点**：`cmd/` 里换一个打印
函数，可以让 `internal/` 里一个从未被调过的接口实现从「有人调」翻成「没人调」。

**这跟改动本身对不对无关。** `fmt.Printf` 换成 `fmt.Fprintf(humanStdout(), …)` 是那个 PR
该做的（它要让输出能被打到别处），波及面却落在另一个包里。

**为什么 PR 的 CI 是绿的**

CI 跑在分支上，分支立在**合并那一刻的 main** 上。掩护它的那个调用点在改动落地的同一批
里、却由另一个 PR 合入，于是「先合的那个」把 main 推红。**门禁的分支绿不等于 main 绿。**
同一件事对门禁白名单也一样：白名单是**跟着 main 走的集合**，任何一次合并都可能让它与
现状不一致。

**解决**

一进一出，条数不变（25 / 上限 25）：

- `internal/money/money.go|Amount.Units` 出清单——**它是真的接上了**：`internal/pipeline`
  结算那一处按最小单位截总和（`settlement.Breakdown.Total.Sub(settlement.Actual).Units()`）。
  它在清单里已经陈旧了一阵子，而**陈旧条目只提示、不算失败**，所以没人被叫醒。
- `internal/ratelimit/redis.go|redisLogAdapter.Printf` 进清单，类型 `lib`：它实现 go-redis
  的 Logger 接口，由库自己的 goroutine 拨号失败时经接口回调，本仓没有也不该有调用点。

**不要为了把清单刷空而去硬接调用方**（第 22 条）——接一条假的比留着它更坏。

**预防**

> 这道门突然冒出一条**旧符号**时，先问「有没有同名的调用点刚刚消失」，而不是先怀疑那个符号本身。

几条具体的：

- 改一个**共用输出**的名字（`fmt.Printf` → `fmt.Fprintf(w, …)`、给日志加一层包装）会改变
  「调用点名字集合」，影响面按**名字**扩散，不按包。做这类替换时，心里要有这一步。
- 白名单的「陈旧条目只提示、不算失败」这条设计是有意的（陈旧的原因恰恰是有人把没门的
  东西接上了，那是好动作），但它也让**积压**无声：这一条要从「一进一出刚好持平」里被读出来，
  那正是它当时没被察觉的原因。
- 合并之后**在 main 上再跑一次门禁**，是唯一能照到「分支绿、main 红」的动作。CI 只在 PR 上
  跑，它答不了这个问题。

与第 31 条（结构体字段的死活门禁照不到）同族：都是**判据的口径**与「有没有人真的用」之间的
缝，而不是某一道门写错了。
