# 54 · 三道死代码门都不看常量

**编号** 54 · **日期** 2026-10-26 · **摘要**：仓库有三道死代码门，
分别管不可达函数、整包没人 import、导出方法没有调用点。常量不在任何一道
的判据里——`deadcode` 的输出结构只有函数，另两道按方法名与包名比对。
于是「导出常量一个引用点都没有」这件事，三条门一起也报不出来。

**现象**

用类型信息数了一遍全仓引用（`go/packages` + `go/types` 的 Uses 表，
不是 grep），筛出「生产文件里定义、全仓含测试没有任何引用点」的符号。
逐条人工核实之后剩下四个是真的：

- `internal/quota` 的 `UnitRequests` 与 `UnitMoney`——
  `channel_quota_state.unit` 可能取的值，但生产代码里没有一处拿它们
  做过判断；
- `internal/snapshot` 的 `typeBlob`——`blobPlaceholder` 走的是
  `type: blockType`，`fieldType` 从来不会是 `"blob"`；
- `internal/tokens` 的 `ShortInputNote`——二十几行注释解释「为什么它是
  文字而不是数字」，然后没有任何代码读它。

四个都跑过三道门：`check-deadcode.sh` 报 19 个不可达符号，全是函数；
`check-deadmethods.sh` 报 14 个导出方法；`check-unimported.sh` 的差集是
空的。三道门全绿。

**原因**

三道的判据都绕着「函数」写：

| 门 | 判据 | 结构上排除了什么 |
|---|---|---|
| `check-deadcode.sh` | `deadcode` 的 RTA 可达性 | 输出是 `Funcs []Function`，只有函数 |
| `check-deadmethods.sh` | 生产代码里有没有 `.Name(` 这处调用 | 只扫导出**方法** |
| `check-unimported.sh` | 仓库包集合减可达包集合 | 只看**整包**，包内符号一律不看 |

常量、变量、类型都没有落进任何一道。而这类符号「没人用」比函数更不容易
被发现：函数没人调，读代码的人会注意到；一个常量摆在那里，读的人默认
「肯定是给别处用的」——尤其是它的注释写着「这几个值是同一口径的判据」
的时候。

`UnitRequests` / `UnitMoney` 这一对特别值得看：注释说它们是判据，而真正
的判据是 `channel_quota_state.unit` 这一列的值，写入侧从库里读、
`selfAccount` 只拿 `UnitTokens` 比一次。另两个常量是**取值约定**，不是
调用点——它们的作用是让「money 该拼成什么样」只有一处出处。这类符号
在引用计数上永远是零，而删掉它会让人回头去抄字面量。

**解决**

区分「零引用且该删」与「零引用且该留」，判据是**删掉之后会不会有第二处
出处**：

- 该删：`typeBlob`。删掉之后 `blobPlaceholder` 的注释仍然解释得清
  「为什么不折进 fieldType」，没有信息丢失。
- 该留：`UnitRequests` / `UnitMoney`。删掉之后「money」这个拼法就只剩
  `channel_quota_state.unit` 的 COMMENT 和迁移里的字面量，而迁移不能
  引用 Go 常量。留的那一份注释要写清它为什么没有调用点。
- 该留：`ShortInputNote`。删掉之后那句话就只剩 `COUNTER.md` 里的一份，
  而代码读不到文档。

**没有为此加第四道门。** 加它要先划清「哪些常量该有调用点」——而上面
三条已经说明这个判断分类器做不了：同一个「零引用」，三种处置。加一道
需要白名单来吸收合法情形的门，白名单会一路长到没人看，那比没有门更坏
（与 `AGENTS.md` 里「白名单只许减不许增、不要为了刷空它硬接假调用方」
是同一条）。

**下次什么时候读**

改 `internal/quota` 的单位常量、`internal/snapshot` 的占位常量，或者
怀疑「有实现、没有调用方」而三道门都绿的时候。数引用要按类型信息数
（`go/types` 的 Uses），不要 grep：同名符号在不同包里互不相干，而接口
方法的调用点记在接口上——`Gateway.Chat` 在源码里一个直接调用都没有，
却每天都在跑。

同一轮里顺手修了 `internal/ledger/store` 的一处裸字面量（`Release` 里的
`status != "pending"` 改成走 `BillingStatusPending`）。那个包在变异清单里，
按 `check-mutation.sh` 的默认行为要跑**整包**：十几个生产文件，我要验的那
一行在其中最大的那个文件里，排在它前面的文件跑完花了近半小时、杀了几百个
变异体，一个都没到那一行。

停掉，改用 `--changed-from main`。收窄之后 gremlins 的 `--exclude-files`
排掉了全部未改动的文件，只变异改过的那一个。分数按改动收窄，脚本自己会打
一行说明它**不可与整包基线对账**——那句话是对的，也是这次该付的代价：
整包那一轮回答的是「这一包的测试强度有没有变」，而这条改动要问的是
「这一行有没有被钉住」。

判据是「**这道门可能因为这次改动而失败吗**」，不是「这个包在不在清单里」。
一个包在清单里，只说明它属于搬钱的代码、值得定期看测试强度；不等于说
改其中一行也要连带重跑全部文件。两条问题分开问，代价差一个数量级。
