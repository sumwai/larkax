# 38 · 迁移编号靠「先发后写」，而扫盘面看不见已分配但未落盘的号

**编号** 38 · **日期** 2026-10-18 · **摘要**：两条分支同时从 main 起、各自要加一条迁移时，
「盘面上现有的最大号 + 1」会算出**同一个号**——因为另一条已经占掉的那个号**还没有文件**，
扫分支、扫工作树、扫 `git log --all` 全都看不见它。

**现象**

两条分支各自要加一条迁移，两条都从 main 起。按「盘面上最大号 + 1」挑号，
两条都会挑中同一个号，而**在任一条分支上都无法察觉**：

- 扫工作树：另一条在别的工作树里，而且它可能压根还没写文件；
- 扫分支（`git ls-tree` 每一条）：另一条的分支上也还没有那个文件——**号是口头占的**；
- 扫 `git log --all`：同上，没有提交就没有痕迹。

于是这个号在盘面上「谁都没用」，在实际分配上「已经被用掉了」。

**原因**

「占号」与「文件存在」之间有**一段时间差**。这段时间里号已经分配出去，
而盘面上没有任何可扫的痕迹。所以「盘面最大号 + 1」只在「没有别人同时在加迁移」时成立——
那是一个**会随协作状态变化而失效的前提**，而它失效时两条分支各自都是绿的
（同第 25 条：两条分支各自的 CI 都绿，合起来不绿）。

它比「号挑错了」更难发现的地方在于：**扫盘面的那些命令都真的跑了，也都真的什么都没找到。**
「找不到」在这里是**正确的输出**，不是证据缺失——所以再加一道「扫得更全」的扫描器
也解决不了它，被判据本身的方向错了。

**解决**

把号变成**先发后写**，三层各管一件事：

1. **号由协调的人统一发**，发在哪条分支就是哪条。总账里记的是「哪条分支拿了哪个号」，
   而不是「盘面上有什么」——后者照不到已发未写的那一段。
2. **盘面扫描仍然有用，但它是第二道**：它抓的是「有人没按发的号写」。
   它的边界要写清楚，否则下一个人会以为「扫过一遍、没撞」就等于「没撞」。
3. **兜底是一次全量 `up → down → up`**，在 rebase 之后跑。两条分支都进 main 之后，
   CI 那道迁移往返拿的是**合并后的树**，撞号在那一步躲不掉（goose 会因为版本重复直接报错）——
   只是发现得晚，那时两边都已经写完。

**预防**

> 这个号是**谁**定的？我是**查**出来的还是**被发**的？

凡是「靠扫描现状推出来的唯一标识」，都要问一句它依赖的现状**是不是完整的**。
同类的还有：从目录里推下一个序号、按现有文件推新文件名、按盘面推端口号
（本仓测试库的端口就是按工作树各分一个，同一个理由）。

加迁移前的固定动作：**先问号，再写文件**；rebase 之后跑一次全量往返。
