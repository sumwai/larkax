# 10 · `--all` 只扫已跟踪文件，新增文件成了自查盲区

**编号** 10 · **日期** 2026-10-16 · **摘要**：`--all` 用 `git ls-files` 只列已跟踪文件，新写的文件恰好在最需要自查的时刻不在范围内。

**现象**

红线自查脚本在本机报「通过」，CI 上同一个脚本却报出 8 处命中。

**原因**

`--all` 分支用的是 `git ls-files`，它只列**已跟踪**的文件。而新写的文件在
推送之前还没 `git add`，于是：

```
本机：  ./scripts/check-redlines.sh --all   → 干净（新文件不在列表里）
CI：    bash scripts/check-redlines.sh --all → 命中（文件已在提交里）
```

这个盲区的形状很讨厌：**自查恰恰在最需要它的时刻失效**——改动越新、
越是没被看过的代码，越不在扫描范围内。而「本机通过」这个结论会让人
放心地提交，等到 CI 报出来时改动已经进了历史。

**解决**

改成 `git ls-files --cached --others --exclude-standard`：
`--others` 带上未跟踪文件，`--exclude-standard` 仍然尊重 `.gitignore`
（否则会去扫 `node_modules` 与构建产物）。

补了一条专门的回归用例：在一个**只有未跟踪文件**的目录里跑 `--all`，
必须命中。

**预防**

- 自查工具的范围要覆盖「将要提交的」，而不是「已经提交的」。
  两者的差集正是最该被检查的部分。
- 本机跑得过、CI 跑不过时，先怀疑**两边看到的输入不同**，
  而不是急着改代码去迎合 CI。
- 新增一个包之后立刻在**未 add** 的状态下跑一次自查，
  这是唯一能暴露这类盲区的时机。
