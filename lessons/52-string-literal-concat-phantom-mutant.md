# 52 · 字符串字面量之间的 `+` 会白送一个编不过的变异体，还改掉分母

**编号** 52 · **日期** 2026-10-26 · **摘要**：一句报错被拆成 `"前半" + "后半"` 两行写，
算术类变异器把那个 `+` 换成 `-`。拼出来的表达式编译不过，工具却把它记成 KILLED，
`Not viable` 还是 0——`killed` 与候选总数一起变大，两轮数字从此不可比。

**现象**

`internal/payment` 整包变异，两轮之间 `killed` 从 151 变到 157、候选总数从 163 变到
164。多出来的那一条落在 `fmt.Errorf` 的错误文案上：一句话写成了两个字符串字面量
相加，变异点就是两个字面量之间的 `+`（`ARITHMETIC_BASE`，`service.go:450:113`），
参数换成 `-`。那一版根本编译不过，报告里却算进 KILLED，`Not viable: 0`。

没有任何断言抓过它。抓不到却记成「杀掉」，就是**空杀**。

**原因**

三件事叠在一起：

- **变异器只看运算符的形态**。字符串拼接收 `+` 与整数加法收 `+` 对它没有区别。
  真正需要拼接的代码（比如拼 SQL）落在这里是一条正常变异体；只是把长文案拆行时，
  它变成一条不可达的变异体。
- **不可达在报告里不是一个独立的桶**。编不过的变异体既不算「测试抓到」，也不进
  `Not covered`，而是被计进 `killed`。于是「killed 涨了」既可能是补了用例，
  也可能是多了一个编不过的变异点。
- **分母跟着变**。候选总数是四列之和，多一条空杀就多一个候选，efficacy 与
  「上轮 N → 这轮 M」全部失去可比性。

还有一层：这个拆分不是写代码的人手写的，是**派活消息里为了便于阅读**把它拆成两段
拼接的，接活的一方原样落了地。查「这是谁引进的」要顺着派活的文本查，别只看 diff
就归给提交者。

**解决**

1. 报错文案折回**一个字符串字面量**（文字逐字不变）。候选总数回到 163，空杀随之消失。
2. 读任何两轮的变异数字之前先核**候选总数**；分母不同时，`killed` 的差值不是进步。
3. 派活时不要替接活的一方把待落地的代码拆成拼接形式：给完整的一行，或给行号。

**自查**

- 新旧两轮的 `killed + 存活 + 超时 + Not covered` 对不上时，去变更里找跨行字面量拼接：

  ```sh
  git diff <旧基点> <新基点> -- '*.go' | grep -nE '^\+\s*"[^"]*"\s*\+\s*$|^\+.*"[^"]*" \+ "'
  ```

- 报错文案需要跨行时，用反引号原始字符串，或者写成一行——别用 `+` 接。

**关联**

- 第 49 条（报变异体数量不带列名与口径，同一个量会被当成另一个量）：本条给的是
  「分母为什么变了」的一种具体来源。
- 第 16 条（工具「没跑成」时看起来和「跑成了」一模一样）：空杀是它在变异报告里的近亲
  ——没有断言参与的「杀掉」，在表里与真的杀掉长得一样。
