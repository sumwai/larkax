# 18 · git 里两处「看着对了」的操作

**编号** 18 · **日期** 2026-10-17 · **摘要**：`commit` 只搬暂存区、`checkout --ours` 只搬一侧：操作成功不等于结果正确。

**现象**

同一天撞到两次。两次都是「操作完成、输出正常、代码也对」，而结果不对：

1. **`git add` 之后又改了文件。** 解合并冲突时逐块解完、`git add` 了，然后才改那两处
   文案。`git commit` 提交的是**暂存区**，不是工作树——推上去的 PR 里躺着的还是旧文案，
   而工作树看起来是「已经改好了」的。没有任何东西报错，`go build` 与测试全绿。
2. **`git checkout --ours <文件>` 会吞掉非冲突的改动。** 合并时用它整文件取一侧，
   它会连另一侧**非冲突**的改动一起丢掉。那次丢掉的是一句注释：main 把
   「这里记为零」改成了「这里跳过这一项（不放进明细）」，而代码三侧都是 `continue`，
   所以 main 那句才是对的。丢掉的只有注释，同样不报错。

**原因**

两处的共同点是**判据用错了对象**：

- [第 1 条](01-private-content-in-repo.md)判的是「工作树对不对」——它是对的。该判的是「**提交里**对不对」。
- [第 2 条](02-grep-combined-flags-silent-miss.md)判的是「冲突解没解开」——解开了。该判的是「**与另一侧比，少没少东西**」。

git 不会替你做这两件事：`commit` 只搬暂存区，`checkout --ours` 只搬那一侧。
两者都**不报错**，因为它们的行为都是定义好的、没有歧义——只是与你以为的不是一回事。

**解决**

1. 提交之后立刻 `git status --short`，**输出为空才算提交完**。写成固定动作，
   与「开分支后 `git log --oneline main..HEAD | wc -l` 必须是 0」是同一类东西。
2. 整文件取一侧之前，先 `git diff --theirs -- <文件>` 逐行看丢的是什么，
   确认「丢掉的只有注释」再收工。更稳的做法是**逐块解**，而不是整文件取一侧。

**预防**

- **「操作成功」与「结果正确」是两件事**，而 git 的大多数操作只保证前者。
  凡是一次操作搬动的是「另一个位置的东西」（暂存区 vs 工作树、一侧 vs 另一侧），
  就要在操作**之后**去那个位置看一眼。
- 这与[第 16 条](16-silent-check-failure.md)是同一个形状：检查工具「没跑成」时看起来和「跑成了」一样。
  那里是测试被跳过，这里是 git 操作成功——共同点是**「没有信号」不等于「没有问题」**。
- 合并里被丢掉的如果只有注释，**编译与测试都不会报**。所以「测试全绿」不能当作
  「合并没丢东西」的证据。
