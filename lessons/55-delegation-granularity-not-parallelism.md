# 55 · 派给多个 agent 的活，慢在颗粒度不在并行度

**编号** 55 · **日期** 2026-10-26 · **摘要**：一次 workflow 有多慢，取决于**每个 agent
被要求答多细**和**收口压给了谁**，不取决于同时开几个。并发上限从头到尾没碰到，
而最慢的一条普查线决定了整条流水线的时长，最后一步又是一个 agent 吞下全部前序产出。

**现象**

一次调查四个维度（名词 / 动词 / 宾语 / 输出）的 workflow，8 个 agent：

| 环节 | 并发 | 耗时 | 转录体积 |
|---|---|---|---|
| 四条普查线 | 4 | 20 / 43 / 60 / 61 分钟 | 各 2.8–3.6 MB |
| 三条词表 | 3 | 24 / 26 / 47 分钟 | 各约 1 MB |
| 收口 | 1 | 34 分钟后仍未返回，被会话超时掐掉 | — |

全程 2 小时 22 分。并发是 4 → 3 → 1，而上限是 `min(16, CPU−2)`——**一次都没碰到**。

收口没回来还有一层后果：三份词表躺在 workflow 的 journal 里，主会话为了接着用，
还得先花几分钟去定位它们。

**原因**

四条，按贡献排序：

1. **任务书要求「穷尽且每条追到 `file:line`」。** 为了证明两个动词的语义差别，
   普查 agent 要翻 `internal/` 里的 SQL。四条线合计 103 条事实，代价是每人 3 MB
   上下。而主会话自己跑几条 grep 就得出了同一批结论——问「有没有规律」时，
   找到正反例就够了。
2. **阶段之间是全屏障。** 最早的普查线 20 分钟就完了，最晚的用了 61 分钟，差 41 分钟。
   下游要读齐上游全部产出，于是整条流水线被最慢的一条钉住——不是平均值。
3. **收口塞进了一个 agent。** 它要吞三份完整词表（约 64 KB）加全部约束。
   合并同义项、划边界、下结论本来就是主控的判断活。
4. **约束没定就起，档位没显式给。** 第一版 workflow 在约束确定前启动，
   三个阶段等于白跑；两个版本都没指定 effort / model，每个 agent 都继承了
   主会话的档位。

**解决**

起 workflow 之前过五条：

| 规则 | 怎么看出走偏 |
|---|---|
| **先看有多少东西**——几行命令答得完，自己答 | 任务里写「全部」「每一个」 |
| **按问题拆，不按材料拆**——后面的人要读前面全部，就是拆错了 | 非得等齐才能开工 |
| **收尾自己做**——合并、划线、下结论是自己的活 | 最后一步要吃前面全部结果 |
| **结果写成文件**——按说好的路径取，别去翻对话记录 | 得回头找结论在哪 |
| **没定清就别开工**——范围、取舍、交什么，先问 | 任务里还有「待定」 |

具体到派活这一侧，还有一条现成的判据（见
[`.claude/skills/larkax-workflow/SKILL.md`](../.claude/skills/larkax-workflow/SKILL.md)
第九节）：**一个 agent 只答一个能判对错的问题**。完成判据写不成「跑哪个命令、
看到什么算完」，这条任务就不用派了。

**注意「并行省不了串行依赖」**：上表第二行不是说不许分阶段。真存在全依赖时，
正确做法是把维度重新切一遍，让每个下游只吃自己那一片；做不到就让主线串行做掉。
把一件串行的事拆成几段再合起来，一秒都没省，还多付了启动成本。

**关联**

- 第 22 条（有实现、有测试、没有门）：同一类问题的另一面——那条讲「做完的事
  没有门守着」，本条讲「派出去的活没有形状约束」。
- 第 43 条（把「我想不出用例」当成「没有输入能区分」）：都是把**自己判断不了**
  包装成**已经判断过了**。那条交给分诊，本条交给一个吞不下的 agent。
- 第 49 条（报变异分数不带口径）：报「workflow 跑完了」却不报并发曲线与转录体积，
  读的人会以为慢在并行度上。
