# 35 · 用例里写死的「当前最大值」，会在它增长时无理由地红

**编号** 35 · **日期** 2026-10-17 · **摘要**：一条用例断言 notes 里出现
「最新的迁移版本是 **21**」。加一条迁移之后那个数变成 22，用例红了——而**被测的
函数一行没改**。它把一个由仓库自身增长驱动的数写成了字面量，于是红的理由与它
要证的事毫无关系。

**现象**

一条分支加了一条迁移（编号 22）。门禁在 `cmd/larkaxctl` 红：

```
--- FAIL: TestDoctorDatabaseCheckDoesNotCreateTheVersionTable (0.05s)
    doctor_test.go:60: 它仍然该报出二进制里的最新版本，
        实际 notes 是 ["二进制里最新的迁移版本是 22" "库里没有 goose_db_version 表：一条迁移都没跑过"]
```

这条用例要证的是「doctor 在一个空 schema 上只读、什么都没写」。它顺手断言了
那句 note 里的**版本号**，而那个号是写死的：

```go
if !strings.Contains(notes, "最新的迁移版本是 21") {
```

**原因**

那个数由**仓库自身增长**驱动：迁移文件的个数。它不是被测函数的性质，而是
「今天仓库里有几条迁移」的快照。每加一条迁移它都会变，而**变的那一刻，
被它钉住的代码一行没动**。

代价不是「修一行」本身，而是**排查方向被指向了错误的地方**：看到这条红的第一个
动作是去翻 `doctor.go`，翻完发现它没改，再回来想「是不是迁移加错了」，最后才
意识到是断言写死了。中间那几轮都在错误的地方。

**解决**

从**产生那个数的地方**现算，而不是抄一个快照：

```go
if want := fmt.Sprintf("最新的迁移版本是 %d", latestMigrationVersion(t)); !strings.Contains(notes, want) {
```

`latestMigrationVersion` 数的是内嵌迁移文件里最大的编号前缀。它与被测代码
**不是同一段实现**（那边走 goose 的解析，这边只数文件名），所以不是同义反复——
但它也**不是一道强判据**（goose 认不出的文件这里照样数得到），这一点写在注释里，
免得下一个人以为它守得比实际多。

一条都数不出来时直接 `Fatal`：那时「数不到」与「数出来是 0」在断言里长得一样
（见第 16 条）。

**预防**

> 这个断言里的数，是谁产生的？它会不会因为**别的地方**的改动而变？

会的话就从那个地方现算，别抄快照。同一形状的还有：枚举的个数、接口的方法数、
某个 `switch` 的分支数、文档里列出的包数或路径数。

这类断言有一个共同点：**它红的理由与它要证的事无关**。而「无关的红」比「红」更贵，
因为它先花掉一次排查。

**顺带记一笔：门禁红在别处是常态，不是异常。**

同一条分支的门禁第一轮红在上面这条，修完第二轮**又红在另一处**——那是跨包的
设置干扰（另一个包把 `settings.billing.default_asset` 改成了账本不认的品种，
而本包的装配要去读它）。两次红**都不是这条分支改出来的**。

所以门禁红了先分类再动手：

1. **我改的** —— 真修；
2. **别处的既有脆弱点** —— 它今天被我的分支撞上，但它不是我引进的；判断要不要
   在这一轮里一并修（修了会混进无关的改动，不修则这条分支推不上去）；
3. **本来就偶发** —— 找得到机制就修，找不到就重跑并记下来。

**别把「重跑一次绿了」当成「已修」**——那正是第 16 条说的「没跑成」与「跑成了」
长得一样，只不过换到了门禁这一层。
