# 19 · 测试夹具造出生产不可能出现的数据，新判据一上来就命中它

**编号** 19 · **日期** 2026-10-17 · **摘要**：夹具的零值时间戳在生产里不可能出现，新判据会把「夹具的假」当成「数据的真」报出来。

**现象**

给对账加了一类新 finding（`status='pending'` 且 `started_at` 早于一天的预留）
之后，一条与它毫无关系的用例挂了：

```
--- FAIL: TestReconcileAcceptsNormalSettlement
    预留中的钱包不该被报出来: [{... stale_reservation ... 请求 "req-…" 的预留自
    0001-01-01T08:05:43+08:05 起一直是 pending，已滞留 2562047h47m16.854775807s ...}]
```

**原因**

`billing_requests.started_at` 由 `SaveReservation` 写成 `RuleMatchedAt`，而测试
助手 `reservation()` 从来不设它，于是那一行的时间戳是**公元 1 年**。生产里它
永远是预留当时的墙钟（pipeline 从 `p.now()` 取），所以这个值在库里不可能
出现——它是夹具造出来的。

新判据一上线，这些夹具行**全部**命中：任何一条留在库里的 pending 预留都算
「陈旧」。用例挂掉只是它最显眼的一面；更隐蔽的一面是同一行报出来的数字——
时间差超过 292 年，超出 int64 纳秒能表示的范围，`已滞留` 那一栏溢出成了
`2562047h47m16.854775807s`，一串没有意义的字符。

**解决**

1. `reservation()` 助手显式给 `RuleMatchedAt: time.Now()`，与
   `pipeline.Reserve` 走同一条路。需要陈旧数据的用例自己把它拨回去
   （`reconcile_test.go` 的 `reserveAt`）。
2. 没有给判据加「值太老就不算数」的例外：那是在为假数据打补丁，
   真数据走不到那里，补丁反而会把真的畸形值一起挡掉。

**预防**

- **给某一列加判据之前，先问：夹具给这一列填的是什么？** 夹具与生产走两条路
  的地方，新判据会把「夹具的假」当成「数据的真」报出来，而挂掉的是别的用例。
- 夹具里的零值时间、空字符串、0 号 id 都是「库里不可能出现的值」，而它们恰好
  是新判据最容易命中的地方。
- 报错信息里的数字也要读：`2562047h…` 是溢出，不是「滞留了很久」。
