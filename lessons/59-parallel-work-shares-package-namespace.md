# 59 · 并行派出去的活各自绿，合起来编译不过：包级名字是共享资源

**编号** 59 · **日期** 2026-10-28 · **摘要**：两条任务分给两个执行者、改同一包的不同文件，
各自的检查都绿，合流时整个包编译不过——因为 Go 的包级标识符是共享资源，而它不体现
在文件名上。「文件不重叠」不构成并行的充分条件。

## 现象

一个包要加一条新路径，拆成两条任务并行派出去：

- 任务 A 在 `api.go` 里定义一个判断函数 `foo`；
- 任务 B 在 `stream.go` 里定义一个包装器类型 `foo`。

两条任务改的文件不重叠，各自跑自己包内的 `go build` / `go test` 都是绿的——
A 完成时 B 还没落盘；B 进场时 A 已经提交，但 B 只跑了它自己那部分检查。

合流时整包报：

```
stream.go:151:10: foo (function) is not a type
stream.go:189:6: foo redeclared in this block
	api.go:812:6: other declaration of foo
```

## 原因

- **包级名字是共享资源，但它不体现在文件名上。** 派活时看「我们改的文件不一样」就
  以为不冲突，这是把文件当成了隔离单元。
- **各自绿的检查是真的绿**：A 跑的时候 B 还不在树上；B 跑的可能是包内子集，或者它
  检查时 A 的改动还没进它看到的树。两边都没说谎。
- **没有一方能看到合流状态**：A 不知道 B 会起什么名，B 进来时未必重跑全包。

## 判据

> **并行的前提是「不共享可变资源」，不是「不共享文件」。** 同一包里两个执行者
> 共享的是**包级名字空间**——它是可变的，而且冲突只在合流时才看得见。

派活时两条做法，任选其一：

- **划名字空间**：任务书里给「新标识符的前缀」（如 `nativeStream*`、`nativeReq*`），
  两边各用各的。这比「你们小心别撞名」可靠——后者需要每个执行者知道对方会起什么名，
  而它不知道。
- **不并行**：同一包里顺序做。判断标准是「会不会新增包级标识符」，不是「文件是否重叠」。

## 预防

- **合流点必须由派活的人自己跑一遍整包检查**，不能只收各方回报的「我这边绿」。
  这一条不是可选的：两个执行者的检查覆盖面在设计上就不包含对方的产物。
- 派活时把「本任务会新增哪些包级标识符」写进任务书。写不出来，说明这活还没想清楚。
- 合流后如果编译过但行为不对，看第 24 条与第 32 条——那是**语义**层面的缝，
  本条是**编译期名字空间**层面的缝，两种缝的检查动作不一样。

## 关联

- 第 24 条（缺陷长在两处之间的缝里）：同族的「缝」，但那条缝在语义边界上、两处
  各自有用例也测不出；本条的缝在编译期，一旦合流就会响。
- 第 32 条（共用函数的判据改了，另一条调用路径还钉着旧行为）：共享的是函数语义，
  本条共享的是名字。
- 第 55 条（多 agent 的活慢在颗粒度与收口）：那条讲并行度的收益，本条讲并行的
  前提条件。并行不是免费的，代价之一是合流点必须自己验。
