# 32 · 共用函数的判据改了，另一条调用路径还钉着旧行为

**编号** 32 · **日期** 2026-10-17 · **摘要**：改一个被两条路径共用的函数的**判据**之前，先把调用方数一遍；而两条路径要的**是不是同一件事**，决定了是「跟着改」还是「拆开」。

**现象**

`#338` 给 `catalog.Catalog.UpstreamModel` 加了一条新判据：规范名在任何作用域下
都没有别名时，原样返回规范名，而不是报 `ErrAliasNotFound`。理由是大多数部署
一条别名都没配（规范名与上游名逐字相同），「查不到就报错」会把它们每一次请求
都打死。

这个函数**早就有另一个调用方**：`cmd/larkaxctl` 的 `alias resolve`。它那条用例
钉着旧行为——「没有别名的规范名应当报错」。于是门禁直接红：

```
--- FAIL: TestAliasResolveMissing (0.06s)
    alias_test.go:422: 没有别名的规范名应当报错
```

**那条用例是唯一会喊的东西。** 请求热路径那边全是新写的用例，钉的是新判据；
两道白名单门（`deadcode` / `deadmethods`）看的是「有没有调用点」，判据变了它们
照过；契约测试看的是对外响应的形状，`model` 字段仍是调用方要的那个名字，也不响。

**判据**

改一个函数的**判据**（不只是改实现、加参数、改性能）之前，先 `grep` 一遍它的
调用方。改实现时调用方通常不受影响；**改判据时每一条调用路径都要重新判一次**。

**处置方向：先问「这两条路径要的是不是同一件事」**

两种走法都现成，而选错的代价是把一处**故意的耦合**当成巧合拆掉：

- **拆开**（给热路径另加一个方法，让原函数保持旧语义）：适合两条路径要的确实是两件事。
- **跟着改**（改另一条路径的判据与它的用例）：适合它们要的是同一件事。

这里是后者，而且**代码自己写着**：`runAliasResolve` 的注释说它调的就是选路那
同一条查询，「不另写一条：两处各写一份时，漂移的表现是同一次请求，选路与计费
用了两个上游名」。那处耦合是**故意的**——拆开才是引入漂移。

所以最终改的是 CLI：一条用例拆成两条，一条钉「一条都没配」退出码 0 且打印规范名，
一条钉「配过但没覆盖这个渠道」仍报错。

**怎么识别「故意的耦合」**：去看被共用那个函数的调用点旁边有没有注释解释
为什么共用。有——那就是判据的一部分，别拆。

测试**，这一条是**缝里有测试，而它是唯一会喊的**。
