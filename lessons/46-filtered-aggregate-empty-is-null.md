# 46 · 带 FILTER 的聚合，「没有匹配的行」与「和为 0」是两件事

**编号** 46 · **日期** 2026-10-22 · **摘要**：给聚合加了 `FILTER (WHERE ...)`
之后，一行都不匹配时 `SUM` 返回的是 **NULL**，不是 0。这一列扫进 Go 的非空类型
（`int64`）会让整条查询失败，而失败发生在**取候选渠道**这一步——每个请求 500。

**现象**

门禁里 `internal/assembly` 与 `internal/channels` 两包全红，几十条 e2e 一起挂：

```
取可用渠道失败: 读取渠道行失败: sql: Scan error on column index 16,
name "cost_events": converting NULL to int64 is unsupported
```

单看这句像是在说 Go 扫描，其实问题在 SQL：读侧为了按模型取成本，把聚合改成了

```sql
SUM(r.cost_events) FILTER (WHERE r.model = $1) AS cost_events
```

对一个**只有合并行**（`model = ''`）的老渠道，这一组里没有任何行匹配
`r.model = $1`，`SUM` 就返回 NULL。同一句里 `requests` / `successes` 因为包了
`COALESCE` 没事，`cost` 与 cache 两列落的是 `sql.NullString` / `sql.NullInt64`
也没事——**只有这一列同时满足「可能整列为空」与「Go 侧接不住 NULL」**。

**原因**

聚合函数在空集上的返回值是 NULL，`FILTER` 只是换了个方式构造空集，不改变这条
规则；`COUNT` 是例外（空集给 0）。而「空集」在这里不是一个边界情况——升级之后
所有老数据、以及任何还没按模型写过成本事件的渠道，都落在这一格。

Go 侧的类型选择决定了后果的轻重：扫进 `int64` 是整条查询失败，扫进
`sql.Null*` 就只是一个需要判空的字段。

**解决**

1. 能给「没有行」一个合法含义的列，语义上它是 0（这里是「有成本事件的请求数」），
   就 `COALESCE(SUM(...) FILTER (...), 0)`。
2. 语义上是「没有数据」而不是 0 的列，别用 COALESCE 抹平——让它可空，Go 侧用
   `sql.Null*` 或 `*T` 接住，「没有数据」与「合计确实为 0」要分得开。
3. 补一条「只有合并行、没有任何模型行」的用例。这一类错在**需要库的用例整包跳过**
   时完全看不出来（见第 16 条），本地怎么跑都是绿的。

**预防**

- 写完一条带 `FILTER` 的 SELECT，对**每一列**问两句：「它可能整列为空吗？」
  「Go 侧接得住 NULL 吗？」两句都答「是」就是这一条。
- 别把「这一列在实际数据里总会有值」当理由——新加的维度在第一天必然处处是空集。
