# 63 · 两处取值不同不是缺陷的证据；核查之前先问「我查的地方对吗」

**编号** 63 · **日期** 2026-10-28 · **摘要**：看到「同一个量」在两处不一致，直接判它是分叉并给出
统一口径的修法方向——而那个差异是刻意的，两处取值相反正是它的设计理由。同一天还有它的四个镜像：
在一个必然找不到的地方核查，然后把「找不到」当成「不存在」；给别人一个**只有在我这棵树上
才查得到**的行号；一个**指向这棵树里根本没有的文件**的行号；以及**树名与行号各自都对、
却取自两个不同的 blob**。**五件都是同一个病：核查手段比结论弱。**

## 现象

### 一、把刻意的差异当缺陷

一层是「预留/渲染」的输入量估算，一层是「结算兜底」的输入量估算，两处口径不同。
我判它是分叉、要统一，并写了修法方向。

实际是刻意的。那个常量的注释原文：

> 同一个「包装开销」在两条路上的代价方向**相反**，所以它们刻意不是同一个数：
> 结算那条拿它去向用户计费，估高了就是一笔凭空费用，还按工具条数放大，所以取**下界**；
> 预留那条拿它去冻余额，估低了差额由平台承担，而结算按预留封顶，所以取**实测的那个数**。
> **两处共用一个数，必然让其中一边吃错方向。**

我看到的「不一致」，恰是它正确的原因。若按我的方向改，会把「怕多收」那一侧换成「怕少冻」的
常数，**代价方向正好反过来**。

### 二、在必然找不到的地方核查

别人报「某文档第 N 行有一句错话」。我在**主树** grep 不到，于是判定「它报了个不存在的问题」。
那句话一字不差地存在——**在另一个工作树的分支上**，是那一笔新增的内容。主树只有 `main`。

`grep` 返回空，与「这段文字不存在」，在输出里长得一模一样。

### 三、同一个下午，反过来又犯一次

上午刚因为「在主树查分支上的东西」收回一次判断，下午**自己引了一个行号，没说是哪棵树**：

> `internal/api/stream.go` 里有一句把归一化事件的输出丢掉，行号我写的是 `:364`。

对方在自己的树上 grep，`nativeSeen` 命中 **0** 次，回来说「这行不存在」。
它说得对——那句 `return p.inner.event(io.Discard, ev)` 在 gateway 那棵树的分支上，
两棵树同一路径的 blob 不同：

```
主树      nativeSeen 命中 0 次   blob 586fcb8
gateway 树 同一路径 命中 5 次   blob aaf3ffeb
```

**上午我查错了地方，下午我给了别人一个查不到的地方。** 前两次是「我的核查无效」，
这一次是**我的引用无效**——对方照着做，只能得到「找不到」，而它无法分辨是它查错了
还是我说错了。

**这一段的例子本身后来被查出也配错了对**（见下面第五节）——而它正是用来立
「引用要带树名」这条规矩的地方。

### 四、同一条规矩的第三种形态：引用的文件在承载它的那棵树里不存在

同一天再往后，我在一条**文档**里引了一个 `文件:行号`：`native_stream_test.go:59x`，
想举例说明「变异之后失败输出长什么样」。

两个问题叠在一起：

1. **`59x` 是我留的占位符没填**——`x` 让一个该是数字的地方读起来像「脱敏」。
   脱敏与漏填在文本上同形，而读者会按前者理解，于是不会去问「这里到底几」。
2. **那个文件在承载这条引用的树里根本不存在。** 那条教训所在的分支只动了
   `LESSONS.md` 索引与教训正文，没有任何 `internal/` 下的改动；
   `git ls-tree origin/main internal/api/ | grep -c native_stream` → **0**。
   同一路径的文件在另一棵树（另一个分支）上才刚刚被创建。

第三种比前面两种更难发现：**「没说是哪棵树」至少还给了读者一个可以去找的地方；
「行号指向的文件在这棵树里不存在」连找的地方都没有，而它长得像一个合格的坐标。**

### 五、最难受的一种：立在规矩的那一段，自己把行号与 blob 配错了对

这一条写出来**当天**，实现方回去核上面第三节——它发现那段例子内部不自洽：

| 引用 | 实际 |
|---|---|
| 「`internal/api/stream.go:364` 会把归一化事件的输出丢掉」 | `aaf3ffeb` 的 `:364` 是 `if ev.Kind == "usage_input" && …`，与「丢掉输出」毫无关系 |
| 那句在 `aaf3ffeb` 里的真位置 | `:368`（`return p.inner.event(io.Discard, ev)`） |
| `:364` 属于哪个 blob | `61e1e5c9` —— 另一个分支上的另一版 `stream.go` |

**两个 blob 号都是对的**（`586fcb8` 确实命中 0 次、`aaf3ffeb` 确实命中 5 次），
**错的只是把它们与行号配成了对**——行号从 blob A 抄来，贴在了 blob B 旁边。

这比前四种都难受，理由有两条：

1. **它长在立规矩的那一段上。** 读者读到「引用要带树名」，紧接着照那个例子去
   `git cat-file -p aaf3ffeb` 看第 364 行，得到的是一句无关的话——于是他学到的
   不是这条规矩，是「这条规矩的作者自己也没照做」。
2. **带树名挡不住它。** 前四种靠「说清是哪个树」就能防住；这一种的树名是对的，
   错的是行号出自哪一版。所以这条规矩要补一句：**树名与行号必须同源**——
   要么两个都从同一个 blob 取，要么都别写。

现在这一段已经改成不带行号：那句代码本身是
`internal/api/stream.go` 里的 `return p.inner.event(io.Discard, ev)`，
它在两个 blob 里的位置不同（`:364` / `:368`），而那与这条例要讲的事无关。

## 原因

五件看起来不同，根因是同一个：**先有结论，再找支持它的证据**。

- 第一件：我先有「两处不同 = 分叉」这个预设，然后找到「两处确实不同」就收工，
  **没有问「它们为什么不同」**。
- 第二件：我先有「它可能记错了」这个预设，然后在一个能返回空的地方查，**把空当成了证明**。
- 第三件：我先有「这个行为已经写好了」这个预设，然后引了**写着它的那棵树**的行号，
  却没标出树——引用看起来精确，实际只对一个工作树精确。
- 第四件：我先有「这段失败输出值得举例」这个预设，然后从**另一个分支的屏幕上**抄了它，
  没问「这棵树里有这个文件吗」，也没把占位符填完——示例看起来具体，实际两个坐标全落空。
- 第五件：树名与 blob 都对，唯独行号是从**另一版**里抄来的。**每一部分单独看都有据，
  配在一起就没有。**

第二件更危险：它带着「我查过了」的权威感，而**核查位置本身是错的**。
第三件更隐蔽：**它把「我查对了」的责任转嫁给了读者**，而读者手上没有那份上下文。
第四件最省事：**它连「去找」这个动作都省掉了**——读者看到 `:59x` 只会以为是脱敏，
看到文件不存在只会以为自己打开错了分支。**两个错误互相掩护，谁都像是一个诚实的编辑痕迹。**

## 判断

### 差异怎么判

> 看到两处取值不同，先回答「**它们为什么不同**」，再决定它是不是缺陷。
> 答不出来时，那不是缺陷，**是你还没读懂**。

判据不是「一致就好」，是「**能说出为什么**」：

| 形态 | 判定 |
|---|---|
| 差异有书面理由（注释、文档的「已知偏差」节） | **不是缺陷** |
| 差异没理由，且两处后果方向**一致**（都说多收或都说少收） | 可疑 |
| 差异没理由，且没人知道它为什么这么写 | **缺陷候选** |

### 核查怎么判

> 核查一个行号、断言或引文之前，先问「**它应该在哪**」。

- 别人报的行号，**优先在它当时所在的树/分支核**，别在主树判它不存在；
- **自己报行号时带上树名**：`gateway 树:internal/api/stream.go:364`，不是裸路径。
  七个领域各有一棵 worktree，同一路径在两棵树里是两个 blob，裸路径等于没说是哪一份；
- **树名与行号必须同源**。两个都从同一个 blob 取，或者都不写。树名对、行号从另一版抄来，
  是最难查的一种：每一部分单独看都有据，配在一起就没有——而它长得比不写树名更可信；
- **引一个行号之前，先确认那个文件在承载这条引用的树里存在**。`git ls-tree <branch>
  <path>` 一次就够。文档、注释、教训条目都会进版本库，它们各自只活在**自己那个分支**上，
  而它引用的代码常常是另一个分支的新增内容；
- **描述失败输出这类会变的坐标，宁可不带行号**。读者要认的是那句话本身。
  留占位（`59x`、`TODO`）比写错更坏：它读起来像脱敏，不像漏填；
- 跨分支找用 `git grep <pattern> <branch>` 或 `git log --all -S'<那句话>'`，
  比在单个工作树的文件系统里 grep 可靠；
- **判定「某人记错了」之前，先穷尽「是不是我查的地方不对」**。这是门槛最高的一句，
  因为它要求先承认自己的核查可能无效。

## 解决

第一件：撤回修法方向，改为「**两边都不给数**」——既然两个口径不能合并（合并必有一边吃错方向），
那就让两边都落在「没有这个数」这同一个状态上。

第二件：在正确的树上重新核，确认那句话存在，并向被误判的一方明确收回。

第三件：改掉引用方式——**行号前面带树名**，并把它写进「核查怎么判」那一节。

第四件：**去掉那个行号**，只留失败文案本身，并说明「不带行号是有意的」。读者要认的是
那句话，不是它此刻在第几行；而它此刻在第几行，下次编辑就变了。

第五件：**把例子里的行号也去掉**，只留那句代码。它在两个 blob 里位置不同（`:364` / `:368`），
而那与这一条要讲的事无关——要读者认的是「同一路径在两个树上是两个 blob」，不是行号。

## 预防

- **改一个「看起来不一致」的地方之前，先 grep 它的注释。** 这个仓库把理由写在常量、
  函数、迁移文件的头部；`docs/api.md` 与 `contract/README.md` 各有一节「已知偏差」，
  **那就是刻意差异的清单**。
- **同一天同一个 issue 上改判据超过两次，停下来问实现方「我漏了什么」**，
  而不是再改一版。有效的那次正是这么做的：把「该归谁」「根因对不对」先反问，等核完再定方向。
- **问对方时，问「你有什么我没有的」，不要问「把我能核的替我核一遍」。** 有一次我发了十条消息
  追问六个问题，其中五个我自己一小时前就核完了；对方那份回话真正的价值，是它带来了三样我
  没有的东西（官方文档的反向样本、一个指针 vs 数值的不对称、几处会撞红的具体行号）。
  真正该问的只有「归谁」——而那是**我的分派决定**，不该等对方答复。
  **把分派决定伪装成「等对方核实」，是一种拖延。**

## 关联

- 第 60 条（判据写成手段）：同一天同一 issue，那条是**判据形态错**。
- 第 61 条（表格把两个含义塞进一列）：它的镜像——那条是**我合并了两个事实**，
  本条前半是**我把一个设计拆成了两个缺陷**。
- 第 62 条（夹具让代码成死代码）：同一天同一 issue。
- 第 58 条（三种「绿得没有信息」）：与本条同源，都是「**手上的东西不是证据**」。
  58 说自证测试证明实现满足自己、不证明正确；62 说夹具证明实现能处理这个形状、
  不证明上游会发这个形状。**更短的表述是「判据要来自被测对象之外」**——但这个说法合成之后
  就只剩口号了，两条各自的预防动作不同（58 是「把实现改坏，用例该红」，
  62 是「把夹具字段去掉，用例该仍绿」），所以仍是两条。
- 当天四个错形态各不相同：判据写成手段、表格合并两事实、夹具补齐兜底字段、差异当成缺陷。
  **前三个是工具/判据形态错，第四个是事实没核全就下结论**——它们不会以同一形状再犯。
- 第 57 条（契约里的现状句子要指得到代码）：同一族，都是「断言之前先找到它的出处」。
- 本条在当天还多出一例：把「某一条 issue 的一个域已经合入」当成「这条 issue 已经合入」。
  **与「在主树 grep 分支上的东西」是同一个错**——都是把一个局部当成整体。
- 同一句话的第三面：**引用不带树名**。前两面是「我核错了」，这一面是「我让别人核不到」。
  前两面伤的是我的判断，这一面伤的是别人的时间——而它看起来最像「我给了精确的信息」。
