# 63 · 两处取值不同不是缺陷的证据；核查之前先问「我查的地方对吗」

**编号** 63 · **日期** 2026-10-28 · **摘要**：看到「同一个量」在两处不一致，直接判它是分叉并给出
统一口径的修法方向——而那个差异是刻意的，两处取值相反正是它的设计理由。同一天还有它的镜像：
在一个必然找不到的地方核查，然后把「找不到」当成「不存在」。**两件都是同一个病：核查手段比结论弱。**

## 现象

### 一、把刻意的差异当缺陷

一层是「预留/渲染」的输入量估算，一层是「结算兜底」的输入量估算，两处口径不同。
我判它是分叉、要统一，并写了修法方向。

实际是刻意的。那个常量的注释原文：

> 同一个「包装开销」在两条路上的代价方向**相反**，所以它们刻意不是同一个数：
> 结算那条拿它去向用户计费，估高了就是一笔凭空费用，还按工具条数放大，所以取**下界**；
> 预留那条拿它去冻余额，估低了差额由平台承担，而结算按预留封顶，所以取**实测的那个数**。
> **两处共用一个数，必然让其中一边吃错方向。**

我看到的「不一致」，恰是它正确的原因。若按我的方向改，会把「怕多收」那一侧换成「怕少冻」的
常数，**代价方向正好反过来**。

### 二、在必然找不到的地方核查

别人报「某文档第 N 行有一句错话」。我在**主树** grep 不到，于是判定「它报了个不存在的问题」。
那句话一字不差地存在——**在另一个工作树的分支上**，是那一笔新增的内容。主树只有 `main`。

`grep` 返回空，与「这段文字不存在」，在输出里长得一模一样。

## 原因

两件看起来不同，根因是同一个：**先有结论，再找支持它的证据**。

- 第一件：我先有「两处不同 = 分叉」这个预设，然后找到「两处确实不同」就收工，
  **没有问「它们为什么不同」**。
- 第二件：我先有「它可能记错了」这个预设，然后在一个能返回空的地方查，**把空当成了证明**。

第二件更危险：它带着「我查过了」的权威感，而**核查位置本身是错的**。

## 判断

### 差异怎么判

> 看到两处取值不同，先回答「**它们为什么不同**」，再决定它是不是缺陷。
> 答不出来时，那不是缺陷，**是你还没读懂**。

判据不是「一致就好」，是「**能说出为什么**」：

| 形态 | 判定 |
|---|---|
| 差异有书面理由（注释、文档的「已知偏差」节） | **不是缺陷** |
| 差异没理由，且两处后果方向**一致**（都说多收或都说少收） | 可疑 |
| 差异没理由，且没人知道它为什么这么写 | **缺陷候选** |

### 核查怎么判

> 核查一个行号、断言或引文之前，先问「**它应该在哪**」。

- 别人报的行号，**优先在它当时所在的树/分支核**，别在主树判它不存在；
- 跨分支找用 `git grep <pattern> <branch>` 或 `git log --all -S'<那句话>'`，
  比在单个工作树的文件系统里 grep 可靠；
- **判定「某人记错了」之前，先穷尽「是不是我查的地方不对」**。这是门槛最高的一句，
  因为它要求先承认自己的核查可能无效。

## 解决

第一件：撤回修法方向，改为「**两边都不给数**」——既然两个口径不能合并（合并必有一边吃错方向），
那就让两边都落在「没有这个数」这同一个状态上。

第二件：在正确的树上重新核，确认那句话存在，并向被误判的一方明确收回。

## 预防

- **改一个「看起来不一致」的地方之前，先 grep 它的注释。** 这个仓库把理由写在常量、
  函数、迁移文件的头部；`docs/api.md` 与 `contract/README.md` 各有一节「已知偏差」，
  **那就是刻意差异的清单**。
- **同一天同一个 issue 上改判据超过两次，停下来问实现方「我漏了什么」**，
  而不是再改一版。有效的那次正是这么做的：把「该归谁」「根因对不对」先反问，等核完再定方向。
- **问对方时，问「你有什么我没有的」，不要问「把我能核的替我核一遍」。** 有一次我发了十条消息
  追问六个问题，其中五个我自己一小时前就核完了；对方那份回话真正的价值，是它带来了三样我
  没有的东西（官方文档的反向样本、一个指针 vs 数值的不对称、几处会撞红的具体行号）。
  真正该问的只有「归谁」——而那是**我的分派决定**，不该等对方答复。
  **把分派决定伪装成「等对方核实」，是一种拖延。**

## 关联

- 第 60 条（判据写成手段）：同一天同一 issue，那条是**判据形态错**。
- 第 61 条（表格把两个含义塞进一列）：它的镜像——那条是**我合并了两个事实**，
  本条前半是**我把一个设计拆成了两个缺陷**。
- 第 62 条（夹具让代码成死代码）：同一天同一 issue。
- 第 58 条（三种「绿得没有信息」）：与本条同源，都是「**手上的东西不是证据**」。
  58 说自证测试证明实现满足自己、不证明正确；62 说夹具证明实现能处理这个形状、
  不证明上游会发这个形状。**更短的表述是「判据要来自被测对象之外」**——但这个说法合成之后
  就只剩口号了，两条各自的预防动作不同（58 是「把实现改坏，用例该红」，
  62 是「把夹具字段去掉，用例该仍绿」），所以仍是两条。
- 当天四个错形态各不相同：判据写成手段、表格合并两事实、夹具补齐兜底字段、差异当成缺陷。
  **前三个是工具/判据形态错，第四个是事实没核全就下结论**——它们不会以同一形状再犯。
- 第 57 条（契约里的现状句子要指得到代码）：同一族，都是「断言之前先找到它的出处」。
- 本条在当天还多出一例：把「某一条 issue 的一个域已经合入」当成「这条 issue 已经合入」。
  **与「在主树 grep 分支上的东西」是同一个错**——都是把一个局部当成整体。
