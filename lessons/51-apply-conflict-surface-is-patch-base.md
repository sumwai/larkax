# 51 · 重放补丁时，「哪些文件会撞」要比的是补丁基点，不是两版 main

**编号** 51 · **日期** 2026-10-25 · **摘要**：`git apply` 的 pre-image 取自
**补丁基点**里的那份文件。所以「这条补丁落到新 main 上会撞哪些文件」要比的是
**补丁基点 → 新基点**之间的差异；比「上一版 main → 这一版 main 改了什么」得到的是
另一个问题的答案——而它看起来同样合理。

**现象**

一条叠在未合分支上的补丁要换到新 `main` 重放。重放前估冲突面，估出来 7 个文件，
其中两处被点名「这里一定会撞」；实际 `git apply --3way` **零冲突**，一处也没撞上。

反过来也出现过：点名的那两处里，有一处两边**逐字节相同**——它根本不在冲突面上。
另一个文件反而是真重合，却没人提。

**原因**

两种 `git diff` 回答的是不同问题：

- ❌ `git diff --name-only <上一版 main> <新版 main>` ——「新版 main 带来了哪些改动」。
  它把「这条分支相对上一版 main 的改动」和「补丁基点里那份文件」混为一谈。
- ✅ `git diff --name-only <补丁基点> <新基点>` —— 只有在这两个点之间变过的文件，
  补丁的 pre-image 才与它预期的不一样，才有撞的可能。

**个数可以碰巧相同，成员不同。** 那次两种算法各自都得到 7 个文件，光看个数一模一样，
差别只在成员——所以「数一数对不对得上」这种核法在这里完全无效，必须取交集或直接
`diff` 两个文件集。

`--3way` 也解释了另一半现象：它在内存里按 blob 做三方合并，pre-image 与补丁预期
**逐字节相同**的文件，等于原地不动，无论别的文件怎么变都不会冲突。

**自查**

重放前，把真实冲突面算出来：

```sh
git diff --name-only <补丁基点>..<补丁 head> | sort > /tmp/patch.txt
git diff --name-only <补丁基点> <新基点>        | sort > /tmp/base.txt
comm -12 /tmp/patch.txt /tmp/base.txt            # 两个集合的交集 = 可能的冲突面
```

再逐文件判一次：`git rev-parse <补丁基点>:<path>` 与 `git rev-parse <新基点>:<path>`
**相等** ⇒ pre-image 原地不动，这个文件不会冲突。

**这是充分条件，不是必要条件。** blob 不等也不一定冲突——两边改动落在不相邻的区域时，
`--3way` 能干净合上。把「blob 相同」与「不冲突」说成等价命题，就又是一条看起来很像
真的判据，正落进本条要防的那一格。

**教训**

判「两条分支改同一处」，要比的是**两边相对同一个基点的改动**，不是「两条分支各自
相对自己上一版改了什么」。用错基点时，得出的清单个数合理、文件名合理，只是在错的
那一维上——比一张空清单更危险，因为它支撑得起一个决定。

预演过的补丁也不能全信：干跑时解出来的冲突，只对干跑用的那个基点成立。基点一换，
冲突面要重算。

**关联**

- 第 25 条（两条分支各自的 CI 都绿、合起来不绿）：同一类「换基点时两边的前提互相改变」，
  那一条讲的是代码，本条讲的是「怎么判断哪两处前提会碰」。

  那一条的代价进的是提交历史，本条进的是判断。
