# 40 · 任务书写的是意图，不是现状——建对象之前先核对库

**编号** 40 · **日期** 2026-10-18 · **摘要**：一条迁移照任务书的要求建了一张表，
而那张表在更早的一条迁移里**已经建好**（形状正好够用）。撞上的是
`relation "plugin_kv" already exists (SQLSTATE 42P07)`。

**现象**

任务书上写着「加一张插件私有的键值表」。照这个描述写出来的迁移是
`CREATE TABLE plugin_kv ...`——而 `00003_plugin.sql` 里已经有这张表：
主键 `(plugin_key, user_id, key)` 正好就是需要的那层隔离，到期列与部分索引也都在。
跑迁移撞上的是

```
relation "plugin_kv" already exists (SQLSTATE 42P07)
```

`42P07` 就是 `duplicate_table`。这道错会在 CI 那道**迁移 up→down→up 往返**里现形，
而那时提交已经推出去了。本仓的 `CREATE TABLE` 一律**不写** `IF NOT EXISTS`
（全仓 40 处，0 处带它），所以这条错一定会报出来——这是有意的，见下。

**原因**

任务书描述的是**意图**，不是**现状**。「加一张表」这句话里没有被回答的是：
库里现在有几张表、叫什么、形状够不够用。它回答的是「我们要什么」，
照它写就是用想象代替核对。

这与第 33 条（夹具按想象造、真实形状不同）是**同一族**：两处都是照着描述写、
没去核对当时的事实。区别只在核对的对象——那里是「真实的响应长什么样」，
这里是「库里现在有什么」。

**解决**

建对象之前先问**库**，不是先问任务书：

- 建表 / 建索引 / 加列之前，先 `\d+ <表名>`，或翻一遍 `internal/migrate/sql/`
  下已有的迁移（`grep -n '<表名>' internal/migrate/sql/*.sql`）；
- **已经存在且够用** → 这条迁移就不该存在：删掉那个文件，在 PR 里说明为什么没有它；
- **已经存在但不够用** → 那条迁移是 `ALTER`，不是 `CREATE`。

**不要用 `IF NOT EXISTS` 绕过。** 它把「已经有了」这件事静默咽掉，而这次恰好是同一个
问题的另一面：如果那张表早就有、但形状不对，`IF NOT EXISTS` 会让你以为已经建好了，
然后一路跑到某个查询报「列不存在」——那时离现场已经很远。
写不写 `IF NOT EXISTS` 不是风格问题：本仓 `DROP` 一律带 `IF EXISTS`（回滚要能重复跑），
`CREATE` 一律不带（建的时候对象已经在了，是必须说出来的事）。**两个方向相反是有意的。**

**预防**

> 这句话说的是**要什么**，还是**现在有什么**？我怎么知道「现在有什么」？

任务书、issue 正文、上一轮的报告都属于前者——它们描述意图。
凡是「按它说的去建 / 去改一个**可能已经存在**的东西」，都要落回一次对现状的直接查询。
建对象尤其容易中：`CREATE` 是**断言对象不存在**，而这句话该由库来回答。

**相关**：第 33 条（夹具按想象造，真实形状不同）——同族，核对的对象不同；
第 38 条（扫描的视野不完整）——那条是「扫了但看不见」，本条是「根本没扫」。
