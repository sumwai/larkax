# 28 · 限额覆盖了「一次调用」，而插件代码有三段

**编号** 28 · **日期** 2026-10-17 · **摘要**：限额绑在「一次调用」这个抽象上，就必然漏掉顶层求值与出参解码这两段插件代码。

**现象**

插件沙箱给插件调用设了三样东西：超时（带 `Interrupt`）、内存预算、出参字节上限。
独立审查逐处找了一遍**插件代码在哪里执行**，发现被兜住的只有其中一段：

- 模块顶层求值（`rt.Load`）**没有**超时——一个 `while (true) {}` 的顶层能让建会话
  挂住不返回；
- 出参解码（`UnmarshalWith`）跑在 `call()` 返回**之后**——而它会执行插件代码
  （值带 `toJSON` / getter / proxy 时按文本解码），于是那段代码既没有 deadline，
  当前调用的 ctx 也已经被清空；
- 修完前两处之后，review 又找出第三处：**超时被抛弃的那段顶层代码仍然活着**，
  它随后调宿主能力时拿到的是没有 deadline 的兜底 ctx。

三处同一个根因：**「插件代码」被当成了只有 `rt.Call` 那一段。**

**原因**

限额是**绑在一段代码的执行上**的，而「一次插件调用」对应**多处**执行：

```
建会话 → 顶层求值 ──┐
                     ├─ 都是插件代码
每次调用 → hook 本体 ─┘
        → 出参解码（toJSON / getter / proxy 也会跑 JS）
```

把限额挂在「调用」这个抽象上，就必然漏掉那些不在调用里的执行点。而漏掉的
表现很安静：**正常路径上一点异常都没有**，只有一个跑得久或分配得多的插件才会
显形——那正是最容易被当成「这个插件写得不好」而不是「宿主没兜住」的一类。

第三处的形状值得单独记：**「跑那段代码」与「清空当前调用的 ctx」不在同一个
goroutine 里**。清理写在调用方的 `defer` 上，而超时返回的那一刻调用方就返回了，
清理随之执行——可那个跑着 `Load` 的 goroutine 还在跑。它再去调宿主能力时，
槽已经空了，于是落到「没有 deadline 的兜底 ctx」上。**`Interrupt` 拦不住它**：
`Interrupt` 只在引擎的检查点生效，而调一个原生函数不是检查点。

**判据**

不要对「调用」问一遍，要对**每一处执行插件代码的地方**问一遍：

> 这段代码是谁写的？它跑在哪个 ctx 上？那个 ctx **有 deadline 吗**？
> 它分配的内存**谁在算**？它执行到一半被抛弃时，**谁负责让它停下来**？

最后两句是同一个问题的两面：**超时之后残余的代码，与正常跑完的代码，需要同样的兜底。**

**预防**

- **「清空当前调用的 ctx」必须与「跑那段代码」在同一个 goroutine 里**，两者写在
  同一个函数、拿同一个 ctx 参数。分成两处时，超时那条路上必然出现「槽空了而代码
  还在跑」。
- **预分配的容量跟着上限走，不跟着入参走。** 同一个包的另一处：日志字段的转换按
  「每个值」扣预算，而容器按 `len(keys)` 预分配——插件给一个百万元素的数组，写出来
  的日志行只有几百字节，宿主侧却为此分配了上百 MB。预算管到值、管不到容器，等于
  没管。
- 判断「限额够不够」时，先**把执行点列出来**，再逐个核对，而不是拿一个执行点
  的测试通过当证据（[第 23 条](23-untested-guard.md)：一个守卫没人钉住，等于它没被证明在工作）。
- 这类缺陷**修完再发**：本条记录的是原理与形状，具体的触发写法在插件系统接线
  之前不写进公开仓库——那时它等于一份攻击指南，而没有任何人正需要它。
