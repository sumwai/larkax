# 53 · 一条断言用子串匹配时，别的分支的报错也能满足它

**编号** 53 · **日期** 2026-10-26 · **摘要**：断言写「报错里含 `订阅 id`」，看着是在钉
「非法订阅 id」这条守卫，实际上下游自检的报错也含这四个字。守卫削弱之后用例照样绿，
修好之后也随时会被同一处报错重新满足——而是不是真有覆盖，只有红证能回答。

**现象**

变异轮把 `internal/ledger/transactions.go:420:22`（`SubscriptionID <= 0` 改成 `< 0`）
列进**存活**。这个位置上有用例：`plan_purchase_test.go` 的「没有订阅」传 0，期望报错含
`订阅 id`。第一反应该是「缺用例，补一条」。

把守卫改成 `<` 复现一次：交易照样建起来，那条用例仍然**绿**。守卫确实没拦住，但后面
那层自检报了另一句话——科目 `prepaid:0` 的订阅 id 不是规范写法（`account.go:472`）——
同样含 `订阅 id`。日志里于是同时出现「守卫没拦住」与「用例通过」。

**原因**

子串断言钉的是**字样**，不是**哪一条分支报的**。同一个词会出现在好几处报错里：守卫自己的、
下游自检的、数据库 CHECK 的。其中任何一处报出来都能满足它，于是「这个位置有覆盖」这个
结论没有依据。

所以存活清单上的一条，原因有三种而不是两种：没用例、**用例的断言太松**、等价变异。
第二种最容易被误诊成第一种，而照原样补第二条用例并不会比第一条更好。

这与 `internal/plans/purchase_mismatch_test.go` 开头那条规矩互为镜像：那里防的是
**排在前面**的分支先报（币种那条在真库上走不到，整条分支删掉都没人发现），本条防的是
**排在后面**的分支也报。两头都会让用例绿在该红的地方之外。

**解决**

- 断言钉**这一条分支独有的字样**：`订阅 id` → `订阅 id 非法`。
- 红证要**一条主张配一条**：改断言前后各复现一次变异体。改前绿、改后红，才说明新断言
  真的钉住了这条守卫；只看「改后红」分不清是断言起了作用，还是又一次被别的报错顺带满足。
- 写守卫自己的报错文案时带一个别的分支不会用到的限定词（「非法」「越界」「不能为空」），
  下游自检的文案就没法撞上它。

**自查**

读到一条存活，先看这个位置上**有没有用例**再决定怎么修：

```sh
# 位置上有用例吗（`-v` 日志里跑过、名字对得上哪种输入）
grep -rn 'SubscriptionID = 0' internal/ledger/*_test.go
# 断言用的那个子串，还有谁在报
grep -rn '订阅 id' internal/ledger/*.go | grep -v _test.go
```

红证的失败原文里要是出现了**另一处**的文案（不是这条分支自己那句），就是没钉住。

**关联**

- `internal/plans/purchase_mismatch_test.go` 开头那段注释：前面分支先报的同一类问题。
- 第 52 条（空杀）：两种「看起来被钉住、其实没有」的形态，一个在变异报告里，
  一个在断言本身。
