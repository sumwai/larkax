# 16 · 检查工具「没跑成」时看起来和「跑成了」一模一样

**编号** 16 · **日期** 2026-10-16 · **摘要**：检查类工具的成功信号是沉默，而它的失败模式也常常是沉默，两者在终端里长得一模一样。

**现象**

同一个形状在这个项目里出现了**五次**，每次都单独修了一遍才发现它们是同一个问题（第五次在 2026-10-28 补入）：

| 位置 | 「没跑成」的样子 | 「跑成了」的样子 |
|---|---|---|
| 红线扫描器 | `grep` 因参数错误退出码 2，被 `\|\| true` 吞掉 | 空输出，报「通过」 |
| 变异测试 | 并发过高导致 132 个变异判超时 | 真实的低分 |
| 集成测试 | 没有 DSN，`t.Skip` 让包返回 ok | `ok`，退出码 0 |
| golangci-lint | 工具版本旧，拒绝加载配置 | 退出码 0，「0 issues」 |
| **管道里的过滤器** | `go test ./... \| grep -E "FAIL"` —— 没有失败时 `grep` 退出码 **1**，被后面的 `echo` 冲掉 | 同一个空输出 |

**原因**

检查类工具的**成功信号是「沉默」**——没问题就不输出。而它的失败模式又常常是
「什么都没检查」——也是沉默。两种沉默在终端里长得完全一样，退出码也一样。

而人看输出时的默认判断是「没报错就是没问题」，于是坏掉的检查比没有检查更糟：
它给出的是一个**虚假的保证**。

这四处的具体机制各不相同（`|| true` 吞退出码、并发让超时判据失真、
`t.Skip` 返回 0、工具版本不匹配），但**症状同形**——所以每次都是当成独立问题
修的，修完第四处才看出来这是一类。

**解决**

对每一处，让「没跑成」显式地长得不像「跑成了」：

- 红线扫描器：退出码 2 单独报出来，CI 里区分 1（命中）与 2（故障）
- 变异测试：固定串行、脚本在超时条数过多时打印「这个分数不可信」
- 集成测试：CI 里显式检查输出中一个 `--- PASS` 都没有、或出现 `--- SKIP` 就报错
- golangci-lint：把「工具版本」这件事写进 AGENTS.md，并锁住 CI 里的版本

**预防**

- **写检查工具时，第三件事是想「它坏掉时会输出什么」**（前两件是它该抓什么、
  它该放行什么）。如果坏掉时输出「通过」，就必须额外做点什么。
- **判据不要只看退出码**（`t.Skip` 与真正的通过都是 0），也不要只看
  「有没有错误输出」（没有输出既可能是干净也可能是没跑）。
  用工具能给出的**正向证据**：命中的条数、PASS 的条数、检查过的文件数。
- **异常值要像异常值。** 一个「0.00%」和一个真实的「质量不行」在屏幕上
  没有区别，所以要么让工具自己报出来，要么固定住那个会漂移的变量。
- 同一个症状第二次出现时，先问「这是不是同一个问题的另一个面」。
  这个项目里它出现了四次，前三次都当成独立问题修了。
- **在管道里判测试结果，等于把退出码交给最后那个命令。** `cmd | grep X` 的退出码是
  `grep` 的：**没有匹配就是 1，与 `cmd` 成功了没有无关**。而如果后面还接了
  `echo` 或一个赋值的命令替换，连那个 1 也看不到。
  **正确形状**：`go test ./... -count=1 > log 2>&1; echo $?; grep ... log`——
  落盘再看，退出码在落盘那一刻就固定了。
  **这一条是 2026-10-28 现场踩的**：一次「零 FAIL」的回报，证据是一条把退出码
  冲掉的管道。重跑带真实退出码才作数。
- **汇总句是最容易变成没人核的断言的东西。** 「九道门禁全过」读起来像结论，
  实际是一句没有出处的概括——它把九个独立的结果压成一个数字，而那个数字
  没有任何一次执行直接产出过。其中一道恰好**没跑成**（命令落到坏掉的 shim 上、
  直接退出）时，汇总仍然是「全过」，因为在写汇总的人眼里它从没红过。
  **写法**：逐道列名字与退出码，或者至少写「跑了哪几道」。**没有出处的概括
  不是结论，是记忆。**
