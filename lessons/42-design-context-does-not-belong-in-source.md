# 42 · 设计上下文会被顺手夹带进源码，而它读起来像一条正常的注释

**编号** 42 · **日期** 2026-10-18 · **摘要**：任务交给 agent 时，它会把自己刚在讨论里
知道的东西写进最近的那个文件——需求来源、取舍过程、「本轮范围」。这类句子**不违反任何
现有门禁**（红线扫描抓的是形态：密钥、主机、本机路径），**读起来也像一条认真的注释**，
于是没人问它一句「这句话是给谁看的」。

**现象**

两处形态，发现时各有一个实例：

1. **范围语**（规划过程的残留）：`internal/ledger/store/posting_test.go` 的
   「…不在本轮范围」、`store_test.go` 的「（不在本轮范围）」。它们说的是**当时那一轮
   开发的范围**，而不是代码本身的性质——半年后读的人不知道「本轮」是哪一轮，
   只知道自己错过了某个上下文。（发现时已改成陈述代码性质的说法。）

2. **把设计取舍写给使用者看**：`larkaxctl` 的帮助文本里塞着「`-o` 是行业惯例
   （kubectl、gh）」「`-V` 打版本、`-v` 是详细模式，与多数工具相反」这类句子。
   它不是错的，是**放错了地方**：使用者要的是「怎么写这条命令」，而
   「我们为什么这么定」是协作者的事（#543 / #544 修的就是这个）。

**原因**

- **agent 的信息源就是那段对话**，而「把刚知道的东西写下来」是它的默认动作：
  写注释时最省力的素材，恰好就是刚讨论过的那一段。
- **「这个仓库是公开的」对它不是一个感觉，是一条要去记住的规则。** 红线扫描器
  抓不到这类句子——它按形态抓密钥与主机，抓不到「谁提的、为什么现在做」，
  于是泄漏了也**没有任何反馈**。没有反馈的规则会被慢慢磨损。
- 评审清单里没有这一条，所以即使有人读 diff，读到的也是「一条在解释为什么的注释」。

**解决**

界限一句话：**注释解释「为什么」是可以的，但要绑在代码上**——为什么用这把锁、
为什么是这个顺序、改错会怎样、哪条用例钉着它。**不许写**需求来源、讨论过程、
谁提的、排期，以及「本轮 / 这次 / 本次范围」这种只有当时在场的人才懂的指代。

评审时加一问：**这句话是给「读代码的人」看的，还是给「当时在讨论的人」看的？**
后者删掉——它要留，就留到仓库外的笔记区。

**能机器判的那一半要判，剩下的那一半只能靠评审读。**

- 可判：**面向使用者的文本**（帮助、文档、错误与提示）里不该有设计理由。
  这一半有硬边界——读者是使用者，谈「取舍」一定放错了地方，所以它能被一个词表
  挡住：命中即红。红证是把那句「`-o` 是行业惯例（kubectl、gh）」搬回根帮助——
  搬回去，它就红。
- **剩下的那一半脚本覆盖不了，只能由 review 逐条读。** 词表判据在全仓没有边界：
  实测 `决策` 255 处、`会话` 79 处、`本次` 71 处、`取舍` 58 处，绝大多数是技术词与
  领域词（`systemone` 的 `Decider`、账本的「本轮对账」与「本轮跳过的行」、插件的
  「会话」）；词表在这里假阳性泛滥，而**一份没人认真看的报告等于没有门**——
  与 `docs/development.md` 的「golangci-lint」一节要求 `golangci-lint` 只开有价值
  检查器是同一个道理。所以这一条**是 review 的活**，不写成扫描器。

**预防**

- 任务书里写死这一段（与红线并列）：注释只解释「为什么这么写」，不写「为什么现在做」。
- **派 review agent 时把这一条写进它的任务书**，并要求它逐条回答：
  「这句话是给读代码的人看的，还是给当时在讨论的人看的？」——脚本照不到的地方，
  只能靠这一问。发现范围语时，把它改写成对**代码性质**的陈述。

**关联**

- 第 39 条（一句话会被多个入口返回给使用者）：面向使用者的文本这一半，与它是同一族。
- 第 2、7 条（扫描器坏掉时的输出与「干净」长得一样）：所以「可判的那一半」才要写成门，
  而它必须带自测。
