# 56 · 拿基线做对照时，不要覆盖工作树文件

**编号** 56 · **日期** 2026-10-27 · **摘要**：为了证明「这次改动没弄坏东西」而把同一个
文件切成旧版本跑基线时，`git show HEAD:file > file` 会覆盖工作树；未提交的改动只剩在
暂存区里，而 `git diff --cached` 看起来一切正常。

## 现象

为了证明「这次改动没弄坏东西」，需要拿改动前的版本跑一遍同样的命令，对比结果。
一个很自然的写法是：

```sh
git show HEAD:web/src/api/types.ts > web/src/api/types.ts
npx vitest run
```

跑完之后，工作树里的文件**已经被覆盖成 HEAD 版本**。如果改动当时还没 commit，
它就没了。

## 为什么危险

`git status` 会显示 `MM`：第一列是暂存区、第二列是工作树。改动只在暂存区里活着。

- `git checkout .`、`git restore .`、`git stash` 都会把它抹掉
- 更糟的是**看起来没坏**：`git diff --cached` 仍然显示完整的改动，
  于是「改动还在」这个观察成立，而它其实已经不在工作树里了
- 接下来任何一条命令（跑测试、跑 lint、跑门禁）读的都是**旧版本**

这一步一旦漏掉，后面所有「跑过了、是绿的」都白说——它们验的是另一个文件。

## 三种不会丢改动的做法

```sh
# 1. 先暂存，测完 pop
git stash push -- <文件>
<跑基线>
git stash pop

# 2. 写到仓库外的临时路径
git show HEAD:<文件> > /tmp/baseline.ts
<把 /tmp/baseline.ts 拿去跑>

# 3. 另开一棵树（基线测试要跑几分钟时最干净）
git worktree add /tmp/base origin/main
```

第 3 种最稳：它不碰当前工作树的任何东西，而且能同时保留「改后」与「改前」两份，
不必来回切。

## 判据

跑完基线之后、继续之前，`git status --short` 必须是**单列**（`M ` 或 ` M`）。
出现两个字母（`MM`）就说明暂存区与工作树不一致，先弄清哪一份是对的。

**不要靠 `git diff --cached` 判断改动还在不在**——它只看暂存区。
要看工作树，用 `git diff`（不带 `--cached`）。

## 关联

- 第 16 条（「跳过」与「通过」在输出里长得一样）：这里也是同一个毛病——
  「改动还在暂存区」与「改动还在工作树」在 `git diff --cached` 的输出上长得一样，
  而后面所有命令读的是后者。

## 变体：同一棵树上有别的执行者正在写

上面三条做法都以「这棵树此刻只有我在写」为前提。**并行环境里这个前提不成立。**

一次变异测试（改坏实现、跑用例、看红不红、再恢复）在同一个文件上进行，恢复用的
快照**拍在了另一个执行者刚写了一半的文件上**。恢复动作把它的新代码回滚掉，测试
短暂变红，两边都以为是自己或对方的问题。

判据：

> **要改文件再恢复，先确认没有别人在写这个文件。** 做不到就等它交付——变异测试
> 本来就不必抢在写码中间做，等交付后在干净的树上做，判别力一样，风险为零。

「改坏—验证—恢复」这类动作比 `git show > file` 更隐蔽：它看起来是自己在操作自己的
文件，而实际恢复的是**别人也在写的那份状态**。同一条判据：**动的那个文件是谁的，
比此刻谁在敲键盘更要紧。**
