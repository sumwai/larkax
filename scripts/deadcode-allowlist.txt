# check-deadcode.sh 的白名单：允许暂时不可达的符号。
#
# 格式，一条一行，四栏用 | 隔开（理由里不能出现 |）：
#
#   <文件路径> | <符号名> | <类型> | <理由>
#
# 路径与符号名取 deadcode 输出里的那两栏（`path.go:12:3: unreachable func: Name`
# 取 `path.go` 与 `Name`），**不带行号**——行号会随任何一次编辑漂移，
# 那样每改一行代码白名单就得全量重写，第二次就没人维护了。
#
# 类型两档：
#
#   lib  库构件。先有库、后接线是这个仓库刻意的顺序，库构件本来就该先有、先被测。
#   gap  被追踪的缺口。理由里**必须**带一个 issue 号（`#123`），
#        否则 check-deadcode.sh 会拒绝这份白名单。
#
# 这一档的用处是让 review 能问出「这一条为什么还在」：lib 的答案是「它是积木」，
# gap 的答案是「有一个 issue 在跟」。
#
# **lib 那几条的理由要写清「目前只有测试在调」**——「有实现、有测试、没有调用方」
# 的符号，看代码的人会以为它已经生效。理由栏说不清的事，对应函数的注释里要补一句。
#
# 本文件按 <路径> 再按 <符号名> 排序，与 deadcode 的输出顺序无关——
# 比对按集合做，加一条或删一条只动一行。
#
# 这份清单产出时的条件（换任何一个，条数都不可比）：
#
#   命令      deadcode ./cmd/larkax ./cmd/larkaxctl
#             （扫描起点由 cmd/ 自动发现，这两个就是当前发现的全部）
#   工具      golang.org/x/tools v0.52.0（脚本里的 PINNED_TOOLS_VERSION）
#   条数      59，与脚本里的 MAX_ENTRIES 一致
#
# **条数从 60 跳到 112 的原因**——这一条要与「条目数只许减不许增」的规矩一起读。
#
# `internal/plugin` 这一片（#261）首次被生产代码 import，于是它**第一次进入
# deadcode 的分析范围**：在此之前整包没人 import，它根本不在被分析的那张图里。
# 它那 52 个契约符号（hook 调用点、会话派发、补丁应用、契约类型的解码）是这一片
# **按边界刻意不接**的东西，全部记成 `gap | #216`，由 #262 / #263 / #264 三片
# 逐片接上、逐片从这份清单里删掉。
#
# 也就是说这一跳是**结构性的**：一个包刚进入视野，而不是有人拿白名单把新出现的
# 不可达符号按住。判据是问一句「这些符号是因为有人接了什么才变多的，还是因为
# 有人躲了什么才变多的」——这里是前者。**#262–#264 落地时条数要跟着降回来。**
#
# 112 之后减了 8（#245）：上游用量的归一收成一处实现，`internal/tokens/normalize.go`
# 整文件删除，它名下 7 条随之消失；`internal/route/stream.go` 的
# `WrapStreamStarted` 也一并删掉，是第 8 条。所以那一轮之后是 104。
#
# **104 之后减了 43（#262）**：`onRequest` / `onResponse` 接上之后，请求侧的
# 注册表选插件、会话派发、补丁应用与严格解码、请求/响应的上下文转换都真的被
# 调到了，那一片条目随之从这份清单里删掉。剩下 61 条是 onRoute / onStream /
# onUsage 三片（#263 / #264）与其它还没接线的构件。
#
# **61 之后减了 2（#263）**：`onRoute` 接上之后，`adapter.go` 的
# `RouteContextFrom` 有了生产调用方，它下面的 `healthName` 随之可达——两条一起
# 从清单里删掉。**onStream / onUsage 那两片（#264）还没动**，所以这次只减 2。
#
# ⚠️ **在这一片包上，「报告里没有」不再等于「已经接上」。** `contractFieldNames`
# 里那句 `reflect.TypeOf` 随 #262 变成可达之后，RTA 的反射过近似生效：`internal/plugin`
# 里凡是「运行时类型的方法」一律被判成可达，`deadcode -whylive` 对它们一律回
# `reachable only through reflection`，没有静态调用路径。所以下面这几类符号是
# **在报告里消失、而实际没有接线**的：`Session.OnStream` / `Session.OnUsage`
# （#264 的缺口）、`Registry.Get`、`Result.Failed`
# 一类没有生产调用方的方法。删掉它们是对的——白名单要跟的是 deadcode 的输出，
# 不是「已知缺口」的账本（那个账本在 issue 里）——但要清楚删掉不等于接上了。
#
# 判据：`deadcode -whylive` 对某条回 `reachable only through reflection` 时，
# 「它可达」是分析器的近似，不是有人调了它。这与「有门与没门在输出上长得一样」
# 是同一个形状（见 LESSONS 第 22 条）。
#
# 关掉一批缺口之后，把这些行删掉、并把 MAX_ENTRIES 往下调。
# 忘了删不会失败：脚本只会提示「这一条已经可以删了」。
