# larkax 的文字标准

这份是**怎么写**，不是**谁做什么**。谁审、什么时候审，见
[`larkax-workflow`](../larkax-workflow/SKILL.md)。

## 一、不要把一句能说的话，收紧成一个词

这是这一节的总原则。一个说法如果**要展开成一句话才讲得清**，那读者就得先知道
那句话是什么，才读得懂你这个词——而你本来可以直接写那句话。

| 收紧成的词 | 它展开是什么 |
|---|---|
| 留痕 | 把这件事记下来，之后能查到 |
| 钉住 | 用一个具体的值把这条边界固定住，改了它就红 |
| 收下 | 白名单里允许这个符号 |
| 兜底 | 主路径失败时还有一条退路 |
| 门禁 | 提交前必须过的那几个检查脚本 |
| 在飞 | 正在做 |
| 尾巴（决策尾巴） | 留在公开场域里的待定事项 |
| 硬接 | 为了过检查而造一个假调用方 |
| 刷空 | 把白名单清空 |

**也不是所有短说法都该改。** 判断在「展开之后，是不是比你那个词更清楚」：

- 「上游」展开是「被我们中转的那个服务方」——更长，但在面向使用者的文档里确实
  更清楚，所以第一次出现时值得展开一次，之后可以简写；
- 「白名单」展开是「允许通过的条目」——它和「黑名单」是一对标准说法，压缩没有
  损失，可以直接用。

判据落到一句话：**这个词，一个中文很好、但不在这个圈子里的人，要不要先猜一下
才读得懂？** 要，就换成那句他能直接读懂的话。

**已有的文字不回头改**：上表左列那些词在仓库里已经用了几百处，为它们翻新旧文
不值得。新写的段落照这条规矩来；同一段里保持一种说法就够。

## 二、断行：断点落在读者本来就要停的地方

中文没有词边界，所以「字数到了就断」看起来像被机器截断。仓库里有一处真的
（`internal/keyquota/quota_test.go`）：

```
// 把 `>` 改成 `>=` 时两边一起变，用例照样通过（见 docs/development.md 的「用常量
// 测常量等于没测」）。
```

断在引号内部，读者要在行尾与行首之间把「用常量测常量等于没测」接回去。

**好的断点在标点之后、两个子句之间**——读者在那里本来就要停一下。
自查的办法：把断点两边的字连起来念一遍，卡住了就是断错了。

另一样：同一段里各行的长度别差太多。一行 47 字、下一行 28 字，视觉上头重脚轻，
即使断点在句界上也不好看。

**改别人的段落时要重排折行。** 替换一处更长的字符串，旧的折行不会自己跟着变，
于是断点落在引号、括号或短语内部的半截上——`human-taste` 这套标准就是为这一类
问题写的，因为它发生得比想象中频繁。

## 三、指代：不写给当时在座的人

「本轮」「这次」「本次范围」「按之前定的」「上面说的那个」，以及需求来源、讨论过程、
谁提的、排期——这些是写给当时在讨论的人的，不是写给读这份文字的人的。

改写方向：把「为什么**现在**做」换成对**文字所描述的那个东西本身**的陈述。

## 四、怎么用

- **写之前**：过一遍，尤其是要动别人已经写好的段落时。
- **写之后**：拿它当清单逐条检查——自己查，或者让一个评审带着它查
  （[`reviewer`](../../agents/reviewer.md) 的判据表里，「用词」与「格式与排版」
  两行说的就是这件事）。
- **不要做成脚本。** 「这个词展开之后是不是更清楚」「这个断点卡不卡」，机器分不出来
  ——它不知道这段字是写给谁的。这类判断要么靠人读，要么靠一个知道该说给谁听的
  agent 读。
