# larkax 开发流程

本文件说明**我们怎么让这个仓库动起来**：谁做什么、怎么交接、怎么算做完。
仓库是什么样、代码怎么写、文档怎么写，看 [`AGENTS.md`](../../../AGENTS.md)。

## 一、先认清你戴哪顶帽子

每个会话只戴一顶。戴错了比做慢了更糟。

| 角色 | 唯一职责 | 不能做 | 判据在哪 |
|---|---|---|---|
| **主控**（orchestrator） | 拆任务、派活、集成、提交、开 PR、合并、记账 | **不写业务代码**；不进实现细节 | 本文件 |
| **实现**（impl） | 在自己的 worktree 里写代码与测试 | 不碰 git 状态；不建 PR；不合并；不碰别人的目录 | 本文件 |
| **评审**（reviewer） | 只读，独立产出判据与风险清单 | 不改任何文件；不转述实现者的自我评价 | [`.claude/agents/reviewer.md`](../../agents/reviewer.md) |
| **验证**（verifier） | 在真实环境里端到端跑 | 不改代码；不开 PR | [`.claude/agents/verifier.md`](../../agents/verifier.md) |
| **分诊**（triager） | 消化报告，只把结论回给主控 | 不直接面向用户；不替主控决策 | [`.claude/agents/triager.md`](../../agents/triager.md) |

**文字怎么写才算好，不是一顶帽子，是一套标准**，在
[`larkax-human-taste`](../larkax-human-taste/SKILL.md)——写的人照它写，审的人拿它查。

**主控的硬边界**：主控下场写业务代码，是这一轮开始失控的第一个信号。哪怕只改一行，也该派出去。

## 二、一条 issue 的一生

| 步 | 做什么 |
|---|---|
| ① 选活 | 按优先级 × 依赖 × 机器余量挑一条；先确认它不是在「僵着」 |
| ② 建 workspace | worktree + 分支 + 独立数据库，每 issue 一套，互不干扰 |
| ③ 派活 | 起 agent，把任务书发过去 |
| ④ 实现 | 干活；卡住就回报卡在哪（沉默不算进展） |
| ⑤ 评审 | 另起一个评审，同 worktree、只读、独立判据 |
| ⑥ 集成 | 主控核对证据 → 提交 → 跑门禁 → 开 PR |
| ⑦ 合并 | CI 绿 + 评审过 → 合并。**PR 里带迁移时**：先看 `origin/main` 的 `internal/migrate/sql` 里最大的号，比 PR 新增的号大就先改号再合（未部署过才改），或者把两条带迁移的 PR 按号从小到大合——见 [`LESSONS.md`](../../../LESSONS.md) 第 45 条 |
| ⑧ 清理 | 关会话、删 worktree / 分支 / 容器（**先确认 PR 已 MERGED**） |
| ⑨ 记账 | 更新状态文件；在 issue 上留一条状态评论 |

⑨ 之后回到 ①。

**异常三条路**，现在最容易失控的就是它们：

- **卡住**：实现者回报卡点 → 主控判「补信息 / 换做法 / 降级开新 issue」，不静默重试。
- **要决策**：不打断用户 → 能定的先定，定不了的攒起来一次讲（见第五节）。
- **信号丢失**：超过预期时间没回报 → 主动查状态、问一句。**不假设它还在跑。**

## 三、派活的形状

任务书缺任何一项，这一轮就注定要来回收拾：

- **目标**：一句话说清要什么。
- **完成判据**：怎么算做完，且**可执行**（要跑哪个命令、看到什么才算过），不是「实现好了」。
- **边界**：**不许碰什么**——哪些目录/包/文件、哪些命令（尤其是改 git 状态的）。
- **环境**：能用什么、不能用什么。
- **回报方式**：做完或卡住时发给谁、消息里放什么。
- **主控是谁**：会话名，否则它不知道往哪回报。

**关键纪律要内联进任务书**，不要只写「见某文档」——对方未必会去翻。

## 四、回报的形状

**完成 = 主控看到证据**（门禁通过 / CI 绿 / 复现用例红了再绿）。
以下三条**都不算**：它说「做完了」、它不动了、状态显示 `idle` / `done`、命令退出码是 0。

消息格式（第一行必须能独立看懂）：

1. 第一行：哪个 issue，做完还是卡住。
2. 5–10 行要点：改了哪些文件、加了几条用例、验证结果、剩余边界。
3. 报告正文的位置。

**不要把大段 diff 或整份报告贴进消息。**

## 五、决策分流

| 类型 | 谁定 |
|---|---|
| 库/框架选型、包结构、命名、错误处理、测试策略、文档措辞 | 自己定 |
| 涉及**钱**的规则、对外契约的破坏性变更、架构级不可逆选择、权限边界 | **不自己定** |
| 上面两类之外、拿不准的 | 先问决策模型；它有结论就用结论，并把结论写进去 |
| 决策模型也定不下来的 | 攒起来，**一次讲一条**给用户，不要零散打断 |

拿不准又必须动的，选保守、可逆、默认安全的做法，并说清选了什么。

**不要在公开场域留决策尾巴**：issue / PR / 评论里不出现「要定的事」「请拍板」这类话。

## 六、已知的失败模式

每一条都「看起来很合理」：

| 看起来像 | 实际可能是 | 该怎么办 |
|---|---|---|
| 它不说话了，应该在忙 | 可能已经停了 | 主动查、问一句；不假设还在跑 |
| 状态显示 `done` | 可能一件事都没做 | 看产出物在不在（报告、worktree 里的改动） |
| 门禁退出码是 0 | 可能压根没跑（被别的锁挡住） | 看汇总表里每道门都有 PASS/FAIL |
| 评审也说「没问题」 | 可能只是在复述实现者的话 | 评审必须独立看代码与 diff |
| 主控顺手改了一行 | 这一轮开始失控 | 派出去 |
| 同一条 issue 派给了两个会话 | 两人在同一棵树、同一批路径上互相覆盖；后撤的一方按文件名撤回，会把对方那一版一起删掉 | 一个 issue 只有一个写者。改派时**先让上一个人停手、并说明这棵树归谁**；发现时间窗重叠时，先让两边核对再动手 |
| 测试通过了 | 可能只是覆盖到了，没钉住行为 | 关键逻辑要看变异测试，见 [`docs/development.md`](../../../docs/development.md) 的「变异测试」 |
| 一个常量既是输入又是判据 | 等于没测 | 用字面量钉（见 `LESSONS.md`） |

## 七、评审看什么

判据在 [`.claude/agents/reviewer.md`](../../agents/reviewer.md)：九个维度、两条纪律
（独立、不确定就说不确定）、`web/` 改动的另一份清单、输出格式。**这里不抄第二份。**

一句话：让一个 agent 扮演**对这个项目一无所知的 reviewer** 去审 diff。主控自己过一遍
的时候，也读那份表逐条走。

## 八、测试角色

**日常开发**：跟随改动写针对性的测试即可，不要求全量 e2e。

**发布新版本时**：跑完整测试，包含：

- **端到端测试**：从客户端 SDK 到上游的完整链路（OpenAI 与 Anthropic 两套协议各一遍）
- **变异测试**：对核心计费与账本代码做变异测试。计费算错是这套系统最贵的 bug，
  变异测试能发现「测试通过了但逻辑是错的」这类问题（怎么跑、分数怎么读，见
  [`docs/development.md`](../../../docs/development.md) 的「变异测试」）

**扮演首次使用者**：测试时让 agent 扮演**第一次使用 larkax 的用户**，给他一个目标
（例如「我要用 larkax 调 Claude 模型」），**不带任何已有上下文**，让他从文档开始
自己摸索。任何让他卡住、需要猜、找不到的地方都是缺陷。

**老用户视角**：如果改动会影响既有用户的使用习惯（改配置格式、改参数名、改默认值、
改界面路径），**另起一轮**让 agent 以老用户视角测试，确认不会造成困扰或静默的行为变化。

## 九、并行与分工

主会话负责：拆解任务、定接口边界、集成、决策、管 PR。实现细节交给子代理——
把读文件、试错、跑测试吃进主会话的上下文，后续轮次就只能在被压缩过的摘要上
做判断，而判断质量会随之下滑。

| 什么样的活 | 谁做 |
|---|---|
| 开新包、重写已有包、跨多文件调研 | 子代理 |
| 定接口、写决策、合并 PR、修一行 | 主会话 |

**每轮开始时先规划**：把这一轮的活拆成**互不重叠的文件集**，让多个子代理
能同时开工，而不是串行等一个做完再想下一个。

任务书按第三节那几项写，另外这几条纪律要**内联进任务书**，不要只写「见某文档」：

- 只跑与自己目录相关的 `go build` / `go vet` / `go test` / `gofmt`
- 禁止任何改动 git 状态的命令（`add`/`commit`/`checkout`/`stash`/`switch`）
  与 `go mod tidy`——多个代理共用一棵工作树时，这些会互相破坏
- **PR 的创建与合并由主会话做**，保证 GitHub 流程一致，也避免多个代理同时操作远端

**但不要每改一次就叫一轮。** 起一个 agent 要花几分钟、烧掉不少 token，而它做的大部分事
（跑 `gofmt`、`go vet`、`go test`、读 diff、看排版）谁都在做。所以：

| 改动性质 | 怎么做 |
|---|---|
| 日常小改（改文案、加个函数、修拼写） | 自己跑命令检查，不起 agent |
| 一次功能改动完成 | 自己检查；只有触及计费、账本、协议转换这类高风险区才起 review agent |
| 准备发新版本 | 起完整的测试与 review agent，此时不省 |

自己动手时，把 [`reviewer.md`](../../agents/reviewer.md) 的判据表与上一节的清单
当成自查表逐条过一遍——它们的价值在清单本身，不在「由另一个 agent 来执行」。

### 派活之前先过五条

这五条管的是**这一批活该不该拆、该怎么拆**。上一节管「这一次该不该起 agent」，
两者一起用。每一条都配一个「怎么看出走偏」——走偏时任务书读起来是合理的。

| 规则 | 怎么看出走偏 |
|---|---|
| **先看有多少东西**：几行命令答得完，自己答 | 任务里写「全部」「每一个」 |
| **按问题拆，不按材料拆**：后面的人要读前面全部，就是拆错了 | 非得等齐才能开工 |
| **收尾自己做**：合并、划线、下结论是自己的活 | 最后一步要吃前面全部结果 |
| **结果写成文件**：按说好的路径取，别去翻对话记录 | 得回头找结论在哪 |
| **没定清就别开工**：范围、取舍、交什么，先问 | 任务里还有「待定」 |

几条补充：

- **「穷尽」只在需要钉住边界时用。** 问「有没有规律」时，找到正反例就够了；
  问「这条路径有没有例外」时才逐条追。任务书里出现「穷尽」，先问一句这个穷尽
  换来的是什么。
- **一个 agent 只答一个能判对错的问题。** 完成判据写不成「跑哪个命令、看到什么
  算完」，这条任务就不用派。
- **真存在全依赖时，重新切维度。** 让每个下游只吃自己那一片；做不到就让主线
  串行做掉。把一件串行的事拆成几段再合起来，一秒都没省。
- **结果落文件，路径事先约定。** 转录大小不受控，往上下文里塞一次就可能爆；
  而收口那个 agent 一旦失败，从转录里重新捞结论要花的时间比整件事还长。
  落盘位置在仓库外——设计文档与调研笔记不进仓库（见 [`AGENTS.md`](../../../AGENTS.md)
  的红线）。
- **会改变产出形状的约束，起之前问。** 范围、取舍、交什么，这三样没定就起，
  多半整个丢掉重来。第一版 workflow 在约束确定前启动、三个阶段全废，就是这一条
  （[`LESSONS.md`](../../../LESSONS.md) 第 55 条）。

## 十、开 PR 之前跑哪些门

判据不是「这道门对我的改动有没有意义」，而是「**有没有哪道门可能因为这次改动而失败**」。
按这个判据缩范围，不要一律全套：

| 改了什么 | 至少跑这些 |
|---|---|
| 只有 `.md`、`.gitignore` 这类非代码文件 | 红线扫描、索引与正文一致性 |
| 动了 `.go`（**只改注释也算**） | 再加 `gofmt -l .` 与 `golangci-lint run` |
| 动了某个门禁脚本 | 那条脚本自己的自测（`scripts/check-*.test.sh`） |
| 动了计费、账本、金额 | 全套，含变异测试 |
| 拿不准 | 全套 |

**只改注释也算「动了 `.go`」**：`golangci-lint` 的 `revive` 开着 `exported` 与
`package-comments` 两条注释规则，改注释能让它红。这个工具未必装得上，
所以改完 `.go` 别只在本机自查（怎么跑见 [`docs/development.md`](../../../docs/development.md)）。

**CI 对每个 push 都跑全套**，所以跳过哪一道都是在赌它不会挂——这张表是把赌注缩到
说得清的范围，不是省事的借口。**先把「这次改了什么」列出来再决定**，
不要按「开 PR 前总要跑一遍」的惯性启动。

## 十一、改完文字按 larkax-human-taste 过一遍

**什么时候**：改动了任何面向人的文字之后——注释、文档、命令行的帮助与错误文案、
issue 与 PR 描述、commit message。

**为什么不能省**：改字的人注意力在「说得对不对」上，不在「读起来顺不顺」上。
替换一处更长的字符串，旧的折行不会自己重排，于是断点就落在了引号内部：

```
// 用例照样通过（见 docs/development.md 的「用常量
// 测常量等于没测」）。
```

标准在 [`larkax-human-taste`](../larkax-human-taste/SKILL.md)：好文本长什么样、
哪些说法是把一句能说的话收紧成了一个词、断点该落在哪儿。**它是一套标准，不是
一顶帽子**——写的时候照着来，写完拿它当清单查，或者让
[`reviewer`](../../agents/reviewer.md) 带着它审。

**不要做成脚本。** 一个说法能不能展开得更清楚、一个断点卡不卡，机器分不出来——
它不知道这段字是写给谁的。
